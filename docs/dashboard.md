## 8.1 Signing in

Code: `apps/api/src/auth/` and `apps/web/src/features/auth/`.

### Who can sign in

The install's first account is its **owner**, created with the setup link ([below](#creating-the-owner)), which also names the instance ([Settings](#settings)). Other users are admins or members, with access per area and project ([access](access.md)). They join by invitation: an owner or admin copies a link from the Members page and sends it, or with SMTP set up, Ottertrail emails it too ([access](access.md#invitations)). Nobody can sign up on their own: open sign-up is planned for the hosted service, which will also verify new addresses by email.

### Creating the owner

There is no default password. Whoever runs the install creates the owner, on the server, in the instance's folder ([deployment](deployment.md)):

```sh
docker compose exec api node dist/setup.mjs
```

In development, the same command is `vp run setup`. The sign-in page, while no owner exists, and the setup page, opened without a link, say to run it, in both forms.

The command prints a link such as `https://analytics.example.com/setup#token=…`. The pages before signing in (sign-in, Forgot password, setup, an invitation, a reset link) share one layout (`features/auth/auth-layout.tsx`): the canvas the app sits on, the brand mark, and one panel holding the page's title, a line on what it does, and its form. On a phone the panel drops its frame, so the fields take the screen's width. `auth-pages.test.tsx` checks each page's fields, errors and success at 390 wide, the token staying in the fragment, and the panel at 1440.

**Forgot password.** With SMTP set up (`GET /api/setup` says `emailConfigured`), the sign-in page has a "Forgot password?" link at the right of the Password label's row, which opens `/forgot-password`: "Reset your password", one Email field, and "Send reset link". Its answer is the same for every address ("If an account uses that email, we'll send a reset link. Check your inbox and spam folder."), with "Back to sign in"; past the limit it says "Too many reset requests. Wait a little, then try again." Without SMTP there is no link, and one quiet line under Sign in says "Forgot your password? Email isn't set up on this instance, so ask the person who runs it for a reset link."; the page, opened directly, says the same instead of its form. The emailed link opens the reset page, which is unchanged ([access](access.md#account-email)). `account-email.test.tsx` covers both sign-in pages, the answer, the limit, and the page without email.

Opening it shows a form for the owner's name, email, password and its confirmation, the workspace name (the instance's name in the sidebar), and the timezone reports count days in, the browser's chosen at first; all are saved with the account. The API checks the confirmation and the timezone too, as the settings page checks a timezone. A line says whether alert email (`SMTP_URL`) is set up on the server, and how to set it when not. The link:

- works once, and for one hour; running the command again replaces it;
- stops working for good once an owner exists, and the command then refuses;
- carries its token after `#`, in the fragment. Browsers never send the fragment to a server, so the token cannot end up in request logs or proxy logs. The page reads it, then removes it from the address bar.

The database stores only a SHA-256 hash of the token, so reading the database does not reveal a working link. Using the link, checking that no owner exists, and creating the account happen in one transaction, and a unique index allows at most one owner, so two people opening the same link at once cannot both become owners.

A setup page that let the first visitor become the owner would hand a freshly deployed instance to whoever found it first.

The setup endpoint is public, so it does the cheap work first. It refuses a request when an owner already exists or the link is invalid, which costs one database query, before it hashes the password, which costs about 40 ms and 32 MB on purpose. Attempts are also limited per client address: 10, then one a minute. Without that order, anyone could send made-up links and keep the API busy hashing.

The owner's email must pass the check sign-in uses (Better Auth checks addresses with zod's `z.email()`), which is stricter than the usual email format: `ops!alerts@example.com` is refused. Otherwise setup could create an owner who can never sign in, and setup cannot run again once an owner exists. A code review found both of these problems.

### Sessions

Signing in creates a **session**: a random token stored in the `dashboard_sessions` table and sent to the browser in a cookie. Each request carries the cookie; the API looks the token up to know who is asking.

- The cookie is `httpOnly` (page scripts cannot read it, so an injected script cannot steal it), `SameSite=Lax` (another site's background requests and form posts do not carry it; following a link to the dashboard does), and `Secure` over HTTPS.
- A session lasts 7 days and renews while in use. Signing out deletes the session, so its cookie stops working at once, even if it was copied. A signed token that the server does not store (a JWT) could not be revoked before it expires.
- Session rows keep the browser's User-Agent but no IP address; a check constraint rejects one.
- Each user sees their sessions on [Account settings](#account-settings), and signs out any of the others there.
- Requests that change something must come from a trusted origin (the instance's own `PUBLIC_URL`), which blocks cross-site request forgery: a page on another site cannot sign someone in or out.

The session token is stored as it is in the database, so anyone who can read the database could act as a signed-in user. Database access must be protected like the dashboard itself.

### Passwords

Passwords are at least 12 characters and are stored as scrypt hashes. scrypt is slow on purpose and needs a lot of memory, so guessing passwords from a stolen hash costs time and hardware. Sign-in attempts are rate-limited per client address; the API passes the address it trusts (from `TRUST_PROXY`), so a client cannot dodge the limit by sending a fake `X-Forwarded-For` header.

### Built on Better Auth

[Better Auth](https://better-auth.com) handles passwords, sessions, cookies, origin checks, and rate limits. Ottertrail uses only its core (email and password, database sessions), with no plugins, and keeps the owner, setup, roles, invitations, and reset links in its own code and tables ([access](access.md)). Most of Better Auth's security advisories in 2026 were in plugins this setup does not use. The version is pinned; an advisory that affects the core means a new Ottertrail release.

Settings that differ from Better Auth's defaults, and why:

| Setting                                   | Why                                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Sign-up disabled                          | The owner comes from the setup link; teammates come by invitation.                                     |
| No IP address on sessions                 | Ottertrail keeps no IP addresses.                                                                      |
| Rate limits keyed on the API's own header | Better Auth reads `X-Forwarded-For` by default, which a client can forge.                              |
| Origin and CSRF checks always on          | Better Auth turns them off when `NODE_ENV` is `test` unless they are set; set, they cannot be skipped. |
| Telemetry off                             | Already off by default; set explicitly so it stays off.                                                |
| Table and column names                    | Ottertrail's snake_case `dashboard_*` tables instead of Better Auth's camelCase names.                 |

### Configuration

| Variable      | Development default     | In production                                                                   |
| ------------- | ----------------------- | ------------------------------------------------------------------------------- |
| `PUBLIC_URL`  | `http://localhost:5173` | Required: the instance's HTTPS address, such as `https://analytics.example.com` |
| `AUTH_SECRET` | A fixed, public value   | Required: at least 32 random characters (`openssl rand -base64 32`)             |

`AUTH_SECRET` signs the session cookies. In development, the dashboard dev server may run on another port; any `http://localhost` port is trusted then.

### Not done yet

- Two-factor sign-in and passkeys.
- Serving the dashboard from the API in production. In development, the dashboard's dev server forwards `/api` to the API.

## 8.2 Projects

Code: `apps/api/src/projects/`, `apps/api/src/tracker-script/`, and `apps/web/src/features/projects/`.

A project is one website or app. The Projects page lists them, each with what an owner checks first: when its last event arrived ("No events yet" before the first), and, for the owner and admins, its allowed sites ("None: events are refused" without one), how long it keeps events, when it was made, and a link into its settings ("Add a site", to the General tab, when it has no allowed site). Members see the name, the last event, and when it was made. On a phone the table scrolls inside itself, the name and the link pinned, with the scroll hint. It uses only what `GET /api/projects` answers. `projects-page.test.tsx` covers its states. A project's Settings page (`/projects/<id>/settings`) has seven tabs ([settings tabs and the Save bar](design-system.md#settings-tabs-and-the-save-bar)), the chosen one in the address (`?tab=general`; Install, the first, leaves it out); a new project opens on Install:

- **Install**: the install snippet and public key to copy, "Copy setup prompt" (below), whether events are arriving, and a form for [heatmaps](#heatmaps) (off by default). Heatmaps are set here because the setting's visible effect is the snippet above it (`data-heatmaps="on"` once saved), and there is no Web analytics tab.
- **General**: a form for the name, allowed sites, how long events are kept, and the main goal.
- **Your server**: the secret key, and a form for signed user IDs.
- **Spam and bots** (`?tab=spam`): a form for data centers, blocked addresses, and blocked referrers, and "Delete spam" ([below](#spam-and-bots)).
- **Source maps**, **Session replay** (a form for the mode), and the **Danger zone**.

Each form has its own Save bar and follows [the save rule](design-system.md#the-save-rule): Save waits for a change, Discard undoes the edits, a tab with unsaved edits says so, and leaving the page with them asks first. Links into the settings open the right tab: the stack trace's "Source maps settings", the replays page's and the telemetry pages' settings links, and the overview's "Choose the main goal".

### Copy setup prompt

Beside the snippet, "Copy setup prompt" copies a prompt for a coding agent: read the instructions for agents at `https://docs.ottertrail.app/llms.txt` (`AGENT_DOCS_URL` in `features/projects/format.ts`, the one place it is written), then add the tracker, name signed-in users with a server-made signature, report caught errors, upload source maps, and send the server's telemetry over OpenTelemetry. It names this instance's address and the project's public key, and tells the agent to read the secret key from `OTTERTRAIL_SECRET_KEY`: the secret key itself is never in it. With the project's heatmaps on, it also says to add `data-heatmaps="on"` to the tracker's tag, and that `data-ottertrail-name` gives clicked elements readable names, never with personal data in them. `project-settings-tabs.test.tsx` checks the copied text, and `tests/projects.test.ts` the heatmaps part.

### The workspace and a project

The dashboard has two levels, the way hosting dashboards treat each site:

- **The workspace** (the sidebar's first group, under the instance's name): the project list (`/projects`), for the owner and admins the Members page (`/settings/members`), and the instance's settings (`/settings`).
- **Inside a project** (`/projects/<id>/…`): the sidebar becomes the project's own menu, with a switcher to the other projects and a link back to all of them. It lists the project's overview first, then its modules (web analytics, speed, users, errors, and the rest), then the project's settings. The header shows the project's name before the page title.

Every module belongs to one project (its records carry `project_id`), so a module's pages sit under the project instead of at the top with a project picker. The switcher keeps the current page: from one project's web analytics for the last 90 days, it opens the other project's web analytics for the last 90 days.

The sidebar is expanded on every screen. Ctrl B (⌘ B on a Mac) or the header's button collapses it to icons, and the browser remembers the choice (`ottertrail.sidebar` in `localStorage`). Under 60rem it is a menu in a sheet, opened by the header's menu button and closed when a link in it is chosen ([screen patterns](design-system.md#the-shell)).

A screen with a page on the docs site shows a **Docs** link at the header's end, before the shortcut hint: Web analytics links to `https://docs.ottertrail.app/web-analytics/reports/`, an error group to the section on its page, a settings tab to the tab's own page where there is one. One map, `SCREEN_DOCS` in `lib/docs.ts`, gives each route (and settings tab) its page, with `DOCS_URL`, the one place the site's address is written. A screen left out of the map, such as a project with no area open to the user, shows no link: no link is better than a page that does not explain the screen. The link opens a new tab with `rel="noopener noreferrer"`, so the docs site is not told the instance's address, and its name says what it opens ("Web analytics docs (opens in a new tab)"); under 40rem it shows only its icon. `tests/docs-links.test.ts` lists the whole map, so a new screen gets a page or no link by choice; when the docs site moves or renames a page, update the map and that list. `docs-link.test.tsx` checks the link on a report, a list, detail pages, and the settings tabs, its absence, and the phone width.

The sidebar's head and foot are the same on every page:

- **The head:** the mark and "Ottertrail", with the API's health on the right ("API online", "Checking API", or "API unreachable" with its reason in a tooltip and a Retry button; `components/api-status.tsx`, a polite live region named "API status"). Collapsed to icons, the health is a dot on the mark's corner (green, gray while checking, red), which keeps the words for screen readers and shows them, with the reason, in a tooltip on hover and focus. Retry waits for the expanded sidebar.
- **The foot:** who is signed in, after shadcn's NavUser block (`components/app-shell/user-menu.tsx`): an avatar with the initials (there are no photos), the name and email, cut off with an ellipsis when long, and an up-and-down chevron. It opens a menu, beside the sidebar on a desktop and below the button on a phone, whose header repeats the avatar, name and email (wrapped, not cut off), then **Account settings**; after a rule, **Theme**, the theme as on the Appearance tab (System, Light and Dark as radio items with an icon each, the current one checked; a choice applies at once and the menu stays open); and, after another rule, **Sign out**. Sign out ends the session, clears the query cache so nothing of this user's shows to the next, and opens sign-in. Collapsed, only the avatar shows, and its tooltip names the user. The name and email come from `GET /api/me`, read again after the account changes.
- **Text cut off** in the foot shows whole in a tooltip on hover and keyboard focus, only while it is cut off (`OverflowTooltip` in `components/truncated-text.tsx`, the shared rule for cut-off text: [design system](design-system.md#truncated-text)). The project switcher's button does the same with the project's name, and its list wraps long names.

`account.test.tsx` covers the menu (opening, Account settings, Sign out), the collapsed foot and dot, the health in the head, the tooltip for a long name, and the sheet at 390 wide.

`/projects/<id>` opens the project's [overview](#overview) when the user has one of its areas, and otherwise the first page in the menu they may open. The home page (`/`) opens the project this browser showed last (kept in `localStorage`), or else the first project; with no projects, it opens the project list.

### The install snippet

```html
<script
  defer
  src="https://analytics.example.com/t.js"
  data-key="pk_…"
  data-host="https://analytics.example.com"
></script>
```

- `src`: the instance serves the built tracker at `/t.js`, and the Web Vitals script it loads at `/v.js`. A short, neutral name, because ad-block lists often match file names such as `tracker.js` or `analytics.js`. Browsers may cache it for an hour, then check it again with its ETag, so a new tracker reaches sites within an hour. The API reads the file on each request, so a new build needs no restart; until the tracker is built (`vp run -r build`), `/t.js` and `/v.js` answer 503, and a missing one is logged once.
- `data-key`: the project's public key. It only lets pages on the allowed sites send events; it cannot read anything.
- `data-host`: where events go (`/api/events` on the same instance).
- `data-environment` and `data-release` (optional): where the site runs, such as `staging`, and which version of it ([web analytics](web-analytics.md#environments-and-releases)). The Install tab explains both under the snippet; without them, events count as `production`.

The page shows "Waiting for the first event" and checks every 10 seconds, so after installing, opening the site in a browser turns it into "Receiving events".

### Allowed sites

Events are accepted only from pages whose hostname is listed, compared exactly (step 2 of [web analytics](web-analytics.md)). So the list holds bare hostnames: `example.com` and `www.example.com` are separate entries, and there are no wildcards. The API stores each one the way browsers send it in the `Origin` header: lowercase, with internationalized names in their ASCII form (`bücher.example` becomes `xn--bcher-kva.example`). The form accepts a pasted address and keeps only its hostname; the API refuses anything else and names the entry. A change reaches the collection endpoint within a minute, the lifetime of its project cache.

### Requests from the dashboard only

The session cookie is `SameSite=Lax`, which keeps it off other sites' form posts and background requests. Sites on a sibling subdomain of the same domain still count as the same site, though, so the API also checks the `Origin` header on every request that changes something: it must be the instance's own address (`PUBLIC_URL`; in development, any `localhost` port). Better Auth makes the same check for its own sign-in endpoints.

### Keeping events

The Spam and bots tab's "Ignore visits from data centers", on by default, makes collection ignore browser events from cloud and hosting providers' addresses, as bots ([web analytics](web-analytics.md#data-centers)); a project whose visitors use remote desktops in a cloud turns it off. It applies from the next event: the route makes the key cache forget the project.

The General tab's "Keep events" sets how long the project keeps its events: forever (the default), 6 months, 1 year, 2 years, or 5 years ([web analytics](web-analytics.md#how-long-events-are-kept), section 1). Choosing a stricter limit than the current one says, before saving, that older events will be deleted for good within a few hours. The worker deletes them.

### Your server

The "Your server" tab holds the project's secret key, hidden until "Show" and then copyable, with an example of a server-side event, and the switch "Only accept user IDs signed by your server", with an example of signing in Node.js ([web analytics](web-analytics.md#signed-user-ids)). The switch is a field of the tab's form: its Save sends it (`PATCH /api/projects/:id` with `requireSignedUserIds`), and collection uses the new rule from the next event: the route makes the key cache forget the project.

### Spam and bots

The "Spam and bots" tab (`apps/web/src/features/projects/spam-tab.tsx`, after "Your server") holds what keeps spam out of a project's numbers, and deleting what got in ([web analytics](web-analytics.md#spam)).

- **A form**, under [the save rule](design-system.md#the-save-rule), whose Save sends all three (`PATCH /api/projects/:id` with `ignoreDataCenters`, `blockedAddresses`, `blockedReferrers`):
  - "Ignore visits from data centers", moved here from General, with the same `name` (`ignoreDataCenters`).
  - "Blocked addresses": one IPv4 or IPv6 address or CIDR range per line, at most 100. "Add my address" asks the API for the address it sees (`GET /api/client-address`) and adds it, an IPv6 address as its /64, or says it is already listed; it waits for Save like any edit. The hint says who sees the list and that it goes with the project.
  - "Blocked referrers": one domain per line, at most 100, each also blocking its subdomains. A domain that is the project's own site, or a parent of it, is refused ("would block your own site"), as is a public suffix such as `co.uk`.
  - Both lists are checked as the API checks them (`spam-rules.ts`), once a field has been left or a save tried: the field is marked invalid and the error, naming the bad line, replaces its hint. Save sends nothing while one is wrong. Lists compare as the API will store them, so the same entries in another order or form (`203.0.113.7/32` for `203.0.113.7`) are no change.
- **"Delete spam"**, an action outside the save rule: the first and last day (the last week by default, in the instance's timezone), a referrer domain, page path, and country, at least one of them: "Count visits" stays disabled, saying why, until one is set, as the API refuses a delete without a filter. They are checked as typed once counted. When the period ends today, a line says that visits still going on keep the events that arrive after the delete. "Count visits" asks the preview and says what would go, by kind ("12 visits match, with 40 events: 20 pageviews, 3 custom events, 2 errors, and 15 other events (time on page, Web Vitals). 1 session replay goes with them."), or that none match, or that too many do. "Delete visits" stays disabled, saying why, until a count of the filters as they are now exists: changing a filter asks for a new count. It opens a confirmation that names the counts and asks for the number of visits typed; the delete sends that number, and the API deletes nothing when it no longer matches. Afterwards the page says what went, and every query of the project but its settings is fetched again, so reports drop the deleted visits. A delete that stopped partway shows the API's message in the dialog: count again, then delete what is left.

`spam-tab.test.tsx` covers the switch's move, the save rule with Discard, the tab's mark, and the leave guard, the three fields saved together, the checks as typed (the project's own site and a public suffix refused), "Add my address" (once, and an IPv6 /64), Count waiting for a filter, the note on visits still going on, the count, Delete waiting for a current count, the typed confirmation and its request, bad filters, no matches, a failed count, and the tab at 390 and 1440 wide.

### Source maps

The "Source maps" tab (`apps/web/src/features/projects/source-maps-card.tsx`, the routes in [errors](errors.md)) shows what the project has uploaded:

- On an install without an object store, it only says source maps are off there, and that the operator turns them on with `OBJECT_STORE_URL`.
- Otherwise: the instance's use against its limit ("14 MB of 1 GB used", all projects together), then the releases with maps, by their latest upload, newest first or, with "Oldest first", oldest first (the ones to delete for room); at most 100, with a note saying how many there are in all when there are more: release, files, size, and when the last map was uploaded. Each row has a button that lists the release's files with their sizes in a dialog, and a Delete button. Deleting asks first, and says the maps go for good, the errors stay, and that release's stacks show minified code again; afterwards the row goes at once and focus moves to the section's heading (Cancel returns it to the button). Error pages are fetched again.
- Without maps, and behind "Show how to upload" once there are some: the upload command of the CLI (from this repository's `packages/sourcemaps`, which is not on npm yet), a `curl` example for one file, and the rules: one upload per release and minified file, `path` is the file's path as the browser loads it, the release must match `data-release`, and maps built without publishing them (Vite's `build.sourcemap: "hidden"`). The secret key appears only as a placeholder (`sk_…`, `$OTTERTRAIL_SECRET_KEY`) pointing at the "Your server" tab; the tab never prints the real key.

Sizes use powers of 1,024 with the short units KB, MB, and GB. `source-maps.test.tsx` covers the list, oldest first on request, the files dialog, deleting (the request, the list, focus), the install without an object store, and the empty state.

### Session replay

The "Session replay" tab (`apps/web/src/features/projects/replays-card.tsx`; the design in [session replay](session-replay.md), the routes in `apps/api/src/replays/dashboard-routes.ts`) reads `GET /api/projects/:id/replays`:

- On an install without an object store, it only says replays are off there, and that the operator turns them on with `OBJECT_STORE_URL`.
- Otherwise, a form with a radio group (shadcn's Radio Group), "Off" (the default) and "Around errors", each with a line saying what it does. Its Save sends the choice (`PATCH /api/projects/:id` with `replayMode`): while saving the choices are disabled and the Save bar says "Saving…", then "No unsaved changes"; a failure shows the API's message and keeps the choice, still unsaved.
- "On your site": both switches are needed, this setting and `data-replay="errors"` on the tracker's script tag (shown to copy). Before it, always shown, a line in plain words: session replay records what visitors do on the site's pages, and a site that asks visitors first sets that up in its consent banner or consent tool, then turns on "Wait for the visitor's consent". That switch (off by default) is a copy helper, like the privacy options: it is not a field of the form and is never saved, and it changes only the code shown. On, the attribute to copy becomes `data-replay="errors" data-replay-consent="wait"`, and the tab shows the line to call once the visitor agrees (`window.ottertrail.replay(true);`), the stand-in script for calls before the tracker loads, and what `replay(false)` does, with a link to the docs site's consent section (`REPLAY_CONSENT_DOCS_URL`, `https://docs.ottertrail.app/session-replay/turning-it-on/#consent`, built from `DOCS_URL` in `lib/docs.ts`; [waiting for consent](session-replay.md#waiting-for-consent)). It says it is for sites that ask visitors before recording, and makes no claim about what the law requires. Then the privacy defaults in plain words (the page's text, typed values, and images and media are masked in the visitor's browser, and what is masked never reaches Ottertrail) and the site's opt-ins, one line each: `data-replay-text="show"`, `data-replay-media="show"`, `data-ottertrail-mask`, `data-ottertrail-block`, and `data-ottertrail-unmask`.
- "Stored": the project's replays (how many, and their size) and the instance's use against its limit, all projects together; replays are kept 30 days. With at least one replay, "Delete all replays" (`DELETE /api/projects/:id/replays`) asks first and says it cannot be undone and the errors stay; afterwards the count shows none at once, the button goes, and focus moves to the tab's heading (Cancel returns it to the button). Error pages are fetched again.

`replays.test.tsx` covers each state of the tab, the consent switch (the attribute and the calls to copy, nothing else changed, nothing saved), the request a saved choice sends, a failed save, deleting (the confirmation, the request, focus), no delete without replays, and the install without an object store.

### Replacing the key, deleting the project

The Settings page's last tab is a "Danger zone" of changes that cannot be undone, each behind a confirmation:

- **Replace the secret key** (`POST /api/projects/:id/secret-key`), for a secret key that ended up where it should not: servers with the old one are refused at once (a request already looking the key up may still pass), and user IDs signed with it no longer count.
- **Replace the public key** (`POST /api/projects/:id/public-key`), for a key that ended up where it should not. The project gets a new key and keeps its data; pages with the old snippet can no longer send events, so the new snippet has to go on the site right after. The Install tab shows it at once.
- **Delete the project** (`DELETE /api/projects/:id`), with every event it has received: the worker deletes its events from ClickHouse within a minute, and usually from ClickHouse's disk within 6 hours ([clickhouse.md](clickhouse.md#retention-and-deleting-a-project)). The reports cannot be opened from the moment the project is gone. The request repeats the project's name (`{ "confirmName": "Main site" }`), and the dashboard asks for it to be typed, so a mistaken ID or a stray request cannot delete a project. Afterwards the dashboard opens the project list, and the home page stops opening the deleted project.

The collection endpoint keeps keys in a cache for a minute (a key is checked on every event). The project routes tell it to forget a replaced or deleted key, so the key stops working at once in that API process. A batch already on its way when its project is deleted, or a key cached in another API process, is still stored: ClickHouse cannot check that the project exists. The worker's purge deletes those events with the project, or, if they land after it, the orphan sweep does ([clickhouse.md](clickhouse.md#retention-and-deleting-a-project)).

## 8.3 Report endpoints

Code: `apps/api/src/reports/analytics.ts` and `apps/api/src/reports/routes.ts`.

```text
GET /api/projects/:id/analytics?from=2026-11-01&to=2026-11-16[&limit=10]
GET /api/projects/:id/analytics?period=7d[&environment=staging][&limit=10][&country=DE&page=/pricing …]
```

A `period` (`today`, `7d`, `30d`, `90d`, or `12m`) ends today, and the API works out "today" in the instance's timezone: the browser showing the dashboard may be in another one. `7d` is today and the six days before it; `12m` starts the day after the same date last year.

One request returns every report of the analytics page, for whole days in the instance's timezone, `from` and `to` included: the summary, visitors per day, top pages, eleven breakdowns (sources, campaigns, entry and exit pages, countries, regions, cities, devices, browsers, operating systems, releases), and custom events. All of it counts one environment: `environment` names it, in any case, and is `production` when left out. The response says which (`environment`) and lists `environments`: those with events in the range, most events first, then the one shown and `production` even without any, so the page can always switch back. It needs a signed-in user. A range covers at most 366 days, and lists hold at most `limit` rows (default 10, at most 100).

The response also holds `previous`: the summary of the period before (`firstDay`, `lastDay`, and `until`, the cut-off when the period is still running, on `lastDay`), with the same filters (section 7 of [web analytics](web-analytics.md#comparison-with-the-previous-period)). It costs one more summary over the earlier days: on PostgreSQL's benchmark, the whole page went from 56 to 89 ms for 1 day and from 225 to 313 ms for 7 days at 1,000 visits a day.

Filters narrow every report to the matching visits (defined in section 7 of [web analytics](web-analytics.md#filters)): one parameter per filter, named after the breakdown (`source`, `country`, `deviceType` …) or `page`, at most 2,048 characters. An empty value means unknown. Several filters must all match. An unknown parameter is refused with 400: Fastify's validator would otherwise drop it silently, so a mistyped filter (`contry=DE`) would return unfiltered numbers.

### One list in full

```text
GET /api/projects/:id/analytics/list?report=country&period=7d[&search=germ&offset=0&limit=50][&filters …]
```

Behind "Show all": one list of the page (`pages`, `customEvents`, or one of the ten breakdowns), with the same days and filters, 50 rows at a time at most. The answer holds the rows and `hasMore`, which comes from reading one row more than asked for, so no separate count query is needed. The rows are the same as the page's, from the same report functions.

`search` keeps rows whose name contains the text, ignoring case, in the database, so a site with thousands of pages stays quick. `%` and `_` match themselves. Countries are stored as codes and shown as names, so for them the search finds codes whose English name contains the text (`germ` finds `DE`), from the same country names the dashboard shows.

### Visits worked out once

Most reports count visits, and working out visits is the expensive part: it sorts every event in the range (section 7 of [web analytics](web-analytics.md)). Run separately, each report did that again. The endpoint works the visits out once, into a temporary table of a ClickHouse session that belongs to the request, and every report reads that table. The session runs its queries one after another, and the endpoint drops the table when the reports are done (ClickHouse also drops it when the session expires).

On fake data in ClickHouse (`vp run bench:reports`: 200,000 visits in 30 days, the development stack on an Apple M4 Max), before the change described after the table, the whole page:

| Range   | Each report separately | Visits once | Filtered by a country | Filtered by a page |
| ------- | ---------------------- | ----------- | --------------------- | ------------------ |
| 1 day   | 372 ms                 | 263 ms      | 319 ms                | 394 ms             |
| 7 days  | 1,471 ms               | 1,275 ms    | 1,390 ms              | 1,630 ms           |
| 30 days | 4,952 ms               | 3,948 ms    | 3,880 ms              | 4,472 ms           |

The table of visits took most of that: 3.5 of the 3.9 seconds over 30 days. Each of its 12 columns from the visit's first event (source, campaign, browser, location …) was an aggregate of its own. One aggregate for all of them (`firstEventColumns: "together"` in `visits.ts`) made the table 1.3 seconds on the same data. The whole page with that change has not been measured: in later runs, ClickHouse in Podman's 2 GB machine ran out of memory before the end ([clickhouse.md](clickhouse.md#memory)). Reports that work out visits on their own keep one aggregate per column, because ClickHouse then skips the columns they do not read: a sources breakdown took 485 ms that way, 846 ms with one aggregate.

Before ClickHouse, in PostgreSQL, the same benchmark measured the whole page:

| Visits per day | Range   | Each report separately | Visits once |
| -------------- | ------- | ---------------------- | ----------- |
| 1,000          | 1 day   | 168 ms                 | 54 ms       |
| 1,000          | 30 days | 2,393 ms               | 1,039 ms    |
| about 7,000    | 1 day   | 1,151 ms               | 295 ms      |
| about 7,000    | 30 days | 16,710 ms              | 5,254 ms    |

With filters, the temporary table holds only the matching visits, so the reports after it have less to read. At 1,000 visits a day over 30 days, the whole page took 864 ms unfiltered, 539 ms filtered by a country, and 745 ms filtered by a page (which looks up the page's pageviews for each visit).

In PostgreSQL, the page's reports also shared one snapshot (REPEATABLE READ), so their numbers agreed with each other even while new events arrived. ClickHouse has no snapshot across queries: events stored while the page is worked out can reach some cards and not others.

The individual report functions (`summary`, `breakdown`, …) still work on their own, as `vp run report` uses them; a test checks that both ways give the same numbers.

### Not done yet

- Caching. Each request works the reports out again; at the volumes measured above, that takes about a second for a month at 1,000 visits a day.

## 8.4 Analytics page

Code: `apps/web/src/features/analytics/`.

`/projects/<id>/web-analytics?period=30d` shows one project for one period: `today`, `7d` (the default), `30d`, `90d`, or `12m`, as in 8.3. `?from=2026-10-01&to=2026-10-31` shows chosen days instead (a custom range). An unknown period, or days the API would refuse, fall back to the default.

The page is a report ([Report (Console)](design-system.md#report-console)): no cards, hairlines between its parts. From top to bottom, it shows:

1. The filter bar, pinned under the header from 40rem: a picker for the period, with "Custom range…" for chosen days; a picker for the environment, once there is a choice (another environment has events in the range) and always while another than production is shown, so there is a way back; the active filters (or how to add one); then the days covered and the instance's timezone. The days come from the API, so they are the instance's days, not the browser's. The environment goes in the address as `env=staging`, left out for production, and switching it keeps the period and filters.
2. Seven numbers in one strip (`StatStrip`): visitors, visits, pageviews, views per visit, bounce rate, visit duration, and time engaged (defined in section 7 of [web analytics](web-analytics.md#the-numbers)). Under each, its change from the period before: an arrow and a size ("12%", or "6 pts" for the bounce rate), read out as a sentence ("Up 12% from 683"). A change shows only when its counts reach 20 in either period (visitors, visits, and pageviews on their own; the per-visit figures and the bounce rate on visits), and reads "New" when the period before had none ([the change rule](design-system.md#report-console)). The arrows stay in text colors: status colors are reserved for state, and up is not always better (a bounce rate). A note names the days compared and, for a running period, the time of day the comparison stops; it also says that a visitor is recognized for one day only, so the same person on two days counts twice.
3. Visitors, visits, or pageviews per day, as a short, wide line, the metric chosen beside its title. Hovering over the chart shows all three numbers for the nearest day. "Show the numbers" opens the same data as a table. A one-day period draws no line, since one point shows no trend.
4. Breakdowns (`BreakdownTable`), three side by side when the content is 64rem wide and two from 48rem, most visitors first, each with a bar for its visitors; a toggle group in a breakdown's header switches its list (Top pages, Entry, Exit), and on a phone each row stacks, its figures labelled: pages (top, entry, and exit), sources and campaigns, countries, regions, and cities, devices, browsers, and operating systems, releases, and custom events. While no visit names a release, the Releases card says how to name one instead of listing every visit as "Unknown". An empty period in another environment than production names it, and suggests another environment. Each list shows its first 10 rows; when it shows all 10, "Show all" opens it in full. A missing value (no location, an unknown browser) shows as "Unknown", and a visit without a campaign as "No campaign".

A project without events shows how to install the snippet instead; a period without events offers the last 12 months.

### Custom range

"Custom range…" opens a dialog with the first and last day, starting from the days the page shows. A calendar picks them: a click on the first day, then on the last; once a range is complete, the next click starts a new one. It opens on the month the range ends in, weeks start on Monday, and today is underlined. The days can also be typed, day first as the dashboard writes them (`DD/MM/YYYY`): the fields take digits only and add the slashes themselves, and a typed day moves the calendar to its month. A half-typed day is not an error until it is complete or left. The days are checked as the API checks them (real days, the last not before the first, at most 366) before they can be shown.

The calendar is shadcn's `Calendar`, built on react-day-picker, with its parts moved out of its render function (they were made anew on every render). The browser's own date fields came first, but their pop-up calendar ignores the dashboard's look. The slashes come from a small function of ours (`maskDay` in `day-text.ts`) rather than a mask library: the one tried, `@react-input/mask`, refuses a keystroke that arrives before its timer has read the cursor, so digits typed very fast were lost. `maskDay` works within the input event itself, keeps the cursor after the same digits, and is unit-tested; Backspace right after a slash deletes the digit before it, and Delete right before one the digit after it. The dialog's code, the calendar included, loads when "Custom range…" is first chosen: about 23 KB gzipped that every other visit to the dashboard would download for nothing. Chosen days keep the filters, a preset period replaces them, and the project switcher and "Show all" keep them. The comparison with the previous period works for them too: as many days right before.

### Show all

"Show all" opens a list in a dialog, with the page's period and filters: 50 rows at first, then "Load more", and a search by name, sent once typing pauses (a quarter of a second). While a new search loads, the last results stay, dimmed. A row's link filters the page by it and closes the dialog. The search box has the focus when the dialog opens, and Escape closes it.

### Filters

Every row of a list is a link that filters the page to its visits: a source, a country, "Unknown", a page from Top pages, and so on (custom events are not filters yet). Active filters show in the filter bar, each with a button to remove it, and "Clear filters" removes them all. They live in the address (`?country=DE&page=/pricing`), so a filtered view can be linked, reloaded, and left with Back. A new period keeps the filters; switching to another project keeps the period but drops them, since a page or campaign belongs to one project. When nothing matches, the page says so and offers to clear them. Goals follow the breakdowns, full width.

The router reads an address value as JSON only when it is written exactly as JSON writes it, so a hand-written value such as `2024.10` or `1e3` stays as typed, and the page turns the numbers it does read (`2024`) back into text. Links the app builds quote such values (`city=%222024%22`), so they read back the same. The page ignores a value it cannot use (an object, a NUL character, over 2,048 characters) rather than sending it.

### Charts without a chart library

The page needs one single-series line and one kind of bar, so both are drawn directly in SVG and HTML (`day-chart.tsx` and `ranked-list.tsx`) instead of adding a chart library. A library becomes worth adding when reports need more kinds of chart, such as funnels or retention tables.

They follow the chart rules in [the design system](design-system.md#charts): one hue (`chart-1`), no legend for a single series (the card title names it), thin gridlines, and numbers in text colors, never in the series color.

### Keyboard and screen readers

- The chart holds a visually hidden range input with one step per day. Tab moves focus to it; the arrow keys, Home, and End move between days; screen readers read each day with all three numbers, as the hover box shows them.
- The ranked lists are tables with column headers. The bars are hidden from screen readers, because the numbers beside them are text.

### Refreshing

The page loads its data again every minute while it is open. When the period changes, the previous numbers stay on screen, dimmed, until the new ones arrive. If a load fails, the last numbers stay, with the error and a Retry button.

### The stack trace

### An occurrence's replay

The latest occurrences have a Replay column (`apps/web/src/features/errors/occurrence-replay.tsx`), from each occurrence's `replay` in the API's answer:

- **Ready:** a "Play replay" button, named with the occurrence's time for screen readers ("Play replay of the error at 16 Nov 2026, 16:00"). It opens a dialog that takes most of the screen, with the error's time, timezone, and page, around the replay's timeline ([below](#replays)) and a frame of the player page (`/api/projects/:id/replays/:replayId/player?errorAt=<ms>`, titled "Session replay around the error at …", `referrerpolicy="no-referrer"`). The frame has no `sandbox` or `allow` attribute: the player has to run its own script and read the replay as the signed-in user, and the API serves its page with a Content Security Policy of its own ([session replay](session-replay.md#playback)). Closing the dialog returns focus to the button.
- **Pending:** "Arriving…" in muted text; on hover, and for screen readers, "The page sends its replay about 10 seconds after the error."
- **Missing, or none:** a dash, read as "No replay".

The player itself is `packages/replay-player`, plain DOM and TypeScript around rrweb's `Replayer` (`@rrweb/replay`), built into one script (`dist/player.js`) that the API serves at `/replay-player.js`. It fetches the recording, checks its shape (version 1, rrweb events, a viewport size, a full snapshot), and fits the recorded viewport into the frame, keeping its shape. Its controls: Play or Pause (also Space, unless focus is on a control that uses it), a timeline (the arrow keys move 5 seconds; its spoken value reads "0:12 of 1:05") with the error marked on it by a red bar, the elapsed and total time, "Jump to the error" (it carries the same red bar and the error's time, "· 1:30", which names the bar: the bar lets the slider take the pointer, so it shows no hover text), speeds of 1×, 2×, and 4×, and "Skip inactivity" (on by default). It starts a minute before the error at most. A line says what was masked never reached Ottertrail. A replay that is gone says "This replay is unavailable. It may have expired."; other failures say to try again. rrweb builds the recorded page in a frame sandboxed with `allow-same-origin` only, never `allow-scripts` (rrweb 2.2.2's `createSandboxedIframe`; `UNSAFE_replayCanvas` is never set). The package's browser test plays a recording with a `<script>` and `onerror`, `onclick`, and `onload` handlers and checks that none of them runs.

`replays.test.tsx` covers the column's three states and the dialog with its frame and timeline.

It follows the [chart rules](design-system.md#charts) and sits in a `ReportChart` section, so it has its title, a line on what it draws (with the total and the timezone), and "Show the numbers", a table of every bucket that holds anything. It is laid out by the pane's width (it measures its container), not the window's, so it fits the pane at 40% of the screen as well as a phone.

- **Records over time** (Logs): the records per bucket, stacked by severity, as bars from one baseline with 2px of surface between parts and between bars and a rounded top. Severity is a state, so the parts that say something is wrong take the status colors their badges use: Error or worse (error and fatal, `status-critical`) on the baseline, where its height reads exactly, then Warning (`status-warning`). The rest stay neutral: Info in `chart-neutral` (a light gray, `#b0a9b0`), and "Debug, trace, or none" in the de-emphasis gray (`ink-tertiary`). No chart slot is used, so a hue never means a category on one page and a state on another. The dataviz validator, on `surface-1` and `surface-2`: adjacent parts at least ΔE 13.8 apart under color blindness (deutan) and 18.3 to normal vision, every part at least 3:1 ([design system](design-system.md#charts)). The legend names the four parts in the stack's order.
- **Traces over time** (Traces): the traces (root spans, as the list counts them) per bucket, with errors (`status-critical`, on the baseline) and without (`chart-neutral`), as the logs chart draws them; the two are ΔE 8.2 apart under color blindness (deutan) and 15.6 to normal vision. A trace has errors as "With errors only" finds it; when the period held more failed spans than that filter reads (10,000), the line under the title adds "Errors counted among the latest 10,000 failed spans." A toggle beside the title switches to **Duration over time**: one line of the 95th-percentile duration per bucket (`chart-1`, no legend for one line, a gap where no trace ran). Counts and durations have different units, so they never share an axis.
- **Hover and keyboard:** hovering a bar shows its bucket ("Mon 16 Nov 2026, 22:00 to Tue 17 Nov 2026, 00:00"), each part's count, the total, and what a click does. A hidden range input moves between buckets with the arrow keys and reads each out with every part's count.
- **A bar narrows the period:** clicking a bar, or Enter on the range input, sets the custom range (`from` and `to`) to the day the bucket starts on, plus its length in days when a bucket is longer than a day, within the period; the filters stay. The days are counted on the calendar, so a day's bar narrows to exactly that day even when the day is 23 or 25 hours long. The period's days are whole days, so a bucket shorter than a day narrows to its day, which the chart then shows in 15-minute buckets. A period of one day has nothing narrower, so its bars do nothing.
- **States:** a skeleton while it loads; a failure says "The chart could not load", with the API's message and Retry; a period without a record or trace says so in its place. The chart never holds up the list: the list loads, fails, and retries on its own, and a filter's new chart dims the old one while it loads.

### Live

Code: `live-logs.ts` (the polls and what they hold), `LiveLogsView` in `logs-page.tsx`. The "Live" switch in the Logs filter bar (`?live=true` in the address) shows the records arriving now instead of the period's, like `tail -f`.

- **While it is on,** the period picker gives way to a disabled "Live" in its place, and the days shown leave the bar; the environment, service, minimum severity, words, and trace ID still apply, and changing one starts the view again. The chart is hidden: it counts records by when they happened, over whole days, while the live list goes by arrival, and a chart of the last minutes that moved every few seconds would only repeat the list.
- **New records** come in at the top, newest arrival first, one line each as in the list. The page asks the API about every 2 seconds, and never more than once a quarter second, for the records that arrived since its last poll (`GET …/logs/live?after=<cursor>`, [telemetry](telemetry.md#live)). A record the page already holds (a retried record's copy, which arrives again later, or a record the API read again) is dropped, by its ID. A short line says that records appear a few seconds after they are sent, since senders send them in batches, and that Live keeps the newest 1,000 records and stops after 15 minutes.
- **Records left out are marked:** when more than a page (200) arrived between two polls, the API sends the newest and a line in the list says how many it skipped ("50 records skipped, because more arrived at once than Live shows. Turn Live off to search them."), where they would have been. When Live comes back after a stop or a tab hidden longer than the API's window (5 minutes), the API starts from the window and a line says which arrivals the list does not hold ("Records between 12:01 and 12:16 aren't shown, because Live looks back only 5 minutes. Turn Live off to search the period."), in the instance's timezone.
- **The list does not move under the reader:** while the view is paused (Pause, then Resume), scrolled away from its top, or a record of the list is selected, new records wait under a button, "N new records", at the list's top; it puts them at the top and scrolls there. They join by themselves once nothing holds them. A selected record opens beside the list as in the period's view, and stays in the list however many records arrive. A selected record the live list does not hold (an address naming one) holds nothing, and its pane says it is not in the live list and how to find it. Turning Live on or off clears the selection.
- **Guard rails:** it polls only while the tab shows (`visibilitychange`), and starts again at once when it shows. The list keeps at most 1,000 records, the oldest going first; the records waiting under the button are kept apart, at most 1,000 too, and past that the button says "1,000+ new records", so waiting records never push the list out. After 15 minutes it stops by itself and says "Live stopped after 15 minutes", with Resume. A busy API (503: its places for live polls are taken) is asked again at the next poll, without a message. Any other failed poll stops it, with the message and Retry; the records shown stay.
- **It needs nothing of the period's list:** Live does not ask for the period's records. The timezone comes from the live answers, and the service filter offers the services of the records seen, beside those the period's list already gave, so Live runs even when the period's list cannot load.
- **Turning it off** returns to the period's view, with the period, filters, and chart as they were.

The widgets sit in two columns when the content area is at least 64rem wide, whatever the window: the sidebar takes its share. On a phone a wide table scrolls inside its widget, its first column pinned and a fade at the edge where more columns wait; the attention list stacks.

Rules that apply to all of them:

- **Period.** The last 7 days by default, compared with the 7 days before; Today and the last 30 days are the other choices (`?period=` in the address). A period that is still running is compared up to the same moment of the one before, as on the analytics page. The filter bar shows both ranges and the timezone.
- **Small numbers.** Each change rests on its own figure's counts in both periods (for a share such as a conversion, the counts it is taken of). It shows only when the larger of the two reaches the minimum: 10 for errors, 20 for page loads, requests, visitors, and users. A few events make any percentage look large. When the period before had none, a figure that reaches the minimum reads "New" instead of a percentage.
- **No colour for direction.** A change is an arrow and a size. Colour marks only what a rule or a threshold calls bad: a firing alert, a check that is down, a poor Web Vitals rating, a regressed error. Server changes are not judged; alert rules do that.
- **Uptime** reports incidents only. There is no target.
- **Speed** rates a device only from 20 page loads; below that it says "Too few page loads to rate". A device's rating is the worst of its three metrics.
- **Visitors** count a person once for each day they visited, as everywhere in web analytics. The traffic widget says so.
- Bounce rate and visit duration stay on the analytics page.

### Four states

Each widget loads and fails on its own: its data comes from a route of its own, and one that fails shows an error with Retry while the others stay. Each has a skeleton while it loads, and an empty state that says what is missing: nothing set up yet (no errors ever, no traces, no checks or rules, no goals, no signed-in users), with the page that explains how, or nothing in the period.

### Access

A widget is shown only to users with its area, and its route refuses the others (403), so a widget a user may not see is neither fetched nor shown as locked. The layout route needs only the project. A member with none of the overview's areas finds "Nothing on your overview", with buttons to the pages they can open, and the project opens on their first page instead. Inside a widget, the usual rules hold: the newest signed-in users are named only to users with the `users` area, and no widget links to a replay.

### Your own layout

"Edit overview" gives each widget Move up, Move down, and Hide or Show buttons. Each change shows at once, is saved after any save still running (one at a time, in order; an older answer never replaces a newer change), and is read out ("Traffic moved to 6 of 10."), and focus stays on the button pressed. "Reset to default" brings the default order back, and Done leaves edit mode. A hidden widget's data is not fetched.

The layout belongs to one user and one project (`overview_layouts`), so it follows the user to any browser, and goes when the user or the project is deleted. It holds widget IDs in order, and those hidden. A widget the user could not see when saving keeps its place, and a widget added later, or one whose area the user gains later, appears in its default place.

### The main goal

A project setting (`projects.main_goal_id`), chosen on the project's Settings page by those who manage projects. The business figures start with it. It must be one of the project's goals: a foreign key names the goal and the project together, and deleting the goal clears the setting. Without one, the Main goal widget shows new signed-in users: those whose first event, of all the project keeps, fell in the period.

### What the queries cost

The widgets reuse the reports' own queries where they exist: firing alerts and checks (PostgreSQL), the error list, the Speed page's per-device query, the analytics summary and per-day counts, goal counts, and the source breakdown and top pages. Three queries are new and lighter than the pages they summarise:

- **Services:** one read of both periods' server spans, grouped by service only, so a span's attributes are never read (no routes).
- **Signed-in users:** when each user was first seen comes from `user_first_seen`, a row per user ([ClickHouse](clickhouse.md#first-seen-times)), so new users and cohort membership never read the whole history. Activity is read only from the earlier of the period before and the first cohort's Monday, grouped by user, without `FINAL` (a retried event changes neither a user's first event nor the weeks they were active). The Main goal widget's fallback reads the first-seen table alone.
- **Goals:** the visitor count each conversion is divided by, read from the events without working out visits.
- **Errors:** the period's occurrences and its groups, new ones among them, counted in full rather than from the 1,000-group list.

Before the first-seen table, the signed-in users query read all 1.2 million events: 131 ms and 134 ms, and the default overview ran it twice.

Every query runs with the dashboard's ClickHouse limits (15 s and 300 MB a query) and within its shared limit of queries at once (`DASHBOARD_SETTINGS`, `DashboardQueryLimiter`).

## Settings

Code: `apps/api/src/settings/`, `apps/api/src/access/access.ts`, and `apps/web/src/features/settings/`.

Each customer has an instance of their own ([CLAUDE.md](../CLAUDE.md)). The instance holds projects, and the settings that differ between instances live in the instance, not in the deployment's environment.

### The one check

`requireProjectAccess` (`access/access.ts`) runs on every route under `/api/projects/:id`, and each route says what it needs: an area at view or manage, the `projects` permission, or only the project. The request must be signed in, or the answer is 401. The project must exist and be one the user may reach, or the answer is 404, the same for both. Without the area or permission, the answer is 403. A project ID sent by the browser is never enough on its own. Routes outside a project run `requirePermission` from the same file. Roles, areas, and the tests that walk every route are in [access](access.md).

### Instance settings

PostgreSQL's `instance_settings` table has one row:

- `name`: the display name at the top of the sidebar. The setup form sets it (the field "Instance name").
- `time_zone`: an IANA timezone, UTC until the setup page sets the one chosen there.
- `update_location_data`: whether the worker keeps the location database and the data-center ranges current; on by default (see [Location data](#location-data)).

`/settings` is tabs ([settings tabs and the Save bar](design-system.md#settings-tabs-and-the-save-bar)), the chosen one in the address (`?tab=`): **General** (the name and timezone) and **Location data** for the owner, and **Storage** (`?tab=storage`) and **Notification channels** (`?tab=channels`) for the owner and admins. Each tab shows only to users with its permission, so an admin's Settings opens on Storage, and a tab they may not see (`?tab=general`) falls back to it; members do not see the page ([access](access.md)). The tabs are one list, `INSTANCE_TABS` in `features/settings/settings-page.tsx`: adding a tab is one entry there. Links into Settings land on their tab: the Alerts page's "Channels are in Settings" and "Go to Settings", and the rule form's "Add one in Settings", all open `?tab=channels`; storage notifications link to `?tab=storage`. Every tab stays mounted, so each tab's data loads when the page opens, not when its tab is chosen: the Storage tab measures the stores on any visit to `/settings` by the owner or an admin.

General shows the name and timezone (`GET /api/settings`) to the install's owner (`dashboard_users.role = 'owner'`), who alone can change them (`PATCH /api/settings`), as one form under [the save rule](design-system.md#the-save-rule): "Save instance settings" waits for a change, Discard undoes it, the tab shows "Unsaved", and leaving asks first. `instance-settings-tabs.test.tsx` covers the tabs per role, the save rule, the guard, the links, and the fit at 390 and 1440. The timezone field, here and on the setup page, is a combobox (`components/timezone-combobox.tsx`): typing filters the browser's IANA names, plus `UTC`, by any part of the name, ignoring case and treating spaces as underscores ("new york" finds `America/New_York`), and each option shows its current offset from UTC. A name is picked from the list, so it cannot be mistyped; the saved name is listed even when the browser's list leaves it out. The API stores the name Node.js resolves it to (`US/Pacific` becomes `America/Los_Angeles`, and a few newer names come back as older ones: `Europe/Kyiv` as `Europe/Kiev`). It refuses fixed offsets such as `+08:00`, and names PostgreSQL does not know: Node.js and PostgreSQL carry separate timezone databases, and reports and retention use PostgreSQL's to work out where days start. (ClickHouse, which puts events on their days, knows every name Node.js does.)

Reports count days in the instance's timezone, and visitor IDs change at its midnight ([web analytics](web-analytics.md#one-salt-per-timezone-and-day)). Changing it therefore moves where days start in every report, past days included, and counts visitors afresh from the change until midnight; the page says so before saving.

The API and the worker read the settings through one module (`apps/api/src/settings/settings.ts`), which caches them for a few seconds. The process that saved a change uses it at once, and any other process picks it up within seconds.

### Storage

Code: `apps/web/src/features/settings/storage-tab.tsx` and `apps/web/src/lib/storage-api.ts`; the API and the thresholds are in [deployment](deployment.md#storage). The Storage tab of `/settings` (`?tab=storage`), for the owner and admins: an entry of `INSTANCE_TABS` that renders `StorageTab` with the tabs' `InstanceTabProps` (its own query, the instance's timezone, and `onDirty`, so the tab shows "Unsaved" and the leave guard asks while the storage-warnings choice is unsaved). Its first section is "What fills the disk", the second "Storage warnings".

- **Warnings first:** each in an alert with a Warning or Critical badge, its title, and what to do. A warning the worker has on whose figures could not be measured now shows as still on (`held`). "No warnings" shows only when every figure was measured; otherwise a "Not checked" badge names what was not checked (`undetermined`). The budget rows' badge follows the warning's state, so it stays down to 88% like the warning.
- **Channels change elsewhere:** adding, renaming, or deleting a channel in the Notification channels tab reloads the Storage tab, and a chosen channel that was deleted drops out of the choice rather than refuse the save.
- **One row per store:** the disk, ClickHouse (each table's size and retention, and how many projects keep events forever), PostgreSQL (its largest tables), session replays, source maps, and Garage. Each row gives used, limit, left, and its share of the disk; a value that does not exist or could not be measured is `Missing` with what is missing in words ("Not measured", "No limit of its own: the disk", "Off"), never 0. The budgets and the disk have a meter: a native `<meter>` for assistive technology, drawn as a `chart-1` bar on its `seq-1` track, since browsers style `<meter>` each their own way. ## Code splitting

Each page loads in a JavaScript chunk of its own the first time it is opened. The main chunk holds what every page needs: React, the router and its routes' address checks, the session check, the shell (sidebar and header), the project and product layouts, and the shared UI components. Before the split the build was one 1,434 kB file (419 kB gzipped); now a first visit to `/projects` loads about 718 kB (240 kB gzipped), and to a project's Overview about 788 kB (263 kB gzipped). Libraries that only some pages use load with those pages: the resizable panels (`react-resizable-panels`) with the workbench pages, the calendar (`react-day-picker`, `date-fns`) only when "Custom range" is first chosen. The replay player is not in the dashboard's build at all; the API serves it (`/replay-player.js`).

- **How:** `router.tsx` makes each page component with `lazyPage` (`lib/lazy-page.ts`), on TanStack Router's `lazyRouteComponent`. Routes keep their `validateSearch` and `beforeLoad` in the main chunk, so addresses are read and redirects happen before any page downloads. A route whose component passes the address to the page (most of them) wraps it in `withPage`, so the router loads the page's chunk with the route.
- **Preloading:** `defaultPreload: "intent"`. Hovering or focusing a link for 50 ms loads its page's chunk, so a click rarely waits. A preload also runs the target routes' `beforeLoad`, except the session check: the app route skips it for a preload, since Better Auth rate-limits `get-session` (by default 100 requests per 10 seconds per address; `apps/api/src/auth/auth.ts`), and hovering down a long list would reach that.
- **The session check:** `sessionQuery` (`lib/auth-client.ts`), in the router's query cache. A "signed in" answer is kept 30 seconds, so moving between pages rarely asks; "signed out" is asked again each time, so signing in is seen at once. Signing out, and any 401 from the API, clear the cache. Only no session or a 401 sends the visitor to sign-in; any other failure (a 429, a 5xx, the API unreachable) shows "Something went wrong" with Reload instead of signing them out. On the sign-in page a failed check just shows the form. While the check runs, nothing is shown: the shell or sign-in follows.
- **While a chunk downloads:** after `pendingMs` (TanStack's default, 1 s) the page's place shows a skeleton (`PagePending` in `components/route-states.tsx`), inside the shell, for at least `pendingMinMs` (0.5 s), so a quick load never flashes one. Pages before signing in show their panel's shape instead (`AuthPending`).
- **When a chunk fails:** a tab left open across a deploy asks for files the new version no longer has. When the import failed because its file could not be downloaded (the browsers' messages for that, or Vite's for a stylesheet), `lazyPage` turns it into a `PageLoadError`, and the route shows "This page could not load", with the browser's reason and a Reload button, inside the shell, so the other pages stay a click away (`RouteError`, the router's `defaultErrorComponent`). A module that throws while it runs is a bug, not a deploy, and shows as any other error. The custom range dialog, loaded the same way, shows "The calendar could not load" with Reload in its place, and the page stays. Browsers remember a failed module, so trying again in place cannot work; reloading fetches the current version. The error has its own message so TanStack Router does not reload the page by itself: the reader decides. Any other error a page throws shows "Something went wrong" with its message and the same Reload button.
- **The budget:** the build fails when the JavaScript a first visit loads before any page (the entry chunk and every chunk it imports statically, each gzipped on its own) grows past `INITIAL_JS_BUDGET` in `apps/web/vite.config.ts`, set with a margin over the size when pages were split out; the failure gives the current size. The check is `scripts/chunk-budget.ts`, so `vp run ready` runs it with the build. When it fails, load what grew lazily inside the page that needs it, or raise the budget with the reason. The largest chunk is the entry, 476 kB (148 kB gzipped), of which React DOM is 204 kB; Vite's 500 kB warning no longer shows.
- **Licences:** `THIRD_PARTY_LICENSES.txt` lists the packages of every module in the build, whichever chunk holds it, so the split changed nothing there (38 packages before and after).
- **Tests:** `lazy-routes.test.tsx` replaces modules: a page that waits, to check the hover preload, the skeleton in the shell, and then the page; a page and the custom range dialog that fail to download, and a page that throws while it runs, to check each message and that Reload reloads (`lib/reload.ts`, replaced in the test). `session-check.test.tsx` covers hovering and a navigation without asking for the session again, a 429 that shows the error, a 401 that sends to sign-in, and the sign-in page when the check fails. `apps/web/tests/chunk-budget.test.ts` covers which chunks count and the budget's limits.
