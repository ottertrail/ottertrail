## 1. The event

### Facts, not totals

Ottertrail stores one row per thing that happened (an event) and computes every number from those rows when a report asks. Nothing stores a running total such as "pageviews today".

This makes definitions changeable. If the session timeout changes from 30 to 20 minutes, reports recompute from the same rows. It also makes cleanup possible: fake or bad events can be deleted, and every report stays correct.

### The events table

ClickHouse's `events` table holds them (`apps/api/src/clickhouse/migrations.ts`; [clickhouse.md](clickhouse.md)). Until 18 November 2026 they arrived in PostgreSQL first, in a table with the same columns; that table is gone, and so are the migrations that made it, squashed since into one.

| Column              | Meaning                                                                     | Set by |
| ------------------- | --------------------------------------------------------------------------- | ------ |
| `project_id`        | The project (website or app) the event belongs to                           | Server |
| `event_id`          | Random ID generated by the sender                                           | Sender |
| `name`              | `pageview`, or a custom name such as `signup`                               | Sender |
| `occurred_at`       | When it happened, by the sender's clock. Reports use this.                  | Sender |
| `received_at`       | When the API received it, by the server's clock                             | Server |
| `path`              | Page path without the query string, such as `/lessons/closures`             | Sender |
| `referrer`          | The page that linked here, if the browser reports one                       | Sender |
| `utm_*` (5 columns) | Campaign tags from the page URL: source, medium, campaign, term, content    | Sender |
| `properties`        | Custom details as a JSON object, such as `{ "plan": "free" }`, at most 8 KB | Sender |

Later steps added columns: browser, OS, device, country, region, and city (step 4), visitor (step 5), and session (step 6). Then came `environment` and `release` ([Environments and releases](#environments-and-releases)), `user_id` ([Known users](#known-users)), and five `error_*` columns that only an `error` event has ([errors](errors.md#2-storage)).

### Two timestamps

- `occurred_at` is event time: when the visitor did something, in their browser. Reports group by it ("pageviews on Monday").
- `received_at` is arrival time: when Ottertrail's API received the batch, by the server's clock.

They are usually milliseconds to seconds apart, but not always. A phone on a train records a pageview at 09:58 and sends it at 10:20 when it is back online: reports must count it at 09:58. The gap is also useful on its own:

- Late data: a report for yesterday, computed at midnight, misses events that arrive afterwards. Rows with `received_at` after midnight and `occurred_at` before it are exactly those events, so the day can be recomputed.
- Monitoring: `received_at - occurred_at` is the delivery delay. If it grows, trackers are stuck retrying or the server is slow.

Why not `created_at`? It would mean `received_at`, but in an events table it is ambiguous: the event is created in the browser and the row in the database, on two different clocks. Naming both prevents a report from grouping by the wrong one. Tables with a single moment, such as `projects`, keep `created_at`.

The sender's clock can also simply be wrong. Step 2 corrects for that ([Clock correction](#clock-correction)).

### Event IDs make retries harmless

Networks lose replies. A sender can deliver an event, never hear back, and send it again. The table keeps one row per project, day, and event ID (a `ReplacingMergeTree` ordered by `(project_id, toDate(occurred_at), event_id)`), and reports read it with `FINAL`, so:

- a retried event counts once, though [clock correction](#clock-correction) gives it a slightly different time, unless the two fall either side of midnight UTC ([ClickHouse](clickhouse.md#each-event-once));
- the same event twice in one batch counts once;
- the same ID in two different projects is two different events.

Delivery is "at least once"; storing is idempotent (doing it twice changes nothing), so each event counts once. Nothing is looked up before the insert, so the API cannot tell a retry from a new event: it answers both alike ([clickhouse.md](clickhouse.md#each-event-once)).

A batch is one insert, so it is saved completely or not at all. A batch with one invalid event saves nothing.

### Columns plus a flexible part

Fields every event has get their own typed columns, because reports filter and group by them constantly. Custom details go in one column as JSON text, limited to a JSON object of at most 8 KB.

### Limits

Step 2 validates every request before it is stored: text lengths (event name 200 characters, path and referrer 2,048, each UTM value 200) and the properties size. ClickHouse has no check constraints, so those checks are the only ones. PostgreSQL's table had them as a last line of defense while events landed there.

### Ordered for the questions

Almost every report asks "this project, between these two times", so the table is ordered by project, then day (`(project_id, toDate(occurred_at), event_id)`): a report reads the project's days in its range. Add other indexes only when a real query needs one.

### How long events are kept

Each project keeps its events forever unless its owner chooses a limit (`retention_days`: 6 months, 1 year, 2 years, or 5 years in the dashboard; any number from 30 to 3,650 days through the API). Nothing is deleted until then: how long to keep data is the customer's decision.

The worker (`apps/api/src/worker.ts`, a process of its own beside the API) deletes events older than the limit from ClickHouse at start and every 6 hours (`retention/retention.ts`; [clickhouse.md](clickhouse.md#retention-and-deleting-a-project)). The cut-off is a midnight in the instance's timezone, the limit's number of days before today there, so a report never shows a day with only some of its events. One statement deletes the expired events of a thousand projects, and the rows usually leave the disk in the same run ([clickhouse.md](clickhouse.md#retention-and-deleting-a-project)). Running the job twice, or in two workers at once, is harmless.

### Not done yet

- Deleted events stay in backups until those are deleted; there is no backup policy yet ([deployment](deployment.md#backups)).

## 2. Collecting

`POST /api/events` receives events from browsers (the tracker, step 3) and servers. Code: `apps/api/src/collection/`.

### The request

```json
{
  "v": 1,
  "key": "pk_00000000000000000000000000000000",
  "sentAt": 1794823396705,
  "events": [
    {
      "id": "0b9c6a4e-5d1f-4b8a-9a43-2f7d1c3e8b10",
      "name": "pageview",
      "occurredAt": 1794823394705,
      "url": "https://example.com/pricing?utm_source=newsletter",
      "referrer": "https://news.ycombinator.com/item?id=1",
      "properties": { "plan": "free" }
    }
  ]
}
```

- `v` is the version of this format, so it can change later without breaking old trackers.
- `key` is the project's public key (the zeros above are a placeholder; find a project's key in the `projects` table).
- Times are milliseconds since 1970 by the sender's clock.
- `touch` (optional, only ever `true`) says the device has a touchscreen; the tracker sends it when `navigator.maxTouchPoints` is over 1. It tells an iPad from a Mac (see [Enrichment](#4-enrichment)).
- `environment` and `release` (optional) say where the site runs and which version of it, for every event of the batch ([below](#environments-and-releases)).
- `userId` (optional, per event) is the site's own ID for the signed-in user who caused the event ([below](#known-users)).
- Send it as `text/plain` from browsers (see [Cross-site requests](#cross-site-requests)); `application/json` also works. Both are parsed by Fastify's secure JSON parser, which refuses a body with a `__proto__` or `constructor` key anywhere in it (400).
- Unknown fields are removed, not rejected, so a server accepts batches from a newer tracker.

### Environments and releases

A team runs the same app in several places: the live site, a staging site, a developer's machine. Each event says which (`environment`), and which version of the app sent it (`release`). Code: `apps/api/src/collection/environment.ts`.

- **Environment:** 1 to 64 letters, digits, `.`, `_`, or `-`, starting with a letter or digit, such as `production`, `staging`, or `pr-142`. Stored in lower case, so `Staging` and `staging` are one. Without one, events are `production`: every site that names none is the live one, as every event stored before environments existed was.
- **Release:** 1 to 200 characters without spaces or control characters, as the team names its versions: `1.4.2`, `web@2026.11.17+3f2a9c1`, a commit hash. Stored as sent.
- Both belong to the batch, not to each event: one page runs in one environment and one release.

Reports show one environment at a time, production unless another is chosen ([section 7](#one-environment-at-a-time)), so a test site never mixes into the live numbers. A release is a property of a visit, like its browser, with a breakdown and a filter. Errors (stage 2) will use releases to tell which version introduced a problem.

### Known users

Visitors are anonymous: a daily visitor ID, nothing more ([section 5](#5-visitors)). A site can say which of its users is signed in, and every event from then on carries that user's ID (`userId`). The ID is the site's own, such as the user's ID in its database. The docs and the dashboard ask for that rather than an email address: an ID means nothing outside the site. Code: `apps/api/src/collection/identity.ts`, `apps/api/src/identities/`.

- **The rule:** 1 to 200 characters, no control characters or unpaired surrogates. Stored as sent; the tracker trims it first.
- **Nothing on the device:** the tracker keeps the ID in memory, so the site names the user on every page load (`data-user-id` on the script tag, [section 3](#3-the-tracker)), and in a single-page app also when someone signs in or out without a page load (`identify()`, `reset()`). Ottertrail stays cookieless.
- **A user's activity is the events with the user's ID, and only those.** Anonymous events before a sign-in, even in the same visit, are not counted as the user's: on a shared computer they may be someone else's. Different user IDs are never merged.
- **One environment at a time,** as reports: a user on the staging site is another list.
- **Why the ID crosses days and visitor IDs don't:** a daily visitor ID exists so that nobody, Ottertrail included, can follow an anonymous visitor from day to day. A signed-in user has told the site who they are, and the site chose to tell Ottertrail; its privacy notice should say so. A user ID is personal data, if pseudonymous, and is deleted with the project or past its retention.

User IDs are also masked in the API's request logs (`/users/…`, `search=…`): logs are not covered by a project's retention or deletion.

### Signed user IDs

The public key sits in every page, so anyone can copy it and send events that claim to be any user. A project can therefore require its user IDs to be signed by the site's own server (`require_signed_user_ids`, the switch "Only accept user IDs signed by your server" in its settings). The signature is HMAC-SHA256 of the user ID, in UTF-8, keyed with the project's secret key, in hex (either case). The site's server makes it for the signed-in user and puts it in the page beside the ID (`data-user-signature`, or the second argument of `identify()`). Ottertrail makes it again and compares, in constant time (`apps/api/src/collection/identity.ts`). Without the secret key, nobody can make the signature for another user's ID.

```text
Node.js   createHmac("sha256", secretKey).update(userId).digest("hex")      (node:crypto)
Python    hmac.new(secret_key.encode(), user_id.encode(), hashlib.sha256).hexdigest()
PHP       hash_hmac('sha256', $userId, $secretKey)
Ruby      OpenSSL::HMAC.hexdigest('SHA256', secret_key, user_id)
Go        mac := hmac.New(sha256.New, []byte(secretKey)); mac.Write([]byte(userID)); hex.EncodeToString(mac.Sum(nil))
```

When signing is required, a user ID without a valid signature is left out and the event kept, anonymous. The response does not say so, as it says nothing about any filter ([The responses](#the-responses)): check that the user's events show in Users. Refusing the batch would lose the visitor's pageviews over a site's mistake. A signature that is not 64 hex digits is refused as malformed (400); the tracker leaves it out, with a warning, rather than send it. When signing is not required, user IDs are taken as sent.

Decided on 23 November 2026: signing is off by default, and stays optional. A site without a server it can change still gets known users. While it is off, anyone with the public key can send events as any user, so a user's timeline and an error's "users affected" can hold made-up events. The Users list and a user's page say so in one line, "User IDs on this project aren't verified, so anyone with the project's public key could send any ID.", with a "Require signed IDs" link to the Your server tab for the owner and admins ([dashboard](dashboard.md#85-users)).

**Known limit:** the line follows the current setting, not the stored events. Once signing is on it goes, though IDs that arrived unsigned before stay in the lists and counts until their events pass the project's retention.

A page shows its own user's signature, so whoever sees that page can send events as that user: as themselves. They still cannot sign any other ID.

### Server-side events

Some events are better sent by the site's own server than by a browser: a payment, a cancelled subscription. A browser can neither block nor fake them, and they can carry what a page should not see. Code: `apps/api/src/collection/server-events.ts`.

```text
POST /api/server-events
Authorization: Bearer sk_…
Content-Type: application/json

{ "v": 1, "environment": "production", "release": "api@2.3.0",
  "events": [{ "id": "<UUID>", "name": "subscription_started", "occurredAt": 1794823396705,
               "userId": "42", "path": "/checkout", "properties": { "plan": "team" } }] }
```

- **The secret key** (`sk_` and 32 hex characters) is the project's own, shown to dashboard users in the project settings, and replaceable there. It must stay on the server: the endpoint sends no CORS headers, so a page cannot even read its answers. It is stored as it is, not as a hash, because checking a signature means making it again; anyone who can read the database can write events directly anyway.
- **Checked before the body is read:** a missing or malformed key gets 401, then requests per client address are limited (bursts of 600, then 50 a second) only to bound made-up keys, each of which costs a lookup, then the key is looked up (cached, as public keys are): a key no project has gets 401 before its body is read.
- **Every event belongs to a user** (`userId`, required, the same rule as in browsers) and to no visitor: it shows in the user's activity (Users), not in web analytics, which counts what browsers send. `path` is optional; the user's page shows an event without one by its name only. `pageview` and `engagement` are the tracker's and are refused.
- **The server's clock is trusted:** `occurredAt` more than 5 minutes ahead is refused (400), more than 24 hours old is counted as too old, as for browsers. No location, browser, or device is recorded: the request comes from the site's server, not the user's.
- **The rest is as for browsers:** at most 50 events, 64 KB, the same name and property limits, the project's event budget (shared with its browsers), a retried event counted once, as long as the retry sends the same `id` and the same `occurredAt` (a sender that stamps the time again on each attempt stores its retries twice), 202 only after ClickHouse has written the events. The answers are those in the table below, with 401 (`unauthorized`, `unknown_key`) for a missing, malformed, or unknown key in place of 403, and a 202 body of `{ "stored", "tooOld" }`: the events written, a retry's included, and those more than a day old. Retry only on 429 and 503. None of the [spam checks](#spam) applies: not the per-client event limit, the daily cap per visitor, blocked addresses, or referrer spam.

### The responses

| Status | Body `error`                                                | Meaning                                                                                                                                                                                                                                                        | Should the sender retry? |
| ------ | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| 202    | none: `{ "received" }`                                      | Accepted: the batch's events were written to ClickHouse, or filtered ([Spam](#spam)). `received` is the batch's number of events, whatever became of them                                                                                                      | No                       |
| 400    | `invalid_request`                                           | The batch breaks a rule below                                                                                                                                                                                                                                  | No: it will fail again   |
| 403    | `unknown_key`, `origin_not_allowed`, `hostname_not_allowed` | Wrong key, or a site the project does not allow                                                                                                                                                                                                                | No                       |
| 413    | `payload_too_large`                                         | Body over 64 KB                                                                                                                                                                                                                                                | No: send smaller batches |
| 415    | `unsupported_media_type`                                    | Not `text/plain` or `application/json`                                                                                                                                                                                                                         | No                       |
| 429    | `rate_limited`                                              | Too many requests or events, or too many of the project's requests in progress                                                                                                                                                                                 | Yes, after `Retry-After` |
| 503    | `storage_unavailable`, `busy`                               | The key could not be looked up, or ClickHouse could not write, or the API has too many requests in progress. Usually nothing was stored, but after ClickHouse's 10 seconds it may still write the batch; a retry is the same rows, which ClickHouse keeps once | Yes, after `Retry-After` |

Ottertrail answers 202 only after ClickHouse has written the events ([clickhouse.md](clickhouse.md#how-events-get-there)). A batch is saved completely or not at all: if one event breaks a rule, nothing from the batch is stored.

### Checks, in order

The endpoint is public, so anyone can send it anything. Checks run cheapest first, so floods and garbage are turned away before they cost a database query:

1. Requests per client IP address, before the body is even read.
2. Body size, content type, and the JSON schema (Fastify validates before the handler runs).
3. Events per client address ([Rate limits](#rate-limits)), as soon as the batch's size is known, before the key costs a lookup.
4. Project key, from an in-memory cache (`collection/project-keys.ts`): up to 1,000 projects' keys, each for a minute, the least recently used dropped first. Keys no project has are cached apart, up to 256 of them for 10 seconds, so repeating a made-up key costs one query every 10 seconds, not one per request, and a stream of made-up keys cannot push real projects out of the cache. Requests that miss the cache for the same key at once share one query. A stream of different made-up keys still costs a query each; steps 1 and 3 bound it.
5. The `Origin` header against the project's allowed hostnames, and the release's text.
6. Accepted and not stored, answered 202 as a stored batch is: the project's [blocked addresses](#blocked-addresses), then bots and [data centers](#data-centers), then [referrer spam](#referrer-spam). These cost nothing more than the cache, and come before the budget, so they cannot use it up.
7. Each event's rules and page hostname, URL cleanup, and clock correction. A batch refused here spends no budget.
8. Event budget per project and instance.
9. Visitor IDs, then the [daily cap per visitor](#a-daily-cap-per-visitor). It needs the visitor ID, so it comes after the budget; capped events get their budget back.
10. One insert into ClickHouse for the whole batch.

Requests in progress are capped too (`collection/busy.ts`, `collection/in-flight.ts`), so requests cannot pile up in memory while ClickHouse is slow. Once a batch's body has arrived and passed its schema, it takes one of 256 slots per API process, browser and server-side events together (503 `busy`, `Retry-After: 1`, when none is free), and once its project is known, one of that project's 64 (429). A sender still sending its body holds none. A slot is held until the insert settles, even if the client hangs up. ClickHouse gets 10 seconds to write a batch (`wait_for_async_insert_timeout`, in place of its 120); past them the answer is 503 and the tracker sends the batch again, which ClickHouse keeps once.

Replay uploads (`POST /api/replays`, [session replay](session-replay.md)) run steps 1, 2, 4, 5, then blocked addresses with bots and data centers (202, `{ "received": 1 }`, the same answer as a chunk stored or a retry of one, so a sender never learns a filter caught it), then their own budgets in bytes. The event checks of steps 3 and 9 and referrer spam do not apply to them: a chunk carries no events or referrer. Heatmap batches (`POST /api/heatmaps`, [Heatmaps](#heatmaps)) run steps 1 to 6 in the same order, with records in place of events and the project's heatmaps setting after step 5, then their own budgets; they have no visitor ID, so no daily cap. Server-side events and OTLP telemetry run none of the spam checks.

From step 5 on, the project is known, and what becomes of each request is counted in memory, without a query, for the project's Activity tab: accepted, filtered (a bot, spam, too old), or refused, and why ([dashboard](dashboard.md#activity)). A request turned away in steps 1 to 4 is not counted, since nothing yet names its project.

### Keys and allowed hostnames

Each project has a `public_key` (`pk_` plus 32 hex characters). It sits in every page's HTML, so it is not a secret: it only identifies the project and only allows sending events.

Each project also lists `allowed_hostnames`, such as `example.com` and `www.example.com`. Matching is exact: `example.com` does not allow `www.example.com`. An empty list accepts nothing, so a new project collects nothing until its sites are listed.

Two hostname checks run:

- Every event's page URL must be on an allowed hostname.
- If the request has an `Origin` header, its hostname must be allowed too. Browsers always send `Origin` on cross-site requests, and a page cannot change it. Scripts and servers can leave it out or fake it, so this stops misuse from other websites but is not authentication.

There is no dashboard for projects yet. Set them in SQL, for example: `update projects set allowed_hostnames = '{localhost}' where name = 'Playground';`

### Cross-site requests

The tracker runs on the customer's site (`example.com`) but sends to the Ottertrail instance (another domain). Browsers restrict such cross-site requests (CORS):

- A request with a JSON content type first triggers an `OPTIONS` "preflight" request that asks the server for permission. A `text/plain` POST is a "simple request" and is sent directly, so the tracker sends JSON as `text/plain`. The endpoint does not answer preflight requests.
- The browser still sends a simple request, but hides the response from the page unless the server allows it. Every response from this endpoint, including 403, 429, and 503, returns `Access-Control-Allow-Origin` for the request's origin, so the tracker can read the status and decide whether retrying can help. Without it, a rejected tracker would see only a network failure and retry a request that can never succeed. This is safe because the endpoint uses no cookies or credentials and its responses hold nothing private; the origin check still decides what is stored.
- Even then, a page sees only a few headers of a cross-site response. `Retry-After` is not one of them, so every response also sends `Access-Control-Expose-Headers: Retry-After`. Without it, the tracker could not read how long the server asked it to wait.

### Rules for a batch

| Rule             | Limit                                                                                                                                                                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Body             | 64 KB, uncompressed (`Content-Encoding` is not supported)                                                                                                                                                                                                        |
| Events per batch | 1 to 50                                                                                                                                                                                                                                                          |
| Event ID         | A UUID                                                                                                                                                                                                                                                           |
| Event name       | 1 to 200 characters, no control characters or unpaired surrogates                                                                                                                                                                                                |
| Page URL         | Valid `http` or `https` URL, at most 8,192 characters, path at most 2,048                                                                                                                                                                                        |
| Properties       | Flat object: at most 30 keys of up to 100 characters; values are strings (up to 500 characters), numbers, booleans, or null; at most 8 KB in total. Keys and string values must not contain NUL characters or unpaired surrogates, which PostgreSQL cannot store |
| Environment      | Optional: 1 to 64 letters, digits, `.`, `_`, or `-`, starting with a letter or digit                                                                                                                                                                             |
| Release          | Optional: 1 to 200 characters, no spaces, control characters, or unpaired surrogates                                                                                                                                                                             |

### URL cleanup

Query strings can hold secrets (`/reset?token=…`, session IDs). The endpoint keeps only the path and the five UTM tags (`utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`) and drops the rest of the query string and the fragment. UTM values are trimmed and cut to 200 characters, without splitting a character such as an emoji in half. A tag that decodes to a NUL character (`%00`) is dropped, like a bad referrer.

Referrers lose their query string and fragment too: `https://news.ycombinator.com/item?id=1` is stored as `https://news.ycombinator.com/item`. App referrers keep their scheme and host (`android-app://com.google.android.gm`). A referrer that cannot be parsed is dropped, not rejected: a bad referrer is not a reason to lose the event.

### Clock correction

The sender's clock can be wrong by minutes or days. The batch carries two times from that clock: when each event happened (`occurredAt`) and when the batch was sent (`sentAt`). The server trusts only the difference between the two: the event happened `sentAt - occurredAt` before the batch arrived.

```
occurred_at = (time the server received the batch) - (sentAt - occurredAt)
```

A phone whose clock is two hours slow still gets the right times. An `occurredAt` after `sentAt` is impossible and is treated as `sentAt`. Events that happened more than 24 hours before sending are not stored and are counted as too old in the Activity tab (`correctClock` in `apps/api/src/collection/normalize.ts`); the answer does not say so.

The time the request spent on the way is not seen, so an event is placed that much later than it happened, usually a fraction of a second. The tracker reads `sentAt` again for each attempt, so a retry's time comes out later by however much longer it spent on the way. The table matches events by day, not exact time, so the retry is still the same row ([Event IDs make retries harmless](#event-ids-make-retries-harmless)).

### Rate limits

Every limit uses a token bucket: each key has a bucket of tokens that refills at a steady rate. A request (or each event in it) spends tokens; a full bucket allows a short burst, and the refill rate is the sustained limit. An empty bucket answers 429 with `Retry-After`, the seconds until enough tokens return.

| Limit                      | Burst        | Sustained                                        | Checked                 |
| -------------------------- | ------------ | ------------------------------------------------ | ----------------------- |
| Per client address         | 120 requests | 2 requests/second                                | Before the body is read |
| Events per client address  | 200 events   | 20 events/second                                 | Before the key lookup   |
| Per project                | 2,000 events | 200 events/second                                | After the key is known  |
| Per instance, all projects | 6,000 events | 600 events/second (`INSTANCE_EVENTS_PER_SECOND`) | With the project's      |

A batch spends from its project's bucket and the instance's, or from neither: the first keeps one project from crowding out the others, and the second keeps the instance's total bounded however many projects it has (`EventBudget` in `rate-limiter.ts`). Server-side events spend from the same buckets, so a flood of browser events with a project's public key, which anyone can copy, can hold its servers' events back too (429, to retry). An instance that needs more may raise its limit. A refusal's `Retry-After` waits for both buckets. The buckets live in the API process's memory: each process enforces its own limits, and a restart resets them. Ottertrail runs one API process per instance for now.

The request limit lets one client send 50 events in each of its requests, 100 a second; the events limit counts the events themselves (`DEFAULT_IP_EVENT_LIMIT` in `collection/routes.ts`). Both limits, and every other limit per address (server-side events, heatmaps), key on `clientKey` (`ClientRateLimiter` in `rate-limiter.ts`): an IPv4 address as it is, and an IPv6 address by its /64, the block one household or office usually holds, so a client cannot dodge them by rotating through its addresses. A person sends a handful of events a minute; 20 a second sustained, after a burst of 200, leaves room for dozens of people behind one address.

That is also its cost: everyone behind one address shares one bucket. An office, a school, or a mobile carrier's shared address (carrier-grade NAT, where thousands of phones leave through a few addresses) can reach it on a busy site, and then their events wait and are retried (429, `Retry-After`): the tracker keeps up to 200 events and tries again, so a short peak loses nothing, but a long one can. A site whose visitors mostly arrive through one address would need a higher limit; it is a constant for now, not a setting.

Behind a proxy (Cloudflare, Caddy), every request seems to come from the proxy's address. Set `TRUST_PROXY` (see [development](development.md#configuration)) so the API reads the client's address from `X-Forwarded-For`. Leave it unset without a proxy: otherwise any client could claim any address. Set the number of hops to exactly the number of proxies in front of the API that set or append `X-Forwarded-For`: a number too high is as unsafe as setting it with no proxy in front, because entries the client wrote then count. The Docker deployment sets `1`, for Caddy, which replaces the header.

### Spam

Anyone can copy a page's public key and send events, so some arrive that no person caused: runaway trackers, scripts, and referrer spam (visits that only exist to put a site's name in a report's referrers). Five things keep them out or take them away again. Those that turn events away at collection answer 202, with the same body as a stored batch, so a sender never learns it was caught and has no reason to retry. The project's [Activity tab](dashboard.md#activity) counts what each caught. The limit on events per client address is the exception: it answers 429 with `Retry-After`, as the other rate limits do, and the tracker sends the events again then. None of them stores anything about the sender. Code: `apps/api/src/collection/`, `apps/api/src/projects/blocked-addresses.ts` and `blocked-referrers.ts`, `apps/api/src/enrichment/referrer-spam.ts`, `apps/api/src/spam/`.

#### Events per client address

The per-client event limit above: a script that sends full batches as fast as it can is held at 20 events a second, however many visitor IDs it makes up.

#### A daily cap per visitor

After a visitor ID has sent 5,000 events in its day, its further events are answered 202 and not stored, and counted as spam in the Activity tab (`VISITOR_DAILY_EVENT_CAP` in `collection/visitor-cap.ts`, the one constant). A person reading a site sends a few dozen to a few hundred events a day; 5,000 is reached only by a page stuck in a loop or a script.

- The counts are kept in the API process's memory, keyed by project, the visitor's day (in the instance's timezone, the day its visitor ID belongs to), and visitor ID. Nothing is stored, and nothing is looked up before an insert.
- Memory is bounded: 100,000 visitors at most (`VISITOR_CAP_MAX_KEYS`), about 15 MB. Past that, the visitor counted least recently is forgotten, and starts again from zero if it sends again: it may store another 5,000 that day. A restart forgets every count too, and each API process counts its own.
- A retried event counts again toward the cap. A batch ClickHouse could not write gives its counts back.
- Server-side events have no visitor and are not capped.

What it stops: runaway trackers and naive scripts that keep one browser and address. What it does not stop: a sender that changes its User-Agent on every request gets a new visitor ID each time, since the ID hashes the User-Agent ([section 5](#5-visitors)). The per-client event limit and blocked addresses handle that case.

#### Blocked addresses

A project can ignore the browser events of up to 100 IPv4 and IPv6 addresses and CIDR ranges, such as its own office's (`projects.blocked_addresses`; "Blocked addresses" on the [Spam and bots](dashboard.md#spam-and-bots) tab). Their events are answered 202 and not stored, before the project's event budget, so they do not use it up. Their replay uploads are accepted and dropped the same way. Server-side events are never blocked: they come from the site's own server.

- **The rules**, checked by the API on save (and by the dashboard as it is typed): an address or a range (`203.0.113.0/24`, `2001:db8::/48`), at most a /8 of IPv4 or a /16 of IPv6, since a wider range blocks a large part of the internet by one mistyped prefix, and silently. No zones (`fe80::1%eth0`) and no `start-end` ranges. A bad entry is refused (400 `invalid_address`) and named.
- **Normal forms:** an IPv4-mapped IPv6 address (`::ffff:203.0.113.7`) is stored as its IPv4 address, as `clientKey` counts it; a range as its network address (`10.1.2.3/8` is `10.0.0.0/8`); a range of one address as the address; IPv6 in its shortest form, lower case. Repeats are dropped, and the 100 counts after that.
- **Matching** uses Node's `net.BlockList`, built once when the collection endpoint loads the project into its key cache, never per request. A client address that is IPv4-mapped (as a dual-stack server sees IPv4 clients) is checked as IPv4.
- **When a change applies:** saving the list makes the API process forget the project's cache entry, so the next request uses the new list. A second API process would keep its cached list for up to the cache's 60 seconds.
- **"Add my address"** asks `GET /api/client-address`, which answers the address the API sees the request come from (`TRUST_PROXY` applies), and for IPv6 its /64; the dashboard adds the IPv4 address, or the IPv6 /64, since the same browser may use another address of its /64 tomorrow. The route needs the `projects` permission and the address is not logged.

#### Referrer spam

A browser batch with an event whose referrer's hostname is a listed domain, or a subdomain of one, is answered 202 and not stored, before the budget. `semalt.com` catches `www.semalt.com` but not `notsemalt.com` or `semalt.com.example.org`. The whole batch goes: its other events (time on the page, its Web Vitals) belong to the same spam visit. A referrer on one of the project's own allowed hostnames is never spam, whatever a list holds: the tracker sends the previous page as each later page's referrer, so a site whose own domain is listed would otherwise lose every page after its visitors' first. Three sources, combined:

1. **Matomo's community list** (`spammers.txt` of [matomo-org/referrer-spam-list](https://github.com/matomo-org/referrer-spam-list)), in the public domain (its README; CC0-1.0 in its `composer.json`). A copy ships in the repository, pinned to a commit (`apps/api/src/enrichment/referrer-spam/list.ts`; 2,355 domains at commit `6cd0b655c740da5bb39d98cd1bea88e2e0660e80` of 10 November 2026), and reaches instances with each release: instances never download it. Maintainers refresh it with `vp run referrer-spam:update`, which checks the download first: hostnames only, at least 1,000, and two guard lists (`referrer-spam-check.ts`). Real referrers (google.com, bing.com, facebook.com, t.co, reddit.com, wikipedia.org, news.ycombinator.com, and the rest) may not be listed, nor a parent or any subdomain of one, since `www.google.com` and `l.facebook.com` are how they refer visitors. Hosting platforms (blogspot.com, github.io, netlify.app, vercel.app, and the rest) may not be listed themselves, or by a parent, while their users' subdomains may (`eoriseome.netlify.app` is a spam site). An upstream entry that trips a guard wrongly is left out on purpose, with its reason, in the script's `IGNORED_UPSTREAM`, which the script drops and prints. A weekly workflow opens a pull request when it changed ([README](development.md#the-referrer-spam-list)). Only the domains are taken, as data: no code or text of Matomo's or any other analytics product.
2. **Ottertrail's own additions** (`apps/api/src/enrichment/referrer-spam/additions.ts`): one domain per line, `#` for comments, edited by hand, matched like Matomo's, and never touched by the refresh. A domain added here should also go to Matomo's list as a pull request (one per domain), so every user of that list gets it; once it is there, it leaves this file. It holds one entry under `.invalid`, which never resolves, so the tests can check the file is loaded.
3. **The project's own blocked referrers** (`projects.blocked_referrers`; "Blocked referrers" on the Spam and bots tab): up to 100 domains, each with its subdomains. Stored lower case, without a scheme, path, or port, internationalized names in their ASCII form (`bücher.example` is `xn--bcher-kva.example`), repeats dropped (400 `invalid_referrer` otherwise):
   - at least two labels, and not a common public suffix of two (`co.uk`, `com.au`, `co.jp`, `com.br`, and about fifty more in `PUBLIC_SUFFIXES`), since either would block every site under it. No dependency provides the whole Public Suffix List, so rarer suffixes pass;
   - not one of the project's allowed hostnames, nor a parent of one ("would block your own site"), checked against the allowed hostnames as they will be after the change;
   - no IP addresses.

   Loaded with the project into the key cache, so a change applies from the next request in this process, as blocked addresses do. Their matches count in `spam` too.

Limits: a spam visit's later pages carry the site's own pages as referrers, so a bot that browses on after its first page leaves those pages behind (delete them below). A list only knows the domains someone reported.

#### Deleting spam that got in

Spam caught by nothing above, or that came before a rule was added, can be deleted afterwards: whole visits, matched by filters ("Delete spam" on the Spam and bots tab). The routes need the `projects` permission ([access](access.md)):

- `POST /api/projects/:id/spam-visits/preview` counts what a delete would take: visits, their events, and of those pageviews, custom events, errors, and the rest (time-on-page reports and Web Vitals), and the session replays of their errors.
- `POST /api/projects/:id/spam-visits/delete` deletes them, given the same filters and the number of visits the user confirmed (`confirmVisits`). When the visits found are not that number any more, it deletes nothing (409 `visits_changed`).

The filters, checked by Fastify's schemas and then the route (400 otherwise):

- **A period**, required: the first and last day (`from`, `to`, `YYYY-MM-DD`) in the instance's timezone, at most 92 days, ending today at the latest, and not before the project's retention keeps events.
- **At least one of:** a referrer domain (it and its subdomains), a page path (exact), and a country (a two-letter code). Each one given must match. Without any, every visit of the period would go, so the request is refused.
- **No page hostname:** events store their page's path, not its hostname, and every stored event's hostname was an allowed one anyway ([Keys and allowed hostnames](#keys-and-allowed-hostnames)).

What goes: every event of each visit with at least one event in the period that matches every filter. A visit here is a visitor's run of events of any kind (errors and Web Vitals included, so they go with their visit) with no gap over 30 minutes, per environment, as reports count them ([section 6](#6-visits)); events outside the period that belong to such a visit go too. Server-side events belong to no visitor and are never deleted here. A visit still going on while it is deleted keeps the events that arrive after the visits are found: a period that ends today can leave the end of such a visit, which a second delete takes. The dashboard says so when the period ends today.

A delete takes at most 10,000 visits; past that it refuses, deleting nothing (409 `too_many_visits`), and the dashboard asks for a shorter period or narrower filters, to delete in parts. A delete can also stop partway, when ClickHouse fails between its statements: the visits of the statements that ran are gone, with their replays and first-seen times, the rest are not, and the answer is 500 `delete_failed`, "some visits may have been deleted", so the user counts again and deletes what is left. How it deletes, what it reaches, and what it does not: [clickhouse.md](clickhouse.md#deleting-spam-visits). Each delete is logged at info level: the user, the project, the filters, and the counts, never an IP address.

## 3. The tracker

`packages/tracker` builds `dist/tracker.js`, the script a site adds to its pages: about 12.2 KB, 5.2 KB gzipped. It loads `dist/v.js` (3.7 KB gzipped) from beside itself to measure [Web Vitals](#web-vitals), `dist/r.js` (29 KB gzipped) to record [session replays](session-replay.md) when the page asks for them, `dist/h.js` (4.8 KB gzipped) for [heatmaps](#heatmaps) when the page asks for them, and `dist/o.js` (8.0 KB gzipped) on a page opened from the dashboard to show its [heatmap overlay](#the-overlay-on-your-site). `o.js` loads `dist/s.js` (28 KB gzipped, nearly all of it rrweb) only when the owner presses "Save this view" ([saved views](#saved-views)).

```html
<script
  defer
  src="https://analytics.example.com/tracker.js"
  data-key="pk_00000000000000000000000000000000"
  data-host="https://analytics.example.com"
></script>
```

`data-user-id="42"` names the signed-in user ([section 2](#known-users)), with `data-user-signature="…"` when the project requires signed user IDs ([Signed user IDs](#signed-user-ids)); a single-page app calls `window.ottertrail.identify("42", signature)` when someone signs in without a page load, and `window.ottertrail.reset()` when they sign out. A malformed signature is left out, with a warning. Events tracked from then on carry the ID, or none. A page's time-on-page report goes with whoever viewed the page, so the sign-in page stays anonymous even when its report is sent after `identify()`. An invalid ID (empty, over 200 characters, a control character) makes the events anonymous, with a warning in the console: never the user before, who may have signed out, and never no events, as the API would refuse a whole batch for one invalid ID.

Two optional attributes name the environment and release ([section 2](#environments-and-releases)): `data-environment="staging"` on a site other than the live one, and `data-release="1.4.2"`. The tracker checks both as the API does. With an invalid environment it sends nothing and warns in the console: its events would otherwise count as production's. With an invalid release it leaves the release out, warns, and sends the events.

It sends a pageview when the page loads and whenever the path changes, and gives the page `window.ottertrail.track(name, properties)` for custom events:

```js
window.ottertrail?.track("signup", { plan: "free" });
```

`pageview`, `engagement`, `error`, and `vitals` are the tracker's own events: `track()` refuses those names, with a warning. The tracker also reports uncaught errors and unhandled promise rejections, and errors the site reports with `window.ottertrail.captureError(error)`; `data-errors="off"` turns automatic capture off ([errors](errors.md#1-capture)). `data-replay="errors"` records what happened before an error, masked in the browser, when the project's settings take replays too ([session replay](session-replay.md)). With `data-replay-consent="wait"` beside it, recording waits until the page calls `window.ottertrail.replay(true)`, when the visitor agrees; `window.ottertrail.replay(false)` stops it and drops what was recorded, and the last call wins. A page that may call before the deferred tracker runs defines a small stand-in that queues the answer ([waiting for consent](session-replay.md#waiting-for-consent)); with it, `track()`, `identify()`, `reset()`, and `captureError()` do nothing before the tracker runs (they are not queued), and never throw. The tracker loaded twice on one page warns, and the second copy does nothing. Nothing about consent is stored on the device: the site calls `replay(true)` on each page load once its consent tool knows the answer.

### It runs on someone else's site

The script runs on customers' pages, next to their own code, so:

- It never throws into the page. Every entry point catches its own errors.
- It never blocks the page: `defer` loads it after the HTML, and sending happens in the background.
- It stays small, with no dependencies.
- Secrets never leave the visitor's device. Page URLs are reduced to origin, path, and UTM tags, and referrers to origin and path, before anything is sent. The API removes them again, because it trusts no sender.
- Bad input does not cost other events. The API rejects a whole batch for one invalid event, so `track()` cleans names (control characters removed, 200 characters at most) and properties (flat values only, at most 30 keys, strings cut to 500 characters, 8 KB in total) before queuing them.

### What counts as a pageview

A pageview is a new path. The tracker records one on page load, then watches for path changes without a page load: single-page apps (React Router, Next.js, Vue Router) change the URL with `history.pushState` and `replaceState`, and the back and forward buttons fire `popstate`. The tracker wraps those two methods and listens for `popstate`.

A change to only the query string (`?tab=2`) or the fragment (`#faq`) is not a new pageview. Chrome can prerender a page before the visitor opens it; the tracker waits until the page is actually shown.

Going back or forward to a page can show it from the browser's back/forward cache, without loading it or running the tracker again. A load without the cache would record a pageview, so the tracker records one on the restore (`pageshow` with `persisted`), with the page's original referrer, and times the page from zero: time spent in the cache is not engaged time.

The first pageview's referrer is `document.referrer`, the site the visitor came from. After that, the referrer is the previous page in the app, as the browser would report for a normal page load. Reports (step 7) tell the two apart by hostname.

### Batching

New events wait up to a second and leave together in one request. Fifty waiting events, or a backlog after an outage, are sent at once. A request body holds at most 50 events and 60,000 bytes, JSON envelope included, under the API's 64 KB. In the playground run, four events from quick clicks shared one request.

The API rejects a whole batch when one event breaks its rules (step 2), so the tracker never sends such an event: a page whose cleaned URL is over 8,192 characters or whose path is over 2,048 sends none, a longer referrer is left out, and text PostgreSQL cannot store is cleaned out of names and properties.

Each event keeps the time it happened (`occurredAt`), and each request carries the time it was sent (`sentAt`), read again on every attempt, so the API's clock correction stays right even for a retry minutes later, and gives the retry the same time as the first attempt ([Clock correction](#clock-correction)). Batching shows up as delay: `received_at - occurred_at` is about one second for batched events.

### Retries

| Outcome                              | Tracker does                                       |
| ------------------------------------ | -------------------------------------------------- |
| 202                                  | Removes the events from the queue                  |
| 400, 403, 413, 415                   | Drops the batch: sending it again would fail again |
| 408, 429, 5xx, or no response at all | Keeps the batch and retries                        |

Retries wait for `Retry-After` when the server sends it, otherwise about 1, 2, 4, 8 … seconds (capped at 60), with ±20% random jitter so many visitors' browsers do not retry in step after an outage. New events do not cut a wait short, not even ones tracked while the failed request was still waiting for its answer. After 8 failed attempts the batch is dropped.

A retry sends the same events with the same IDs and times, so each counts once (step 1).

The queue holds at most 200 events. If the API is unreachable for long, the oldest events are dropped: memory on the visitor's device matters more than a complete count.

### Leaving the page

When the tab is hidden (switched away, phone locked) or the page unloads, the tracker hands every queued event to `navigator.sendBeacon`. The browser delivers a beacon even after the page is gone, but the page never sees the response, so a beacon cannot be retried. If the browser refuses a beacon, the tracker falls back to `fetch` with `keepalive`, which may also outlive the page. Mobile browsers often skip unload events, so `visibilitychange` is the signal relied on.

A batch that is in flight when the page hides may be sent twice: once by `fetch` and once by the beacon. The API stores it once.

### Time on page

The tracker measures how long each page is visible: time in a background tab or with the phone locked does not count. When the visitor leaves a page (an in-app navigation) or hides the tab, it sends an `engagement` event for that page with `properties.engagedMs`. Under one second is not reported. The time is collected again if the tab becomes visible.

`pageview` and `engagement` are reserved: `window.ottertrail.track("pageview")` is refused with a console warning, so a page cannot inflate its own numbers. The API checks that an engagement event carries a whole number of milliseconds, at most 24 hours; the tracker caps a longer time at 24 hours, so a tab left open for days still reports. Visits (step 6) use these events for duration and engaged time; they never count as pageviews or interactions.

### Web Vitals

How fast each page load felt, measured in the visitor's browser: Largest Contentful Paint (LCP, when the main content showed), Interaction to Next Paint (INP, how quickly the page answered clicks, taps, and keys), Cumulative Layout Shift (CLS, how much the content jumped), and, to explain them, First Contentful Paint (FCP) and Time to First Byte (TTFB).

- **Measured by Google's [web-vitals](https://github.com/GoogleChrome/web-vitals) library** (Apache-2.0, version 6.2.3), which handles the cases a hand-written version would get wrong: back/forward cache restores, prerendered pages, background tabs, and how INP picks among many interactions.
- **In a second script, `v.js`,** served beside the tracker (`/v.js`), which the tracker adds to the page when it starts: 3.7 KB gzipped, about as large as the tracker itself (3.9 KB), so a page that does not want it never downloads it (`data-vitals="off"`). The browser keeps the entries the library reads, so loading it after the page loses only interactions before it ran, which the tracker's `defer` makes rare.
- **One `vitals` event per page load,** sent when the page is first hidden or left, with `lcp`, `inp`, `fcp`, and `ttfb` in whole milliseconds and `cls` to four decimals, as measured until then. It belongs to the page the visitor landed on and whoever was signed in at that moment, whatever in-app navigations came after: an early redirect, such as `/` to `/en/`, does not lose it, and the click that navigates still counts for INP. A value not measured by then is left out: INP without an interaction, LCP if the page was hidden before its main content showed. Later changes, such as a slow click after the visitor comes back to the tab, are not sent. A page restored from the back/forward cache is a new page load, with its own event. When the visitor leaves the page, the browser fires `pagehide`, then `visibilitychange`, when the library takes its last measurements: the tracker sends on the second, so a slow click just before leaving still counts.
- **Not web analytics:** like time on page, `vitals` events make no visit, pageview, or custom event (`analyticsEvent()` in `visits.ts`), and are not a user's own activity (`NOT_THEIRS` in `identities/users.ts`). The name is reserved: the tracker refuses `track("vitals")`, and server-side events cannot use it. An event a site named `vitals` itself before this now counts as a page load's Web Vitals and leaves web analytics; reports ignore values outside the limits below, and a `vitals` event without one is not a page load.
- **In-app navigations get no values of their own.** The library measures page loads, as Chrome's own field data does: in a single-page app, the page load's values belong to the page the visitor landed on, and its INP and CLS include clicks and shifts on later in-app pages, until the page is first hidden.
- **The API keeps only possible values:** each a number from 0 up to 10 minutes (whole milliseconds), CLS up to 100. Any other value, and any other property, is dropped, keeping the event and its batch (`collection/vitals.ts`).

Where `v.js` does not load:

- A site that pins the tracker with `integrity` gets no Web Vitals: `v.js` could not be pinned with it, and loading it unpinned would undo the pin.
- With a strict Content Security Policy, `v.js` carries the tracker's `nonce`. A page that requires Trusted Types refuses it (the tracker goes on without it, and the browser files a report for each page load): turn it off there.
- The tracker resolves `v.js` beside its own address. A site that serves the tracker from its own folder (not supported) would load that folder's `v.js`.
- In development, the dashboard's dev server passes `/v.js` to the API, as it does `/t.js`.

Reports: the Speed page shows each metric's 75th percentile and the share of good, so-so, and poor page loads, by Google's thresholds (good up to 2.5 s for LCP, 200 ms for INP, 0.1 for CLS, 1.8 s for FCP, and 0.8 s for TTFB; poor above 4 s, 500 ms, 0.25, 3 s, and 1.8 s), by device, page, and day ([dashboard](dashboard.md#87-speed)).

Checked in headless Chromium with the built scripts (17 November 2026): the page loaded `t.js`, then `v.js`, redirected in-app from `/` to `/en/`, and after a click and leaving, one `vitals` event for `/` carried all five, INP included.

## 4. Enrichment

Each request carries two clues the visitor never typed: the `User-Agent` header names the browser and operating system, and the IP address shows roughly where the visitor is. When events arrive, the API turns those into columns. Code: `apps/api/src/enrichment/`; the columns are in ClickHouse's events table (migration `0001_create_tables`).

| Column            | From       | Example                             |
| ----------------- | ---------- | ----------------------------------- |
| `browser`         | User-Agent | `Chrome`, `Microsoft Edge`          |
| `browser_version` | User-Agent | `142` (major version only)          |
| `os`              | User-Agent | `macOS`, `iOS` (name only)          |
| `device_type`     | User-Agent | `desktop`, `mobile`, `tablet`, `tv` |
| `country`         | IP address | `DE` (ISO 3166-1 code)              |
| `region`          | IP address | `Bavaria` (English name)            |
| `city`            | IP address | `Munich` (English name)             |

Every event in a request shares these values: one request comes from one browser and one address. Events stored before step 4 have `NULL` in all of them.

### The IP address is never stored or logged

The address is used in memory for the location lookup, the data-center check, the per-client limits, and the project's blocked addresses, and then dropped. No column of an event holds it, and request logs record only the method and URL: Fastify's default request log includes the client's address and port, so the API replaces it (`requestLogFields` in `apps/api/src/app.ts`). A test sends requests and checks that no log line contains the address.

The only IP addresses Ottertrail stores are those an owner or admin types into a project's [blocked addresses](#blocked-addresses), by their own choice: their office's, a scraper's. Only the owner and admins see them (members get the project without its settings, [access](access.md)), they are never stored with events, and they are deleted with the project. `GET /api/client-address` answers the requester's own address to them and logs nothing.

Under GDPR an IP address is personal data. Not keeping it also means locations can never be recomputed later: whatever was known when an event arrived is all there will ever be.

### Browser, OS, and device

[bowser](https://github.com/bowser-js/bowser) (MIT) parses the User-Agent. (`ua-parser-js` was not used: from version 2 it is licensed AGPL, which would bind Ottertrail's own license choice.)

Browsers now freeze parts of the User-Agent so people are harder to fingerprint ("User-Agent reduction"). Every Mac reports macOS 10.15.7 and Windows 11 reports Windows NT 10.0, so OS versions would be wrong: only the OS name and the browser's major version are kept. iPads present themselves as Macs by default, so the User-Agent alone counts them as desktop Macs. Macs have no touchscreen, though, so when the tracker reports one (`touch` in the batch: `navigator.maxTouchPoints` over 1), a "Mac" is recorded as iOS on a tablet. The hint is one yes-or-no value, sent only when true, so it adds almost nothing to tell visitors apart. Touch on anything else changes nothing: many Windows laptops have touchscreens.

### Location

A geolocation database maps IP address ranges to places. Ottertrail uses DB-IP's free [IP to City Lite](https://db-ip.com/db/download/ip-to-city-lite) database: licensed CC BY 4.0, updated monthly (usually on the 1st), in MMDB format, a binary search tree of address ranges. The API loads the whole file into memory (about 130 MB), at startup and again when the file is replaced and reads it with [mmdb-lib](https://github.com/runk/mmdb-lib) (MIT); a lookup takes microseconds and never leaves the server.

- Country is close to a fact. Region and city are estimates: MaxMind, another provider, reports that its GeoIP products place US addresses in the right region about 80% of the time, and in the right city within 50 km about 66% of the time ([source](https://support.maxmind.com/knowledge-base/articles/maxmind-geolocation-accuracy)). Mobile networks, VPNs, and iCloud Private Relay show where traffic leaves the network, not where the person is.
- DB-IP Lite regions have English names only, not ISO codes, so `region` holds names such as `Bavaria`.
- Private and local addresses (`127.0.0.1`, `192.168.x.x`) have no location. In local development every event has an empty location.

Each project picks where its locations come from, in its settings under **General**, **Location data** (`projects.location_source`, migration 0027). It applies to new events only: stored events keep their location, and nothing is filled in or deleted afterwards.

| Source               | Locations from                                                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `database` (default) | The DB-IP file at `GEO_DATABASE_PATH`. If it is missing, events are stored without a location, and the API logs a warning at startup.                |
| `headers`            | Request headers a proxy or CDN in front of the instance adds (below). There is no fallback to the database: a missing header leaves its field empty. |
| `off`                | Nowhere: events are stored without a location, and no lookup runs.                                                                                   |

Collection reads the project's source with its key, from the key cache (`src/collection/project-keys.ts`), so it costs no query per request. Saving a change clears the cache in the API at once: the next request uses the new source. The `GEO_SOURCE` variable did this for the whole instance until release 0.3.0; it was removed, and every Ottertrail command and service that reads the configuration (the API, the worker, `migrate.mjs`, `update-geo.mjs`, and the others) stops at start while it is set, with "GEO_SOURCE was removed; choose each project's location source in its settings (Location data)."

The location file is needed only while some project uses `database`. When none does, the worker does not download it, and the API does not load it, or drops the copy it has (about 130 MB) so that garbage collection frees it (`src/enrichment/reload.ts`). The API checks every minute, and at once when a project's source is changed, created, or deleted; when a project uses `database` again, the file loads if it is there, without a restart. If it is not, the worker downloads it at its next minute's check, as long as automatic updates are on (else `update-geo.mjs` does), and the API's next minute check loads it. While the file is needed and none is loaded, as on a new instance, each minute check looks for it on disk. The check gives up after 5 seconds without an answer, so a network that drops packets cannot hold up reloads, and a check that fails is logged once, and once more when it works again. The data-center ranges are for bot filtering, not locations, and are downloaded and loaded either way.

#### Locations from a proxy's headers

With `headers`, the project names up to three request headers (letters, digits, and `-`, at most 64 characters, stored in lower case): the country one, which is required, and optionally a region and a city one. Refused names: those Ottertrail uses itself (`X-Ottertrail-Trusted-Proxy`, `Host`, `Cookie`, and the like); every header that carries the visitor's address (`X-Forwarded-For`, `Forwarded`, `X-Real-IP`, `X-Client-IP`, `CF-Connecting-IP`, `True-Client-IP`, `Fastly-Client-IP`), since the address is never stored; hop-by-hop headers (`Connection`, `Transfer-Encoding`, and the like); and headers Node keeps only the first of when repeated (`Location`, `Last-Modified`, `Retry-After`, and the like). A region or city value that is an IP address is dropped too.

Anyone can send any header, so the headers are read only from requests that came through a trusted proxy, and Caddy decides which those are. Its Caddyfile in `deploy/compose.yaml` always sets `X-Ottertrail-Trusted-Proxy` to its own `{http.vars.trusted_proxy}`: `true` when the connection came from one of `OTTERTRAIL_TRUSTED_PROXIES`, else `false`. It replaces whatever a client sent, so a visitor who connects directly, or sends the header themself, gets `false`, and their location headers are ignored. A test runs the shipped Caddyfile in the `caddy:2.11.9-alpine` image to check both cases (`tests/deploy-files.test.ts`). The API also reads the headers only when it is set to be behind a proxy (`TRUST_PROXY`): an API reached directly, without one, reads none, even when a request says `true`.

Without Caddy (the image run directly, behind a platform's proxy, with `TRUST_PROXY` set), nothing in Ottertrail can tell a header the proxy set from one the visitor sent: most proxies pass a client's own `X-Ottertrail-Trusted-Proxy: true` straight through. On every request, the proxy in front of the API must then set or remove `X-Ottertrail-Trusted-Proxy`, and set or remove every location header the project names. Otherwise any visitor can choose its own location.

The values are cleaned as the database's are:

- **Country:** two ASCII letters that are an assigned ISO 3166-1 alpha-2 code, or `XK` (Kosovo, which the database uses too), stored in upper case as the database stores it (`fr` becomes `FR`). The list is the codes `Intl.DisplayNames` names, less those ISO has not assigned. Anything else is dropped: `XX` (Cloudflare's "unknown"), `T1` (Cloudflare's Tor), `ZZ` and other user-assigned codes, `EU`, `UN`, `UK`, withdrawn codes such as `YU`, three-letter codes, names, and letters beyond ASCII (Latin-1 `ß` would otherwise upper-case to `SS`).
- **Region and city:** stored as sent, trimmed and cut to 100 characters without splitting a character. The database stores English names (`Bavaria`), so send the region's name, not its code, for the reports to match across projects. A value with a control character, a format character (bidi controls, zero-width characters), or a line or paragraph separator is dropped, as other ingested text is, and so is one that is an IP address.
- **Text beyond ASCII.** Node reads header bytes as Latin-1. A value whose bytes are valid UTF-8 (as `Zürich` sent raw) is decoded as UTF-8; other bytes stay Latin-1. A percent-encoded value (`Z%C3%BCrich`) is decoded.

Cloudflare, as one example: in its dashboard, under **Rules**, then **Transform Rules**, create a request header modification rule for all incoming requests that sets `x-visitor-country` to the dynamic value `ip.src.country`, `x-visitor-region` to `ip.src.region`, and `x-visitor-city` to `ip.src.city`. Then choose `headers` for the project, with those three names, and set `OTTERTRAIL_TRUSTED_PROXIES` to Cloudflare's ranges ([deployment](deployment.md#behind-a-proxy-or-cdn)). Requests from any Cloudflare customer's zone arrive from the same ranges, so Caddy marks them trusted too, and such a zone, pointed at your server, could set any `x-visitor-*` value. Cloudflare's Authenticated Origin Pulls with your own certificate restricts the server to your zone ([deployment](deployment.md#if-you-use-cloudflare)).

### Why the file is held in memory

The geolocation "database" is a file, not a database server: a lookup tree that a library walks by reading the file's bytes, so the bytes must be in RAM to be fast. The API loads the file once at startup and every request reads that single copy. Memory does not grow with traffic.

Measured on a development Mac with the November 2026 DB-IP City Lite data (PostgreSQL ran in Podman's virtual machine, which makes its round trips slower than on a Linux server):

| Option                       | Lookup                                | Memory added to each API process | On disk      | Monthly update                                             | Extra server           |
| ---------------------------- | ------------------------------------- | -------------------------------- | ------------ | ---------------------------------------------------------- | ---------------------- |
| MMDB file in memory (chosen) | 6.2 µs                                | about 130 MB                     | 127 MB       | Download a ready-made file                                 | No                     |
| SQLite file (`node:sqlite`)  | 6.2 µs                                | about 30 MB                      | 562 MB       | Download the CSV (86 MB), import 7.8 million ranges (18 s) | No                     |
| PostgreSQL table             | at least 165 µs (an empty `select 1`) | none                             | not measured | Import into a new table, swap tables                       | No                     |
| MySQL                        | similar to PostgreSQL                 | none                             | not measured | Import                                                     | Yes, on every instance |

SQLite needs little process memory because it reads pages on demand into the operating system's file cache, which all processes share and the system can reclaim. It returned the same answers as the MMDB file for 10,000 random addresses.

The MMDB file is the default because each instance runs one API process and it needs no import code. Switch to SQLite if memory becomes tight, for example with several API processes per instance or on 1 GB servers: only the lookup in `src/enrichment/geo.ts` and the update in `src/enrichment/updates.ts` would change. A PostgreSQL table would add a query to every request on the busiest part of the system, and MySQL would add a second database server to every customer's instance.

Load test: 10,000 requests, 100 at a time, each from a different public address, against one API process with the file loaded. All 10,000 were stored with a country and city, at about 9,800 requests per second (median 9 ms, 99th percentile 46 to 92 ms). Memory went from 177 MB idle to a peak of about 315 MB under load and settled near 270 MB; three rounds (30,000 requests) peaked at the same level. The growth is Node's heap working on 100 requests at once, not the file: it depends on how many requests are in flight, not on how many arrive. The load generator ran on the same machine, so these numbers show the shape, not a capacity promise for a server.

### Keeping the files current

IP ranges change hands: ISPs reassign them, IPv4 addresses are bought and sold, cloud providers move them. An old file does not fail; it gives slowly more wrong answers, city first. Lookups happen when events arrive, so a newer file only affects new events. The same holds for the data-center ranges (below), which providers extend every week.

The worker keeps both files current on its own (`src/enrichment/updates.ts`):

- **When.** At start, then every 6 hours, it looks whether either file is due. It reads the setting every minute, so turning automatic updates on starts a round within a minute. The location database is due when it is missing or holds an older month than the current one (UTC). DB-IP publishes each month's file on the 1st; until it is out, last month's is taken, and the worker asks again for this month's at each look, without downloading last month's again. The data-center ranges are due when the file is missing, unreadable, or written more than 7 days ago. The location database is only downloaded while some project's location source is `database` (checked every minute too, so a project choosing it starts a round within a minute); the data-center ranges are downloaded either way, because collection checks them for every project that ignores data centers.
- **Which month a file holds.** Each update records the month it downloaded, with the file's size and modification time, in PostgreSQL (`location_data_updates`), and writes the same beside the file (`dbip-city-lite.mmdb.month`), so the month is known even when PostgreSQL could not record it. A file that matches neither (replaced by hand) counts by the month it was written in, if it opens and passes the check below; if it does not (cut short, or not a database), it is due at once. A marker that cannot be written is logged as a warning; the update still counts as a success.
- **How.** The file is downloaded next to the old one, under a name of the updater's own (`dbip-city-lite.mmdb.<updater>.download`), unzipped, flushed to disk, and checked: it must open as a City database and place `8.8.8.8` in the US. Only then is it renamed over the old file, in one step. The data-center ranges follow the rules in "Data centers" below; when every source fails, the old file stays as it was and stays due. The worker's first round, and the manual command, delete partial files not written to for longer than a lease lasts, so another updater's download in progress is never touched.
- **Limits.** Redirects are followed by hand, at most 5, and only to `https` addresses. The unzipped location file may be at most 1 GB, each provider's list 50 MB, and each line of DB-IP's ASN file 65,536 characters; past that, the download fails as any other does.
- **Failures.** A failed download or check keeps the old file, logs a warning, and records the error and how many attempts in a row failed. A missing file is tried again after 15 minutes, then 30, doubling up to 6 hours. A file in place is tried again at the next 6-hourly look, and after 3 failures in a row once a day. The manual command does not wait. On shutdown the worker stops a download under way: the old file stays, and the stop is not recorded as a failure; a file already moved into place is still recorded.
- **One at a time.** An update holds a lease, a row in `location_data_lease`, for as long as it runs. A second worker, or the manual command, finds it taken and does nothing. A round gives up 55 minutes in, before its one-hour lease could run out, so two never overlap. No PostgreSQL connection is held during the download, so a restarted or ended backend cannot break an update; a process that dies leaves the lease to expire after an hour. The worker keeps one name for its whole life and takes its own lease back, so a release that failed (PostgreSQL down at the end of a round) does not lock it out. Every process's connection pool also handles an idle connection ending (`src/db/database.ts`): the API and the worker log it in their own log, and the next query opens a new one. While PostgreSQL cannot be reached, the worker logs the failure once, and once more when it works again.
- **Memory.** The check reads the whole location file into memory and keeps nothing once it has answered; the next garbage collection frees it. With the November 2026 file, the check added 128 MB to the process (measured on a development Mac, 19 November 2026). The worker idles at about 54 MB ([deployment](deployment.md#what-runs)), so it peaks near 180 MB for a few seconds once a month. The resident size can stay higher for a while after the buffer is freed, until the operating system takes the pages back. The download streams to disk, and the data-center ranges add a few megabytes.

The API looks every 10 minutes whether either file changed on disk (its size or modification time; `src/enrichment/reload.ts`). A changed file is loaded in full and given the same check as above. Only then does it replace the one in use, so a lookup never sees half a file. A file that fails keeps the old data, with a warning in the API's log and the reason on the Settings page, and is not tried again until it changes again. The API keeps only the copy in use: nothing else refers to a replaced copy, the startup one included, so it goes at the next garbage collection (a test checks this). While the new location database loads, both copies are in memory: the second one added 127 MB in the same measurement, so an API that idles at 177 MB with the file loaded (the load test above) peaks near 305 MB, once a month.

At startup the API logs each file's date, and warns when the location database is missing or more than 60 days old, or the data-center ranges are missing or more than 45 days old. A new instance has neither file at first. With automatic updates on, the worker downloads the data-center ranges when it starts, and the location database too once some project uses it (a new project does, by default). The API loads the location database within a minute of its download, and the data-center ranges within 10 minutes.

The owner turns this off on the instance's Settings page ("Update location data automatically", `instance_settings.update_location_data`, on by default): for an instance without internet access, or whose owner does not want the downloads. The worker then downloads nothing. The same page shows each file's state (for the location database, "Not used" when no project uses it): whether the API has it loaded, its build or download date, the last update, and the last error. When the worker downloaded a file more than 15 minutes ago, by the server's clock, and the API still has the older one, the page says so, with the API's reason when it has one, or else that the API and the worker may not share the folder.

`vp run geo:update` (in the Docker image, `node dist/update-geo.mjs`) downloads both files at once, whatever is due and whatever the setting. When no project uses the location database, it downloads only the data-center ranges and says the location database was skipped; when PostgreSQL cannot be reached, it cannot tell, and downloads both. It takes the same lease and records its status when PostgreSQL can be reached, and updates without them when it cannot. It exits with 1 when a download fails, or when an update is already running, and then says when that update's lease ends at the latest. Ctrl-C (SIGINT) or SIGTERM stops it cleanly: the download is cut off, its partial file deleted, the lease given back, and it exits with 130 or 143.

The license requires credit: show "IP geolocation by DB-IP" with a link to db-ip.com wherever locations are displayed.

### Bots

[isbot](https://github.com/omrilotan/isbot) (public domain) recognizes User-Agents that announce themselves as automated: search engine crawlers, link previews, monitoring tools, headless browsers, and HTTP libraries such as `curl`. A request without a User-Agent counts as a bot too, since every browser sends one.

Bot requests get `202`, the same answer as a stored batch, and nothing is stored: an error would only invite retries. The Activity tab counts them. They are checked before the per-project event budget, so they cannot use it up.

To send test events with `curl`, pass a browser User-Agent (`-A "Mozilla/5.0 …"`), or they are counted as bots. Automated browser tests need a normal User-Agent for the same reason (headless Chrome says `HeadlessChrome`), and must not run in a data center (below).

### Data centers

Many bots say they are an ordinary Chrome or Safari. What gives most of them away is where they run: people browse from homes, offices, and phones, while scrapers, headless browsers, and test runs run on servers rented from a cloud or hosting provider. A browser event from such an address is accepted and ignored like any bot (`202`, the same answer as a stored batch, counted as a bot in the Activity tab), before the project's event budget. The address is checked while the request is in hand, as for its location, and never stored.

The ranges come from two kinds of source, downloaded by the worker each week, or by `vp run geo:update` (`src/enrichment/data-center-sources.ts`), into one file the API reads (`DATA_CENTERS_PATH`; see "Keeping the files current" above):

- **Lists the providers publish** for their customers' firewalls: Amazon Web Services (the EC2 ranges, where servers, Lambda, and containers run), Google Cloud, Microsoft Azure (the `AzureCloud` service tag), Oracle Cloud, DigitalOcean, Akamai Cloud (Linode), and Vultr. A provider's list, not its whole network: Amazon's, Google's, and Microsoft's networks also carry their offices, their DNS, and their own services, whose users are people.
- **Hosting providers without a list**, by the networks (ASNs) their servers are announced from, in DB-IP's IP to ASN Lite database (CC BY 4.0): Hetzner, OVHcloud, Scaleway, Contabo, Alibaba Cloud, Tencent Cloud, and Huawei Cloud (`HOSTING_NETWORKS`). RIPEstat would answer the same question, but its terms do not allow commercial use without written permission.

On 17 November 2026 the file held 20,426 ranges from 14 providers, about 4.7% of IPv4 addresses; a lookup took about 4 µs. A source that fails keeps its previous ranges, and the update records which sources failed; the Settings page shows them. When every source fails, the file is not written at all.

What it costs:

- **People in a cloud are ignored too:** remote desktops (Amazon WorkSpaces, Windows 365), some VPNs, and corporate proxies that run on these providers. A project whose visitors browse that way can turn the check off ("Ignore visits from data centers" on its settings' Spam and bots tab, `ignore_data_centers`, on by default). Server-side events are never checked: they come from the site's own server by design.
- **Not people behind privacy relays:** none of Apple's iCloud Private Relay exit ranges (`mask-api.icloud.com/egress-ip-ranges.csv`, 285,194 ranges on 17 November 2026) was in the file, and CDNs such as Cloudflare, Akamai's edge, and Fastly, which carry such relays, are not in it on purpose.
- **Test runs in CI are ignored:** GitHub Actions runners, for example, run in Azure. Tests that should count need a project with the check off.
- **Behind a proxy without `TRUST_PROXY`,** every request seems to come from the proxy's address, which may be a cloud's: then every event would be ignored. Set `TRUST_PROXY` (see "Rate limits" below).
- **A site that forwards its events through its own server** (to get past ad blockers) sends them all from that server's address, which is usually in a cloud: all of them would be ignored. Such forwarding is not supported anyway, since every visitor would share the server's address, location, and visitor ID. The API logs, once per project and process, when it starts ignoring a project's events this way.
- **Bots elsewhere still count:** on home connections (residential proxies, infected computers) or at providers not listed. Spotting those needs behavior signals; that is not built.

Without the file, nothing counts as a data center, and the API warns at startup; it also warns when the oldest ranges are more than 45 days old. With automatic updates on, the ranges are at most a week old, unless the downloads fail.

Every range is checked before use (`parseRange` in `data-centers.ts`), so one bad line in a provider's list cannot catch everyone: a range wider than a /8 (IPv4) or /16 (IPv6), one over private, loopback, shared, or multicast IPv4, and IPv6 outside global unicast or in 6to4 (whose addresses stand for IPv4 ones) are left out. A source whose download yields fewer than 5 valid ranges, such as a maintenance page in place of the list, counts as failed.

## 5. Visitors

Counting unique visitors without cookies, local storage, or anything else kept on the visitor's device. Code: `apps/api/src/visitors/visitor-ids.ts`; the salts are in PostgreSQL's `visitor_salts` table (migration `0001_create_schema`).

### The visitor ID

```
visitor_id = first 8 bytes of HMAC-SHA256(today's salt, project + IP address + User-Agent)
```

The same browser on the same network gets the same ID for the rest of the day, so pageviews can be counted per visitor. The salt is a random 32-byte secret for one day. Including the project means one person on two projects gets two unrelated IDs. The ID is stored in `events.visitor_id` as a 64-bit integer; the IP address and the salt are never stored with an event.

### One salt per timezone and day

The instance has a timezone, an IANA name such as `Asia/Singapore`, in its settings. It is chosen on the setup page (UTC until then); the owner can change it on the dashboard's Settings page ([dashboard](dashboard.md#instance-settings)). A new salt starts at its midnight, and reports (step 7) count days in the same timezone, so a visit is never split across two salts inside one reported day. With a UTC midnight, a visitor in Singapore reading from 07:30 to 08:30 local time would cross 00:00 UTC and be counted twice that morning.

`visitor_salts` holds one salt per timezone and day, and the project is part of every visitor ID, so projects sharing a salt never share visitor IDs. Changing the instance's timezone moves where days start in all its reports, past days included, and gives its visitors new IDs from the change until midnight.

Aliases become the name Node.js resolves them to: `singapore` is stored as `Asia/Singapore`, `GMT` as `UTC`.

Each event uses the salt of the local day it happened on. A pageview from 23:55 that arrives at 00:05 joins the rest of that day's visit instead of starting a new visitor.

### How salts live and die

- A day's salt is created the first time that day is needed, in the `visitor_salts` table, so every API process and every restart uses the same salt. Each process caches salts in memory.
- Events arrive up to 24 hours late, so a salt is needed until 24 hours after its day ends. It is kept one hour longer (`SALT_GRACE_MS`), then deleted. The endpoint and the cleanup read the clock at slightly different moments; without the extra hour, an event accepted at the very edge of the window could find its salt deleted a moment later, get a new salt, and with it a different visitor ID. A test reproduces that case.
- Deletion runs when the API starts, every hour after that, and whenever a new day's salt is created, so salts go on time even when no events arrive. Each timezone's salts are deleted by its own calendar. Every API process runs the hourly cleanup; deleting twice is harmless. The worker does not delete salts.
- Once a salt is gone, nobody can tell which IP address one of that day's visitor IDs came from, not even Ottertrail's operator. (A deleted row's bytes can stay in PostgreSQL's data files until the space is reused, and in backups, so the promise is complete once those copies are gone too.)
- There is no setting for the rotation period. Daily keeps the privacy promise simple: an anonymous visitor is never linked across days, which is also why a visit that crosses midnight counts as two (section 6). Changing the period later would split the data into two eras, because IDs cannot be recomputed without the IP addresses. The period lives in one place (`dayIn` and `MAX_EVENT_AGE_MS`) if a real need appears.

### What "visitors" means

- For one day: distinct visitor IDs, the number of browser-and-network combinations seen.
- For a longer range: visitors cannot be linked across days, so a 7-day "visitors" figure counts someone once for each day they visited. Reports must say so.

The count is an estimate in both directions:

- One person counts twice when their address changes during the day: phones moving between Wi-Fi and mobile data, VPNs, iCloud Private Relay, and rotating IPv6 privacy addresses.
- Several people count once when they share an address and the same browser version, such as an office network or a carrier's shared address (CGNAT).
- A browser update during the day starts a new ID.

Logged-in users will get exact IDs from the tracker's `identify()`, a later step.

### Privacy

Nothing is stored on the visitor's device, and the IP address is used only in memory. While a day's salt exists (at most about two days), someone with access to the database could test a guessed IP address and browser against the IDs; the IPv4 address space is small enough to try every address. Deleting salts quickly is what closes that window. Database backups contain the salts that existed when they were taken, so the backup retention period extends the window; keep that in mind when backups are set up.

Under GDPR, such IDs are generally treated as pseudonymous data while the salt exists. This describes the design; it is not legal advice.

### Dates as strings

PostgreSQL `date` columns, such as `visitor_salts.day`, are read as `"YYYY-MM-DD"` strings (`apps/api/src/db/database.ts`). By default the `pg` driver turns them into JavaScript dates at local midnight, which shifts the day whenever the server's timezone differs from the data's.

## 6. Visits

A visit (often called a session) is one visitor's run of activity. Code: `apps/api/src/visits/visits.ts`.

### The rule

**A visit ends after 30 minutes without an event.** The next event starts a new visit. A gap of exactly 30 minutes keeps the visit going.

Visits are worked out for one environment at a time. A developer who opens the live site and then the staging site has the same visitor ID on both (same browser, same network, same day), and the two must not join into one visit.

### Worked out when a report asks

Nothing about visits is stored. `visitsQuery` works them out from the events with SQL window functions. Reports use it inside their own SQL; `findVisits` returns the visits as objects.

1. For each event, find the same visitor's previous event (`lag(occurred_at) over (partition by visitor order by occurred_at)`).
2. Mark a visit start where there is no previous event or the gap is over 30 minutes.
3. A running count of those marks numbers each visitor's visits: 1, 2, 3 …
4. Group by visitor and visit number to get each visit's pages, times, and first event.

Because visits are computed from the stored facts every time:

- late and out-of-order events land in the right visit; a late event that fills a gap joins two visits into one;
- a retried event counts once: it is stored as the same row (the same project, day, and event ID), which ClickHouse keeps once and reports read with `FINAL` ([ClickHouse](clickhouse.md#each-event-once));
- changing a rule (30 minutes to 20) applies to all past data at once.

The cost is work at report time: every event in the range is sorted by visitor and time. Section 7 measures it (Speed).

### A time range

A visit counts in the range in which it **started**. Visitor IDs change at midnight, so every visit lies within one local day, and no local day is longer than 25 hours (when clocks go back). The query reads 25 hours before and after the range: enough to see where each visit started, and to see it to the end, since its exit page and whether it bounced can depend on later events.

### What each visit has

| Field              | Meaning                                                                          |
| ------------------ | -------------------------------------------------------------------------------- |
| `startedAt`        | First pageview or custom event                                                   |
| `endedAt`          | Last event, including the last engagement report                                 |
| `durationMs`       | `endedAt - startedAt`                                                            |
| `engagedMs`        | Sum of the visit's engagement events: time pages were visible                    |
| `pageviews`        | Pageviews in the visit                                                           |
| `interactions`     | Custom events, such as `signup`                                                  |
| `entryPath`        | Path of the first pageview                                                       |
| `exitPath`         | Path of the last pageview                                                        |
| `bounce`           | One pageview and no interaction                                                  |
| Source and visitor | Referrer, UTM tags, browser, OS, device, and location of the visit's first event |
| `release`          | The release of the visit's first event                                           |

**Exit page.** Nobody is told when a person leaves: closing the tab, switching apps, losing signal, and walking away all look the same. The exit page is simply the last page viewed, known for certain only once 30 minutes pass without another event.

**Bounce.** One pageview and no custom event. Engagement events do not count, so a long read of one page is still a bounce; `engagedMs` tells a quick exit from a long read. Other tools define a bounce differently, so bounce rates from different tools are not comparable.

**Engagement.** Engagement events extend a visit but never start one. A page left visible for over 30 minutes with no other event reports its time too late to belong to the visit, and that time is not counted, not even when the visitor then clicks a link and starts a new visit at the same moment. At the same timestamp, an engagement event is ordered before a pageview, since it reports the time up to that moment.

### Midnight

Visitor IDs change at midnight in the instance's timezone (step 5), so a visit that crosses midnight counts as two: one that ends before midnight and one that starts after it. Joining them would need a stored link between the visitor's IDs on the two days, and the link would outlive the salts. Anyone who could compute today's ID from a guessed address could follow it back to yesterday's events, which is what daily salts exist to prevent.

The first version stored such a link (`previous_visitor_id`) on every event in the first 30 minutes after midnight. A review found the privacy problem, and the column was removed. The cost is small: a visit is split only if it is in progress at midnight, so a 10-minute visit has about a 10 in 1,440 (0.7%) chance.

### Try it

```sh
vp run visits                      # the first project, last 24 hours
vp run visits -- Playground 6      # a project by name, last 6 hours
```

Times are shown in the instance's timezone.

## 7. Reports

Reports turn events and visits into the numbers a dashboard shows. Code: `apps/api/src/reports/reports.ts`. Like visits, every number is computed from the stored events when asked. Reports read the events in ClickHouse, where the API stores them ([clickhouse.md](clickhouse.md)); PostgreSQL counts the days.

### Days in the instance's timezone

A report covers whole calendar days in the instance's timezone, the timezone that also starts each visitor salt. `localDays` asks PostgreSQL where those days begin and end (`'2026-11-16'::date::timestamp at time zone 'Asia/Singapore'`), so a 23- or 25-hour day, when clocks change for daylight saving, comes out right. Charts count by local day too, and days without data appear with zeros.

### The numbers

| Report           | What it counts                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| Visitors         | Distinct visitor IDs. IDs change daily, so a person who came on 3 days counts 3 times (section 5) |
| Pageviews        | `pageview` events                                                                                 |
| Visits           | Visits that started in the range                                                                  |
| Views per visit  | Pageviews in those visits, divided by visits                                                      |
| Bounce rate      | Visits with one pageview and no custom event, divided by visits                                   |
| Visit duration   | Average of `endedAt - startedAt`. A bounce is 0 seconds unless the page sent an engagement report |
| Time engaged     | Average time pages were visible per visit, from engagement events                                 |
| Visitors per day | Visitors, pageviews, and visits for each local day. A visit counts on the day it started          |
| Top pages        | Pageviews and visitors per path, and the average time on page from that path's engagement reports |
| Breakdowns       | Visits and visitors grouped by one property of the visit (below)                                  |
| Custom events    | Each custom event name, how often it happened, and how many visitors sent it                      |

Visitors and pageviews count events in the range. Visits, bounce rate, and durations count visits that started in it. A visit from 23:50 to 00:20 counts on the first day, while its 00:05 pageview counts on the second.

### Breakdowns

A breakdown groups visits by one property: `source`, `entryPage`, `exitPage`, `utmSource`, `utmMedium`, `utmCampaign`, `country`, `region`, `city`, `deviceType`, `browser`, `os`, or `release`. All but the exit page come from the start of the visit, so each visit counts once, under where it began. Rows are sorted by visitors, then visits. A missing value (no location, an unknown browser) is a row of its own, which the report script prints as "(unknown)".

**Source** is the first of these that exists:

1. `utm_source` from the page URL (`?utm_source=newsletter`).
2. The referrer's hostname without `www.`: `https://www.google.com/search` becomes `google.com`. Android apps send their package name: `android-app://com.google.android.gm` becomes `com.google.android.gm`, the Gmail app.
3. `Direct / none`: no referrer, as with a typed address, a bookmark, or a link in an app that sends none.

A referrer on one of the project's own allowed hostnames is not a source. It means the visit began on a page of the same site, such as a tab left open for over 30 minutes, so it counts as direct.

**Region and city** keep their country (`Springfield, US`), because the same names exist in several countries.

### One environment at a time

Every report counts the events of one environment, `production` unless another is named ([section 2](#environments-and-releases)): its visitors, visits, pages, and lists. Other environments' events never mix in, filtered or not. An environment is not a filter of visits but where the reports look, as the project is.

### Filters

A filter narrows every report to the visits that match it, and to those visits' events. Several filters must all match. Two kinds:

- **A breakdown's value** (`source`, `entryPage`, `exitPage`, `utmSource`, `utmMedium`, `utmCampaign`, `country`, `region`, `city`, `deviceType`, `browser`, `os`, `release`): visits whose property has exactly the value its breakdown row shows, such as `google.com`, `Direct / none`, or `Munich, DE`. The filter and the breakdown use the same SQL expression, so a row's filter keeps exactly the visits that row counted, and a test checks that filtering by each row of a breakdown adds up to all visits. An empty value matches visits where the property is unknown, the "Unknown" row.
- **A page** (`page`): visits with a pageview of that path. Every number then describes those visits, so the pageviews count all their pages, not only the filtered one: filtering by `/pricing` shows what else visitors who saw the pricing page looked at.

"Their events" is exact because a visit lies within one local day (visitor IDs change at midnight) and reports cover whole local days: every pageview and custom event in a range belongs to exactly one of the range's visits, from its first event to its last. Visitors and pageviews under a filter therefore count the matching visits' events. One small difference from the unfiltered page: the average time on a page leaves out stale engagement reports (section 6), which belong to no visit.

Filter values are compared, never parsed or run: each name maps to a fixed expression and the value is a query parameter.

### Comparison with the previous period

Each number of the summary is compared with the period right before: as many days, in the same timezone, with the same filters. A period that is still running (it ends today, or later) only has data up to now, so it is compared up to the same moment of its earlier counterpart: now, moved back by the period's length. At 15:00, the last 7 days are compared with the 7 days before them up to 15:00 on their last day. Compared with whole days instead, a day in progress would always look down. A range that ends after today stops earlier still: on 16 November, all of November is compared with 2 to 17 October, and the comparison's last day says so. Past ranges that are over compare whole days.

The earlier period is seen as it stood at that time: every report ignores events after the cut-off (`until`), so a visit in progress then counts what had happened by then, as today's visits do now, and its pageviews stop at the same moment as its visits. The days are shifted on the calendar by PostgreSQL (`previousDays`), so a daylight saving change keeps the same time of day.

Counts and averages change in percent, rounded; a change too small to round to 1% shows as "<1%", never as no change. The bounce rate, a share, changes in percentage points: from 24% to 30% is 6 points, where "25% more" would mislead. Points are worked out from the whole percentages shown, so the change always matches them. A number with nothing to compare with (nothing before, or 0) shows no change.

### Who can read reports

Signed-in dashboard users, through one endpoint per page ([dashboard.md](dashboard.md#83-report-endpoints)), and anyone with database access through `vp run report`. A public project key never reads data (section 2). Each breakdown name maps to a fixed SQL expression, so request text never becomes SQL, and row limits are clamped to 1-100.

### Try it

```sh
vp run report                      # the first project, last 7 days
vp run report -- Playground 30     # a project by name, last 30 days
```

The last day is today, so it is partial.

Reports that only count events (top pages, custom events) read the range's events once. Reports on visits cost more, and the cost grows with the number of events in the range: working out visits sorts every event by visitor and time, then groups them. At 1,000 visits a day, each 30-day report takes under 0.3 seconds; at about 7,000 a day, 1.2-2.3 seconds.

**What was tried.** Several versions of the visit query were measured against the step 6 query on the same data, and none was faster:

- Sorting only the columns needed to find visits, then reading each visit's first event by its ID: slower, because 190,000 index lookups cost more than carrying the columns through the sort.
- Finding each visitor ID's runs first, then joining runs across midnight: no faster over 30 days, and 10 to 20 times slower over 1 day (0.1 seconds became 1-2). PostgreSQL estimated far fewer rows than there were and chose nested loops, which compare every row with every other.
- A larger `work_mem` (64 MB instead of 4 MB) changed nothing. Turning off JIT compilation saved 5-10%.

`EXPLAIN ANALYZE` misled the first attempt: timing each step slows the steps that handle many rows, which hides where a query spends its time. Timing the whole query is the reliable measure. The query kept is the step 6 query, except that reports that only count visits skip the first-event columns, so the large sort carries less data. Removing the midnight links (section 6) then made 30-day reports up to twice as fast: the query no longer joins the range's events to themselves, so PostgreSQL no longer writes them to a temporary store on disk and reads them twice. 1-day reports got slightly slower, because the query now reads 25 hours on each side of the range.

**If reports get too slow**, in order of effort:

1. Work out visits once per dashboard load and share them between the charts, instead of once per report. Done in step 8.3: two to four times faster for a whole page ([dashboard.md](dashboard.md#83-report-endpoints)).
2. Store visits in a table and rebuild only the days that receive new events (`received_at` shows which). A background job then does the sorting, ahead of time.
3. Keep daily totals per page, source, and country for long ranges.

## Heatmaps

Where visitors click on a page, and how far down they read: click maps, scroll depth, rage clicks, and dead clicks, for one page, period, environment, and device class at a time. Built: capture in the browser, storage, the Heatmaps screen, which shows the figures without a picture of the page ([dashboard](dashboard.md)), and [the overlay on your site](#the-overlay-on-your-site), which draws the same data over the owner's live page. Mouse movement is not recorded: the cursor follows the eyes too loosely to say what people look at, and touch screens have none. Code: `packages/tracker/src/heatmaps.ts` and `heatmap-capture.ts` (h.js), `apps/api/src/heatmaps/`.

### Turning it on

Two switches, both needed, as for session replay:

- **The project's setting**, "Heatmaps" on its Install tab: off by default. While it is off, the API refuses heatmap batches (403 `heatmaps_off`), and h.js stops sending for the rest of the page load.
- **The snippet**: `data-heatmaps="on"` on the tracker's tag makes the tracker load `h.js` from beside itself, with the tag's `nonce`, as it loads `v.js`. Not with an `integrity` attribute: `h.js` could not be pinned with it. The dashboard's snippet gains the attribute once the setting is on.

```html
<script
  defer
  src="https://analytics.example.com/t.js"
  data-key="pk_…"
  data-host="https://analytics.example.com"
  data-heatmaps="on"
></script>
```

### Sampling

Every pageview is recorded by default. `data-heatmaps-sample="0.25"` records a quarter of them: the tracker draws a random number for each pageview, an in-app navigation included, and records it when the number is under the sample. Nothing about the choice is kept; a reload draws again. A value outside 0 to 1 warns in the console and records every pageview. `h.js` is downloaded with the first pageview in the sample, so a page outside it costs nothing.

### What is recorded

For each sampled pageview:

- **Each click** (trusted, primary button, with a position; a key's "click" has none), at most **100 per pageview** (`MAX_CLICKS_PER_PAGEVIEW`; later ones are only counted, below), except inside an element marked `data-ottertrail-block` or `data-ottertrail-mask`, session replay's markers ([session replay](session-replay.md#markers-in-the-sites-html)): a click there is not recorded at all, so a PIN keypad's keys or a signature pad never show where they were touched. The markers count anywhere on the click's way, inside open shadow roots too (the event's composed path); a closed shadow root hides its insides, so mark its host:
  - **the element**, as a structural path: tag names, and each one's place among its siblings of the same tag after the first (`body>main>section:2>div>a`). Only standard HTML and SVG tag names are written (`HEATMAP_TAGS`); any other element, a custom element or a made-up tag such as `<user-card>`, is `x`, since a site's own tag names can carry words. A click in a shadow root counts for its host. A click inside a link, a button, a form control, a label, a summary, or an element with a button, link, tab, menu item, checkbox, radio, switch, or option role goes to that element, so a click on a button's icon counts for the button. The path starts at the nearest element named with `data-ottertrail-name` (below), or at `body`; it keeps the nearest 24 steps and at most 512 characters, marked `*>` when cut;
  - **the name**, the nearest `data-ottertrail-name` on the element or above it, when it is 1 to 64 letters, digits, spaces, `.`, `_`, `:`, `/`, or `-`, starting with a letter or digit; another value is ignored;
  - **where in the element** the click fell, as fractions of its width and height (0 to 1, three decimals);
  - **the viewport's width and height and the page's height**, in CSS pixels, and **the device class** from the viewport's width: mobile under 768, tablet under 1024, desktop from 1024;
  - **rage**: the click is the third or later of 3 or more within 1 second and 30 pixels of each other (`RAGE_CLICKS`, `RAGE_WINDOW_MS`, `RAGE_DISTANCE_PX`);
  - **dead**: nothing on the page responded within 1 second of the click's press ([dead clicks](#dead-clicks), below). A click can be both rage and dead;
  - **its minute**: click times are sent and stored to the minute, so the order of a visitor's clicks within a minute cannot be read back. When the batch arrived (`received_at`) is stored to the minute too, floored: no report reads it, and to the millisecond it would set one request's clicks apart from the next's. Reports need only the day. The API rounds each time, after its clock correction, to the nearest minute, so a retry's few seconds' difference stays in the minute the browser sent and on its day, in the minute after midnight UTC too; a clock more than 30 seconds off the time it says it sent can still move a copy to the next or previous minute, and across midnight UTC to another day.
- **One scroll depth**: the deepest point reached, the bottom of the viewport as a share of the page's height at that moment, with the viewport and page height then; the **fold**, the share of the page visible without scrolling when it first showed (the viewport against the page's first height, so a page that grows as it loads keeps its fold); and **the clicks past the 100** of the pageview, counted (`dropped`). It is measured on the frame after each scroll. The first measurement waits two frames: after the load event on a first load, since a deferred script can run before a client-rendered app draws, and after the navigation on an in-app one. A pageview left before it was ever measured sends no depth. After an in-app navigation the new page starts at 0 and is first measured two frames later, once it has rendered (or at its first scroll); the page left keeps the depth it last measured, so a framework that renders the next page before its `pushState` cannot deepen it. It is sent when the page is hidden or left (as time on page is), and when an in-app navigation leaves the page. Hidden again after scrolling further, or after more clicks past the 100, the pageview sends it again with the same ID, which replaces the first; hidden again without, it sends nothing. Its time is the pageview's start, so the row stays on its day. Pages that scroll inside an element report the document's scroll only.
- **The page's address**, cleaned exactly as pageviews' are (origin, path, and UTM tags; the API keeps the path), and the environment and release of the tag. A single-page app's clicks and scroll depth belong to the path they happened on: the tracker tells `h.js` of each new pageview it records.

### Dead clicks

A dead click is a click after which nothing on the page responds within 1 second (`DEAD_WINDOW_MS`). It suggests something looks clickable but is not, or is broken. The second starts at the click's press (`pointerdown`), when the press came less than a second before the click, since many menus, selects, and tabs (Radix, MUI, click-outside handlers) act on the press; a click without a recent press starts it at the click. `h.js` holds each recorded click until the second is over before it queues it, then sends it with `"dead": true` when nothing responded. A click whose press already had a response is settled at once. The per-pageview cap counts the click when it happens, as before, and clicks are queued in the order they happened, a click settled early waiting for those before it.

The page responded if any of these happened in that second:

- **the DOM changed**, anywhere in the document, or in an open shadow root the press or click went through: a `MutationObserver` with `subtree`, `childList`, `attributes`, and `characterData`. Only that a change happened counts; nothing of it is read. Changes inside Ottertrail's own overlay element (`<ottertrail-heatmap>`) do not count. A closed shadow root cannot be seen;
- **the address changed**: an in-app navigation the tracker reports, `hashchange`, `popstate`, or a different address when the second ends;
- **a request started**: a `PerformanceObserver` on `resource` entries whose `startTime` is at or after the press. Of an entry only its address (compared with the instance's origin, that of the tracker's `data-host`), its `initiatorType`, and its start are read. Requests to the instance do not count, nor beacons and pings (`initiatorType` `beacon` or `ping`), which are other tools' analytics leaving;
- **the page scrolled**, or an element in it (`scroll`, in the capture phase);
- **a popover or `<details>` toggled** (`toggle`, in the capture phase);
- **a form refused its input**: a native `invalid` event;
- **the page was hidden or left** (`visibilitychange`, `pagehide`): a click still held then is sent without the flag, since its outcome is unknown.

A click is never dead when it is on or inside a link with an `href`, a form control (`input`, `textarea`, `select`, `option`, `label`, or an element that is `contenteditable`), a popover or command button (`[popovertarget]`, `[commandfor]`), or a media or plugin element (`video`, `audio`, `canvas`, `embed`, `object`), or when it is a single click (`detail` 1) made while the visitor has text selected: these respond in ways the page need not show, such as focus or playback. A double or triple click selects text itself, so it is judged as any other click. They are matched by tag and attribute presence only. The observers and listeners run only while a click is held or a press waits for its click (a second at most), and are disconnected after.

**Known limits:**

- A page that changes all the time, such as a carousel, a ticking clock, or a live counter, changes within the second after almost every click, so its dead clicks are hidden and the count errs low.
- Requests from other tools on the page (polls, chat widgets, analytics that do not use beacons) count as a response when they start in the second.
- A request is seen only once it has finished (resource timing reports it then), so one that takes longer than the second does not count, though it usually changes the page (a spinner) when it starts.
- Some responses leave no trace `h.js` can see: a native dialog (`alert`, `confirm`, `print`) and a menu shown only by CSS (`:focus-within`, `:hover`). Clicks answered that way count as dead.

**Never sent:** text of any element, typed values, `id`, `class`, `href`, `src`, `title`, `alt`, `aria-*`, any other attribute (only `data-ottertrail-name` is read), query strings other than UTM tags, fragments, a visitor ID, or a session ID. Of the page's referrer, only its origin (`https://news.example`) is sent, for the referrer spam check, and it is never stored. A browser test (`packages/tracker/tests/browser/heatmaps.test.ts`, "privacy") runs the tracker and `h.js` on a page full of planted values (a name, an email, a card number, tokens in a link's and an image's addresses and in the page's query string and fragment, an ID, classes, `title`, `alt`, `aria-label`, `data-*`, `placeholder`, `name`, a value, a form's `action`, typed text, a text area, a chosen option, a made-up tag, a custom element, text in a shadow root, an SVG element's attribute, and an email as an invalid `data-ottertrail-name`), clicks every element, a keypad inside `data-ottertrail-block`, and a signature pad inside `data-ottertrail-mask`, types, chooses, scrolls, and hides the page, then checks that none of the values is in anything sent, that no click in the marked elements was recorded, that other tags are `x`, that every time is a whole minute, that the records hold only the fields above, and that nothing was written to cookies or storage. A second case checks that a referrer's path never leaves.

### Naming elements: `data-ottertrail-name`

Structural paths are exact but hard to read, and they change when the page's structure does. A site that wants readable, stable names adds its own to the elements that matter:

```html
<a href="/signup" data-ottertrail-name="hero-cta">Start free</a>
<nav data-ottertrail-name="main-nav">…</nav>
```

The Heatmaps screen lists clicks under the name, with the path from the named element (`main-nav` with `nav>ul>li:3>a`). Name a container to group what is inside it. The name is sent as it is written, so it must never hold personal data: use names of parts of the page, not of people.

### Privacy and consent

Heatmaps follow page analytics: they have no consent switch of their own. Nothing is stored on the visitor's device (no cookies, no storage), and a record carries less than a pageview: no visitor ID, no page text, no address beyond the path. Session replay is different, because it records what was on the screen ([session replay](session-replay.md#waiting-for-consent)). The planned analytics opt-out will cover heatmaps too. This is not legal advice: a site's privacy notice should say it measures clicks and scrolling.

### Sending

`h.js` batches its records: they wait up to 5 seconds, or until 50 are waiting, and go in one request of at most 50 records and 60,000 bytes (`MAX_BATCH_BYTES`, under the API's 64 KiB), each page's URL and referrer once per request. These requests are not `keepalive`: a browser lets a page's beacons and keepalive requests carry 64 KiB at once, which the sends as the page closes need. When the page is hidden or left, what is waiting goes by `sendBeacon` (or, if the browser refuses one, a `keepalive` fetch), as the tracker's events do, at most 16,000 bytes in all (`MAX_EXIT_BYTES`): a browser lets a page's beacons and keepalive requests carry 64 KiB at once, and the tracker's own exit beacon needs its share. Beyond it the oldest clicks are dropped first. Retries follow the tracker's rules: 429, 5xx, and no answer are retried with the same records and IDs, after `Retry-After` or the tracker's backoff (a batching timer set meanwhile does not cut the wait short), 8 attempts at most; other answers drop the batch; a 403 (heatmaps off, an unknown key, a site not allowed) stops `h.js` for the page load. While a `Retry-After` wait runs, hiding the page sends nothing (the queue waits for the send after it), and leaving it loses what waits. At most 200 records wait.

### The API

`POST /api/heatmaps`, as `text/plain` JSON:

```json
{
  "v": 1,
  "key": "pk_…",
  "sentAt": 1794823396705,
  "environment": "staging",
  "release": "1.4.2",
  "pages": [{ "url": "https://example.com/pricing", "referrer": "https://news.example" }],
  "records": [
    {
      "id": "<UUID>",
      "type": "click",
      "at": 1794823380000,
      "page": 0,
      "label": "hero-cta",
      "element": "section>a",
      "x": 0.25,
      "y": 0.5,
      "rage": true,
      "dead": true,
      "vw": 1440,
      "vh": 860,
      "ph": 4200,
      "device": "desktop"
    },
    {
      "id": "<UUID>",
      "type": "scroll",
      "at": 1794823380000,
      "page": 0,
      "depth": 0.62,
      "fold": 0.2,
      "dropped": 0,
      "vw": 1440,
      "vh": 860,
      "ph": 4200,
      "device": "desktop"
    }
  ]
}
```

- **Limits** (Fastify's schema, then the route): 64 KB body; 1 to 50 pages and 1 to 50 records, each record's `page` one of the batch's pages; a UUID ID; `at` and `sentAt` times; URL and referrer at most 8,192 characters, the path at most 2,048, http or https on an allowed hostname; `element` the path's grammar above (only the standard tag names and `x`, `:n` places, `>`, at most 24 steps and 512 characters, so no class, ID, text, or site's own tag fits); `label` the name's rule; `x`, `y`, `depth`, and `fold` 0 to 1; `dropped` 0 to 65,535; `rage` and `dead` booleans, only on clicks; viewport sides 1 to 16,384 and page height 1 to 1,000,000 pixels; `device` one of the three, and the one the viewport's width gives. A click needs `element`, `x`, and `y` and has no `depth`, `fold`, or `dropped`; a scroll record needs `depth` and `fold` and has no click fields. Times are stored to the minute. Unknown fields are removed. A batch that breaks a rule stores nothing (400; 413 over 64 KB).
- **Checks, in order**: requests per client IP (120, then 2 a second), the schema, records per client address (400, then 40 a second), the key, the `Origin`, the project's setting (403 `heatmaps_off`), then accepted and not stored (202, counted in the Activity tab): blocked addresses, bots and data centers, referrer spam ( a batch with one page from a spam referrer is not stored at all, its other pages and records included, as for events); then the budgets; then each record's rules and clock correction (more than a day old: not stored).
- **Budgets of their own**, apart from events', so heatmaps never crowd them out: 2,000 records, then 100 a second, per project; 6,000, then 300 a second, for the instance. Provisional, until measured on real sites.
- **Acknowledged after ClickHouse has written** the batch, in one asynchronous insert waited for, as events are; 503 `storage_unavailable` while it cannot, with the budget given back, or after 10 seconds. Requests in progress are capped as events' are, at 64 per API process (503 `busy`) and 16 per project (429). 202 answers `{ "received" }`, the batch's number of records, whatever became of them, as for events.
- **Retries are the same rows:** the table keeps one row per project, day, and record ID (with the page, device, and kind, which a retry shares), as events do; reports read with `FINAL`. A scroll depth sent again deeper, or with more dropped clicks, replaces the earlier ([ClickHouse](clickhouse.md#heatmaps)).

### Kept 90 days

Heatmap rows are kept a fixed 90 days, whatever the project's event retention: ClickHouse drops each day past it (TTL), and the reports read at most the last 90 days. Older clicks describe an older layout. Deleting a project deletes its heatmaps with its other ClickHouse rows; the orphan sweep covers them too. Deleting spam visits does not reach heatmap rows, which have no visitor ID; they leave with the 90 days.

### Reports

Two routes in the Web analytics area at view ([access](access.md)): `GET /api/projects/:id/heatmaps/pages` lists the pages with heatmap data in a period (most records first, sampled pageviews and clicks together, so a page whose scroll depths have not arrived yet is listed; 100 at most, searchable by part of the path), and `GET /api/projects/:id/heatmaps?path=…` gives one page's report for a period, environment, and device class (or all):

- **totals:** sampled pageviews (those that sent a scroll depth), clicks, rage clicks, dead clicks, the median scroll depth (interpolated between the two middle pageviews), the share that reached the bottom, and the clicks not recorded past 100 on one pageview;
- **scroll reach:** in steps of 10% of the page's height (10%, 20% … 100%), the share of pageviews whose deepest point reached it, and the average fold: the share of the page visible without scrolling, as each pageview first showed;
- **the most-clicked elements** (100 at most): name or path, clicks, their share of all the page's clicks in the period (not of its pageviews), rage clicks, dead clicks, and the average place in the element;
- **rage-click hotspots** (`hotspots`, 20 at most): the elements with the most rage clicks, and where in them;
- **dead-click hotspots** (`deadHotspots`, 20 at most): the elements with the most dead clicks, and where in them;
- the page's pageviews on each device class.

Both also answer `siteHostnames`, the project's allowed hostnames, where "Open on your site" can open the page: a member with Web analytics sees them here, though not in the project's settings.

A range wholly before the 90 days kept answers empty, with `clipped`; a range reaching into them is cut to their first day. Every query filters by project first, then the range, the environment, and the page, passes every value as a parameter, and has a `LIMIT` or returns one row. One page's report reads with `FINAL`; the page list, which reads every page of the project over up to 90 days, reads without it, and counts distinct record IDs, so a scroll row sent again or a retried record counts once; each day's parts merge once they are an hour old. They run with the dashboard's limits (15 seconds, 300 MB) within its shared limit of queries at once.

### The overlay on your site

"Open on your site" on the Heatmaps screen opens the page on the site itself, in a new window, with the heatmap drawn over it for the person who pressed it ([dashboard](dashboard.md#heatmaps)). The overlay draws on the page as it is now, with its real text, in the owner's own signed-in view. Nothing is stored about how the page looks unless the owner presses "Save this view", which saves a snapshot of the page from their own browser ([saved views](#saved-views)). Visitors' pages are never stored. Code: `packages/tracker/src/overlay.ts`, `overlay-view.ts`, and `overlay-draw.ts` (o.js), `heatmap-path.ts` (element keys, shared with capture), `apps/api/src/heatmaps/overlay-routes.ts`, `apps/api/src/access/overlay-tokens.ts`.

**How it opens:**

1. The dashboard asks for a link token (`POST /api/projects/:id/heatmaps/overlay-link`, Web analytics at view, from the dashboard's own origin, 20 a minute per user), only when the button is pressed, and opens `https://<hostname>/<path>#ottertrail-heatmap=<token>`.
2. The tracker on the page sees the fragment as it starts. It removes it with `history.replaceState` (the rest of the address stays) and loads `o.js` from beside itself with its `nonce`, as it loads `v.js`. Anyone can put a fragment on a link to the site, so the page load is recorded as for any visitor (the page's stand-in and its queued calls, a signed-in user, errors, the landing path), with the tracker paused: its events wait in its own queue (its first 200 kept), nothing is sent, and `v.js`, `r.js`, and `h.js` are not loaded yet, until `o.js` answers:
   - **a real link**: the queue is dropped, and nothing at all is sent for the rest of this page load, a return from the back/forward cache included (no pageviews, custom events, errors, Web Vitals, replays, or heatmap clicks: the owner's look is not counted). A second copy of the tracker on the page does nothing either;
   - **anything else** (a token the server never made, a link used up, an account without access, the server busy or failing, `o.js` failing to load, which settles at once, or not answering within 5 seconds, or a tag with `integrity`, which cannot load `o.js`): the tracker resumes and sends its queue at once, each batch written as it leaves (its `sentAt` then, so the API's clock correction keeps each event's time), the waiting scripts load, and the page load carries on as usual.
   - **the page hidden or left first**: the tracker resumes and its own exit sends the queue, by beacon with its fetch fallback, once; the scripts still wait for the answer (or the 5 seconds), and a real link that answers then mutes the rest of the page load.
   - **a real link that answers after the 5 seconds**: what was sent stays sent, and nothing more is. The tracker drops its queue, the replay recorder (`r.js`) and the heatmap capture (`h.js`), when they already started, stop and drop what they hold (an error after it carries no replay, and the clicks and scroll depth are not sent as the page closes), one still loading stops as it runs, `replay(true)` starts nothing, and scripts that have not loaded never do. An `h.js` from before this change, still in the browser's cache (up to an hour), has no way to be stopped, so on that page load it keeps sending the owner's clicks and scroll depth.
3. `o.js` exchanges the link for a session token (`POST /api/heatmap-overlay/session`), kept in memory only, and reads the page's heatmap with it (`GET /api/heatmap-overlay/:projectId/heatmap?path=…&device=…&period=…`, the session as `Authorization: Bearer`). It reads the environment of the tracker's tag (`data-environment`), production without one. One exchange is in flight at a time, shared by every read that waits for it; an answer for an earlier choice of period or device is dropped.
4. It draws on a canvas in a fixed layer over the whole window, inside a closed shadow root, so the page's styles and scripts cannot reach it. The layer lets every click and scroll through (`pointer-events: none`); only the panel takes clicks.

**What it draws:**

- **Clicks**: each element the API names is found on the page by its key (its structural path and name, as capture wrote it; `resolve()` in `heatmap-path.ts` accepts an element only when `describe()`, the function capture uses, gives it the same key, so capture and lookup cannot drift). Over each element found, a thin outline (red with rage clicks, amber with dead clicks only), its clicks (and rage and dead clicks) as a label, and a blob for each cell of an 8 by 8 grid of the element's box that had clicks: larger and hotter for more. The positions are the grid's cells, not single clicks.
- **Scroll reach**: a band down the right edge of the window, each 5% of the page's height shaded by the share of pageviews that reached it, with the share written every 25%.
- **The panel** (keyboard reachable, with a visible focus ring; × closes it and removes the overlay, as Escape does inside the panel): the page's path, the period (7, 30, or 90 days), Desktop / Tablet / Mobile (at first the class of the window's width: under 768 pixels mobile, under 1024 tablet, else desktop), the totals (pageviews, clicks, rage clicks, dead clicks), and "Not on this page": the elements the page does not have, with their clicks. "Save this view" saves a snapshot of the page for the Heatmaps screen ([saved views](#saved-views)); for a member, who cannot save one, the panel shows "Only the owner and admins can save a view." in its place. A note says that only you see the overlay and the visit is not counted: Ottertrail does not count it, though scripts of the page may (below).

It draws again, at most once a frame, when anything scrolls or the window or page resizes, and finds the elements again, at most once a second, when elements are added or removed or a `data-ottertrail-name` changes. Keys come from visitors' pages, so finding them is bounded: each pass spends at most 50,000 units of work (`RESOLVE_BUDGET`): one for each element examined (a candidate, a child walked down to, an ancestor walked up to), each step looked up or compared, and each sibling counted when a step is first worked out; each element's step is worked out once per pass, with its siblings', and a cut key is matched from its last step upward. Keys left when the budget is spent are listed as not on this page. An element shown, hidden, or moved by a change of its `class`, `style`, `hidden`, or `open` attribute (a tab, a menu, a dialog) is redrawn within a fifth of a second, without looking for the elements again.

**Its states.** Nothing shows until the server has answered about the link, and only for a link it knows. Then: loading; the link expired or was already used ("Open it again from the dashboard"), only for a link the server still knows (made, then used or past its 5 minutes, within the day it is kept); no access (the account cannot view this project's heatmaps, or lost the right); the session ended after 30 minutes; nothing recorded for this page on this device and period; and a failure of a read, with Retry, which reads again with the session. A token the server never made, an answer refusing this site, the server busy (429) or failing (5xx), and no readable answer at all show nothing: the link may never have been one, so the owner opens it again from the dashboard. The link is sent once per page load. When the overlay answers after the tracker has stopped waiting (5 seconds), the visit has been counted, and the panel leaves out its note that it is not.

**Security:**

- **Tokens.** The link and the session are each 32 random bytes, kept only as their SHA-256 hash, as invitations are, bound to the user, the project, the scope `heatmap:overlay` (migration 0026 renamed it from `heatmap:read`, as a session may also save), and the dashboard session that made the link: signing out, a password reset, or that session's end ends them too ([access](access.md#heatmap-overlay-tokens)). The link works once and for 5 minutes; the session lasts 30 minutes from the exchange. Every read and save checks the user's role and grants again, as the dashboard's routes do, so a removed member, a revoked grant, or a deleted project fails on the next read. A save also checks the session, its expiry, and its dashboard session again when it looks up the session's page.
- **The fragment** is never sent to a server, and browsers strip it from `Referer`. The tracker removes it from the address and the history entry as it starts.
- **Scripts of the page can read the link and the session.** The overlay runs inside the site's own page, beside the site's other scripts, and nothing in a page can keep a secret from a script that runs there first or changes what the overlay relies on. Ottertrail narrows what a script can get without trying:
  - A script that runs before the tracker (which is deferred) can read the link from the address.
  - The tracker never puts the link on a DOM node, where a `MutationObserver` could read it as `o.js` is added. The `o.js` element carries only a function, which hands the link over once, and only while `o.js` itself is the running script. It asks the browser through `Document.prototype`'s own `currentScript` getter, taken when the tracker starts, so a later script that shadows `document.currentScript` to point at the `o.js` element gets nothing either. A script that calls it at any other time gets nothing. `s.js` hands its snapshot function back to `o.js` the same way.
  - `o.js` sends its requests with the page's `fetch` as the tracker found it when it started, so a script that wraps `fetch` after that never sees the link or the session.
  - A script that ran before the tracker, or that replaces `Document.prototype`'s `currentScript` getter or `fetch` before the tracker starts, can still read the link or the session, and act as the overlay with them.

  Single use limits what a stolen link can do: either the owner used it first, or the owner's overlay fails visibly ("already used").

- **CORS.** An answer is readable by a page only once its project is known (from the link, or the read's address) and the page's `Origin` is one of that project's allowed hostnames, on any port, over `https:`; plain `http:` only for `localhost`, names under `.localhost`, and `127.0.0.1`, which browsers treat as secure contexts (collection takes either scheme; the overlay's routes do not): the session and the heatmap, the read's preflight, and the refusals that follow (a link used up, no access, a session ended), so the overlay can say why. An answer before the project is known (a rate limit, a malformed or unknown token) is readable by none; the overlay shows nothing for it. Never with credentials, and no cookie is read or set. No answer may be cached: each says `Cache-Control: no-store`. The `Origin` check binds the links to the project's sites only in a browser: a script outside one can send any `Origin` it likes.
- **What a leaked link or session exposes**, at worst: one project's heatmap aggregates (clicks per element in the grid, scroll reach, totals) for 30 minutes, for as long as the user who made it may view them and stays signed in. Nothing about any one visitor, no keys, settings, events, or replays. When that user is the owner or an admin, whoever holds it can also save a view of the link's page in their name, replacing the one saved before: a page they made up, shown only in the player's sandbox ([saved views](#saved-views)). Leaks come from the page's own scripts (above), and from redirects: A link leaks where its page sends the browser elsewhere before the tracker runs: browsers keep the fragment across a redirect, so a page behind a login that redirects to an identity provider, or a path of the site that redirects to another site, hands the link to that site. Whoever uses it first gets the session, and the owner's overlay then says the link was already used.
- **The public key** plays no part: it never allows a read. The overlay's routes take no key, and refuse any field they do not use (a key or a token in the address answers 400).
- **Limits.** Links per user: 20, then 20 a minute (429). Per client address (an IPv6 address by its /64): exchanges, 10, then one every 30 seconds; reads and preflights, 60, then one a second; saved views, 10, then one every 10 seconds. A request whose token has the wrong form (an exchange's body that is not JSON or whose token is not 43 base64url characters, a read or save without a Bearer of that form) or a save without an `https:` `Origin` (or `http:` on this computer) or a `Content-Length` of at most 5 MB spends a bucket of its own: 30, then one a second, not the owner's exchanges, reads, or saves. Only the token's form is checked there: a script on the owner's page that sends made-up tokens of the right form still spends the owner's buckets. A malformed body, query, `Origin`, or `Authorization` is refused before any database work, and a save's `Origin`, Bearer, and `Content-Length` are checked before its body is read.
- **Drawing.** Everything from the API is drawn as shapes or set as text (`textContent`, the canvas's `fillText`), never parsed as HTML, and the answer is checked and capped (200 elements, 64 cells each) before use. Styles go in a constructed stylesheet, or, where a browser has none, a `<style>` with `o.js`'s nonce.
- **No overlay** where the tracker's tag has an `integrity` attribute (`o.js` cannot be pinned with it; the page load is recorded as usual), or where the page requires Trusted Types for scripts (the tracker records the page load once its 5 seconds are up). The Heatmaps screen works there.

**The API's answer** for one page, device, and period (7, 30, or 90 days, cut to the 90 kept), every query project first and with `FINAL`: `totals` (pageviews, clicks, rage clicks, dead clicks), `devices` (pageviews per device), `reach` (the share reaching each 5%), and `elements` (200 at most, most clicks first: name, path, clicks, rage clicks, dead clicks, and `cells`, `[column, row, clicks]` of the 8 by 8 grid, 3,000 cells at most in all, the busiest first). A link used or expired is kept, as a hash, for a day after it expires, so its page can be told why it no longer works; rows a day past expiry are deleted whenever a token is made. An unknown link answers 410 `link_unknown`, a known one 410 `link_expired`.

**Limits of the overlay:**

- Only the project's allowed hostnames, which have no port: for `localhost`, names under `.localhost`, and `127.0.0.1`, the dashboard asks for the port and uses plain http; every other site opens with https.
- The window opens as wide as the device the report is filtered on (390, 820, or 1280 pixels; 1280 for all devices). Browsers may ignore the size. Devtools' device mode gives exact widths.
- An element the page does not have (a redesign, an A/B test, a block only some visitors see) is listed as not on this page: phase 1 keeps no page positions, so there are no fallback dots for it. Two elements with the same `data-ottertrail-name` and path: the first is drawn.
- Scroll reach is for the document; a page that scrolls inside a box shows the document's.
- Other analytics tools on the page still count the owner's visit.
- A visit opened with a link that proves not to be one is sent up to 5 seconds late; one hidden or left before then is sent as it goes. A real link whose answer comes only after that (the owner switched tabs first) counts what was already sent, then nothing more, and `r.js` and `h.js` never load.
- While the tracker waits, its queue keeps its first 200 events (the pageview among them) and drops later ones. What it then sends as the page closes is bound by the browser's 64 KiB for beacons, as for any visit: very long error stacks from the wait can leave some events out.
- Elements are redrawn as the page scrolls or resizes, when elements come and go, and when a `class`, `style`, `hidden`, or `open` attribute changes. A change none of these reveals (a menu opened by `:hover` alone, a CSS animation or transition) shows its dots where the element was until the next of them.
- Elements inside frames or closed shadow roots, and content drawn on a canvas, are not found: capture records a click in a shadow root on its host.

### Saved views

Decided on 22 November 2026: the heatmap can be read over the page without opening the site. While the overlay is open, "Save this view" in its panel saves a snapshot of the page as the owner's browser shows it at that moment; the Heatmaps screen then draws the click map and scroll depth over it ([dashboard](dashboard.md#heatmaps)), and it stays readable after the live page changes, labelled with when it was saved and by whom. Code: `packages/tracker/src/snapshot.ts` and `snapshot-take.ts` (s.js), the Save control in `overlay-view.ts`, `apps/api/src/heatmaps/snapshots.ts` and `snapshot-routes.ts`, `packages/replay-player/src/snapshot.ts`.

- **Only the owner's and admins' own view.** Saving, replacing, and deleting a saved view needs the owner or an admin (the `projects` permission, decided 23 November 2026); members with Web analytics at view see saved views on the Heatmaps screen, without Delete, and their overlay panel has no Save button ("Only the owner and admins can save a view."; the session's answer says `canSave: false`). Only an overlay session can save one, from the user's own browser, on the page their link opened. The tracker never takes a snapshot of a visitor's page.
- **What is saved:** an rrweb full snapshot (the replay recorder's rrweb, 2.2.2) of the page, with the viewport's width and height and the page's height. Text stays, since it is the owner's page and choice. Typed values are masked (rrweb's `maskAllInputs`, every input type). The snapshot then passes the replay filter with text and media shown ([session replay](session-replay.md#proving-it-the-privacy-test)): no scripts or event handlers, addresses cut to origin and path (an image whose address needs its query string does not load), and `data-ottertrail-mask` and `data-ottertrail-block` apply as in replays. `data-ottertrail-name` stays, since keys start from it. The overlay's own element is left out. A browser test plants typed values, a token in a link, and masked text, and checks none of them is in what is sent.
- **Loaded on demand:** `o.js` loads `s.js` from beside itself, with its nonce, only when Save is pressed, and keeps the session to itself: `s.js` hands the compressed snapshot back and never sees a token. `o.js` takes the function only from `s.js` as it runs, not from another script of the page.
- **Sent** as gzip-compressed JSON (`{"v":1,"events":[…],"pageHeight":…}`) to `POST /api/heatmap-overlay/:projectId/snapshot?path=…` with the session as `Authorization: Bearer`, from the project's site (its preflight too, as for reads). At most 5 MB compressed and 500,000 objects and arrays in its JSON (about three per element, so about 150,000 elements): a larger page is not sent, and the panel says it is too large. The API refuses more than 5 MB (413, from the request's `Content-Length` before the body is read, and again as read), more than 32 MiB unpacked (413), more than 500,000 objects and arrays or 4,000,000 values (413), and objects and arrays nested more than 500 deep (400 `snapshot_too_deep`: the player's rebuild recurses as deep as the page nests, and this allows pages over 200 elements deep), counted in one pass over the text before it is parsed, since memory follows the objects, not the text; it checks one snapshot at a time. The panel says why for each. It refuses anything but that shape (400 `invalid_snapshot`): version 1, one Meta event with the viewport's size, one full snapshot of a document, otherwise only style events, and no other fields. It checks the shape, not the HTML in it, which the player treats as untrusted, as it does replays.
- **One per page and device class:** the device is the viewport's width, with the heatmaps' breakpoints (mobile under 768 pixels, tablet under 1024, desktop from it). Saving again for the same page and device replaces the view and deletes its old object. Stored gzip-compressed, as sent, in the object store under `heatmap-snapshots/<project_id>/<uuid>.json.gz`; PostgreSQL holds one row per project, path, and device (`heatmap_snapshots`, migration 0023): who saved it, when, the viewport's size, the page's height, and the object's key. A user removed leaves the view, saved by no one named.
- **No object store:** the session's answer says so (`snapshots: false`), and the panel shows "Saving a view needs object storage on the Ottertrail server." in place of the button; the API answers 409 `object_store_not_set_up`.
- **Kept** until saved again, deleted on the Heatmaps screen by the owner or an admin, or the project is deleted (its prefix is deleted with its other objects, and the orphan sweep covers a project PostgreSQL no longer knows). Not by the 90 days heatmap rows are kept: the view is the page, not visitors' data. Included in [backups](deployment.md#backups) with the store's other objects.
- **Shown** in the replay player's page and sandbox ([session replay](session-replay.md#playback)): rrweb rebuilds it in a frame sandboxed with `allow-same-origin` only, so scripts never run, under the player page's Content Security Policy ([session replay](session-replay.md#playback)): stylesheets from the project's allowed hostnames and inline (`'unsafe-inline'`), images from the allowed hostnames, `data:`, and `blob:`, fonts from the allowed hostnames and `data:`, and none of them from Ottertrail's own address, so a snapshot cannot send a GET with the viewer's cookie to the API. Scripts and connections are the player's own (`'self'`). The player finds each element of the heatmap in the frame by its key, with the overlay's own `resolveKeys()`, and draws on a canvas over the frame with the overlay's own drawing (`overlay-draw.ts`): outlines, the 8 by 8 cells, the labels, and the scroll bands. The view scrolls; links and forms in it do nothing. It sends the dashboard the elements it did not find, which the screen lists as "Not on this snapshot".

**Limits of saved views:**

- A snapshot is the page as it was: once the page changes, elements of newer clicks are listed as not on it. Save again to replace it.
- Stylesheets, fonts, and images load from the site when the view is shown; one from another hostname, or one the site has removed since, is missing.
- Content in frames, on a canvas, or in closed shadow roots is not in it, as in replays.
- Heights in viewport units (`100vh`) follow the saved viewport's height, which the view keeps.
