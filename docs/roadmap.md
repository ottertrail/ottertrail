Status: stage 1 (web analytics) is built and being checked; see the step table in [web-analytics.md](web-analytics.md). Of stage 0, instance settings with one access check, projects, public keys, the browser tracker, and a deployment template ([deployment.md](deployment.md), tested locally) exist. Events go straight to ClickHouse since 18 November 2026, confirmed once it has written them, and reports read them there, with retention, deletion, and backups ([clickhouse.md](clickhouse.md)). Environments and releases exist for analytics events: a site names them in its snippet, and reports show one environment at a time ([web analytics](web-analytics.md#environments-and-releases)). Known users exist too: a site names its signed-in user, optionally signed by its server, and the Users pages list them with their activity; a site's server can send its own events with the project's secret key ([web analytics](web-analytics.md#known-users)). Browsers in data centers are ignored as bots ([web analytics](web-analytics.md#data-centers)). Of stage 2, browser errors exist: captured by the tracker, grouped, with counts, affected users, first and last seen, and a resolved status ([errors](errors.md)), and source maps a site uploads turn their stacks back into its own code ([errors](errors.md#5-source-maps)). Session replays of the minute before an error exist too, masked in the visitor's browser before anything is sent, with a Replays page that lists and filters them, a timeline of the visitor's pages, clicks, and typing beside the player, and a user's replays on the user's page ([session replay](session-replay.md)). Web Vitals exist too: measured on each page load with Google's library and shown on a Speed page ([web analytics](web-analytics.md#web-vitals)). Product analytics exists: product events with property breakdowns and filters, one ordered funnel that can be saved by name, one retention report, and saved goals counted on the analytics page, with their definitions written down first ([product analytics](product-analytics.md)). Stage 3's features are built: servers' traces, logs, and metrics are received over OTLP and stored in ClickHouse, their exceptions join the error list, the Traces, Logs, Metrics, and Services pages show them, the Databases pages show the database calls inside traces by query shape, the slowest first by time spent ([telemetry](telemetry.md#databases)), and the Hosts pages show each server's CPU, memory, filesystems, network, disks, and load from an OpenTelemetry Collector's host metrics ([telemetry](telemetry.md#hosts)); its last step, trying it in a deployment, waits for the hosting work. Stage 2 is built. Of stage 4, uptime checks exist: the worker requests each check's URL on its schedule, refusing private addresses, and the Uptime pages show each check's state, uptime, response time, and incidents; the channels alerts go to exist too, email over SMTP and signed webhooks, delivered and retried by the worker and managed on the Settings page; and alert rules exist, on a check going down, a certificate about to expire, new, regressed, and spiking errors, a route's latency or failed share, and a metric above or below a value, evaluated by the worker and managed on each project's Alerts page; stage 4 is complete ([uptime and alerts](uptime-alerts.md)). Stage 5's features are built, within the decision of 18 November 2026 that replays stay error-only and whole sessions are not recorded ([session replay](session-replay.md#decisions-still-open)); it is not yet tried on a real site, and its budgets wait for one's recordings. Roles exist: an owner, admins, and members with access per area and project, checked by the one access check on every route, with invitation links, a Members page, and reset links ([access](access.md)). Signing up for the hosted service (which creates the customer's instance), and a deployment in production do not exist yet.

## How stages are chosen

Ottertrail replaces the separate tools a small software team runs beside its app: web and product analytics, error tracking, and monitoring (traces, metrics, logs, uptime, and alerts).

Each stage either replaces one of those tools or adds a missing capability. A stage is complete when it can replace the tool it targets for a real production app, not when the first version ships.

Not Ottertrail's job: hosting, the app's database, CI, DNS, captchas, backups, the support inbox, AI APIs, and email: no campaigns, mailing lists, or email analytics (decided 17 November 2026). Ottertrail sends only its own account email, such as sign-up verification and password resets, and alert notifications.

## Next in stage 0

In this order, so that later work builds on the final model:

1. **One customer per instance.** Built, except open sign-up ([dashboard.md](dashboard.md#settings), [access](access.md)). An instance holds projects; one server-side check guards every project route. The instance's name and timezone live in its settings, which the owner changes on the dashboard. The hosted service gets open sign-up, which creates the customer's instance; a self-hosted install keeps today's one-time owner setup link. Roles, access per area, and invitations are built ([access](access.md)).
2. **Events in ClickHouse.** Done, in four steps ([clickhouse.md](clickhouse.md)): ClickHouse is in the stack with settings for an 8 GB server, the worker copies events there, reports read them there, and retention, project deletion, and backups cover it. Since 18 November 2026 events go straight to ClickHouse, as telemetry does; PostgreSQL no longer holds them. Still to decide: whether visits are worked out when events arrive or when reports run, as now (the [benchmark](storage-benchmark.md) found query-time visits need memory as data grows).

## Notes

- One instance per customer (decided 18 November 2026): the hosted service gives each customer an instance of their own, the same image as self-hosters run, so no customer can slow another. Provisioning instances (servers, backups, DNS, upgrades) is separate work, not built.
- Access model ([access](access.md)): an owner, admins, and members per instance, each member with access per area and project. Built: the roles, grants, and checks, invitations, the Members page, and reset links.
- When replacing a tool, run the old and new side by side and compare their numbers. The OpenTelemetry Collector can export to both at once.
- Traces and logs are the highest-volume data. They go to ClickHouse, ordered by project and time, with retention by dropping old partitions. The instance's volume and each project's are limited so one project cannot crowd out the others.
- Something outside Ottertrail must monitor Ottertrail itself: keep at least one independent health check.
- Retention and the activity timeline belong in stage 2 because they need identities. The anonymous visitor ID changes every day by design ([web-analytics.md](web-analytics.md#one-salt-per-timezone-and-day)), so "came back a week later" can only be counted for users the app identifies.
- Session replay was planned last: recordings are much larger than events and hold whatever is on screen, so they need masking, per-project opt-in, and storage limits. Its most useful view, the moments before an error, needed stage 2 first, and it was built before stages 3 and 4: its first version, replays around errors, private by default ([session-replay.md](session-replay.md)).
- Later, not scheduled: AI usage tracking (tokens, cost, and latency per user and feature).
- Not planned: click heatmaps (they need the page layout at each screen width, in practice the session replay recorder; reconsider with stage 5), scroll depth (could be added to the time-on-page report if asked for), and reports from ad and search platforms.
