# Where data is stored

Every place Ottertrail keeps data, and how long, checked against the code on 23 November 2026. The public docs site has the same table for operators ("Where data is stored" under Reference). When retention or storage changes, update both.

## ClickHouse

Tables in `apps/api/src/clickhouse/migrations.ts`. A deleted project's rows go from every table within a minute (`clickhouse/delete-events.ts`, the purge after `project_deletions`).

| Table                                                 | Holds                                                                                                                                                            | Kept                                                                                                                                                     | How it goes                                                                                                                                                                                                                                                                              |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events`                                              | Pageviews, custom events, server events (`POST /api/server-events`), browser errors, exceptions from OTLP spans and logs (`telemetry/exceptions.ts`), Web Vitals | The project's `retention_days`: none (forever) by default; the dashboard offers 6 months and 1, 2, or 5 years, the API any number from 30 to 3,650       | The worker, at start and 6 hours after each run (`retention/retention.ts`): a lightweight delete to a midnight in the instance's timezone, taken off the disk later by `APPLY DELETED MASK`                                                                                              |
| `ai_calls`                                            | One row per LLM call: model, tokens, latency, status, user, conversation, feature, trace and span IDs. No prompt or response text.                               | As the project's events, including calls found in spans                                                                                                  | The same worker job (`delete-events.ts`)                                                                                                                                                                                                                                                 |
| `user_first_seen` (and its view `user_first_seen_mv`) | When each signed-in user was first seen                                                                                                                          | No limit of its own                                                                                                                                      | Rebuilt from the events left after a retention or spam delete; the rebuild waits while ClickHouse's disk has under 7% free                                                                                                                                                               |
| `heatmaps`                                            | Clicks by element, scroll depth                                                                                                                                  | 90 days (`HEATMAP_RETENTION_DAYS`)                                                                                                                       | TTL                                                                                                                                                                                                                                                                                      |
| `spans`, `logs`, `metric_points`, `metric_histograms` | Traces, logs, metrics, as sent                                                                                                                                   | The project's `telemetry_retention_days`, 1 to 365, at most `TELEMETRY_RETENTION_DAYS` (30 by default, 1 to 365, `config.ts`), which is also the default | TTL at `TELEMETRY_RETENTION_DAYS`, whole days (`ttl_only_drop_parts`); `migrate` changes the TTL when the variable changes (`clickhouse/migrate.ts`). For a project that keeps fewer days, the worker's retention run: a lightweight delete to a midnight UTC (`retention/retention.ts`) |
| `check_results`                                       | Each uptime check's runs                                                                                                                                         | 90 days                                                                                                                                                  | TTL; a deleted check's results stay until then                                                                                                                                                                                                                                           |
| `schema_migrations`                                   | Applied migrations                                                                                                                                               | For good                                                                                                                                                 |                                                                                                                                                                                                                                                                                          |
| `system.query_log`                                    | Every query and insert, ClickHouse's own                                                                                                                         | 7 days                                                                                                                                                   | TTL in `deploy/clickhouse/config.d/ottertrail.xml` (also inline in `deploy/compose.yaml`)                                                                                                                                                                                                |
| `system.backup_log`, `system.crash_log`               | ClickHouse's backups and crashes                                                                                                                                 | 30 days                                                                                                                                                  | TTL, the same file                                                                                                                                                                                                                                                                       |

The same file switches off the internal logs Ottertrail never reads. ClickHouse keeps its other logs forever by default, so any log turned back on needs a TTL too.

An exception from a span or a log record is kept twice: as an error event, for the event retention, and inside its span or log record, for the telemetry retention.

With the tracker's `data-traces="on"`, a page load's events keep its server trace's IDs, and a browser error keeps the page's last 5 traced requests before it: method, path without query string, status, duration, and trace ID, never headers or bodies ([web analytics](web-analytics.md#traces)). They go with the event, for the event retention.

## The object store

S3-compatible: Garage on the same server by default, or R2 or S3 ([deployment](deployment.md#session-replays-and-source-maps)). Prefixes are listed in `OBJECT_PREFIXES` (`backups/settings.ts`).

| Prefix               | Holds                                                                   | Kept                                                                                                                                                                                                                                  |
| -------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `replays/`           | Joined session replays                                                  | 30 days (`REPLAY_RETENTION_DAYS`, fixed), deleted by the worker every 6 hours with their row; also when replay is turned off for the project, by spam deletes, and with the project. Budget `REPLAY_STORAGE_BYTES`, 2 GiB by default. |
| `source-maps/`       | Uploaded source maps                                                    | Until the release is deleted, the same file is uploaded again, or the project is deleted. No age limit: when `SOURCE_MAP_STORAGE_BYTES` (1 GiB by default) is full, uploads are refused.                                              |
| `avatars/`           | The instance icon, users' avatars, project icons, fetched site favicons | Until replaced or removed. A removed member's and a deleted project's are deleted; a failed delete of a member's is logged and the file stays.                                                                                        |
| `heatmap-snapshots/` | Saved heatmap views                                                     | Until saved again, deleted, or the project is deleted                                                                                                                                                                                 |

## What is not kept

- **Visitors' IP addresses.** Collection uses them in memory for the location, the daily visitor ID, and rate limits, and writes none. Three ways an address can still be stored: addresses an admin types into Blocked addresses; OTLP attributes, which are stored as sent (an app's `client.address` lands in `spans` or `logs`); and whatever a sender puts in event properties, error messages, or log bodies.
- **AI prompts and responses.** `POST /api/ai-calls` has no field for them and drops unknown fields. From OTLP, they are dropped under a fixed list of attribute names, prefixes, and GenAI log events (`telemetry/ai-content.ts`: the OpenTelemetry GenAI conventions, Vercel AI SDK, OpenLLMetry, OpenInference). Text under any other name, in a log body, or in an exception message is stored.
- **Page content, except as chosen.** Heatmaps keep no text: the path, the device, `data-ottertrail-name`, an element path, and positions. Session replays record pages around errors only in "Around errors" mode, masked unless the site unmasks text or media. A saved heatmap view keeps its page's text (typed values masked), only when a user with Web analytics access saves one.

## Deleting one user's data

For erasure requests, an owner or admin can delete everything Ottertrail stores about one known user of a project: Delete data on the user's page ([dashboard](dashboard.md#85-users)), or the app's server with the project's secret key (`POST /api/user-deletions`, [web analytics](web-analytics.md#deleting-a-users-data)). Either records a row in `user_deletions` and answers 202. Every minute the worker takes up to 100 due rows (`FOR UPDATE SKIP LOCKED`, leased for 15 minutes), deletes the data of each project's users together, then clears the user ID from the row; the row keeps when it was asked for and by whom. A failure waits a minute, doubling up to an hour, and is tried again until it succeeds. Code: `apps/api/src/identities/deletions.ts`.

What goes, for the project and the user ID. Nothing of other users goes, except in a shared replay (below), and nothing of the same ID in another project:

| Store                                  | What                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events`                               | Every event with the user ID: pageviews, custom events, server events, browser errors, server exceptions (`user.id` or `enduser.id` on the span or log), Web Vitals, time on page                                                                                                                                                                                                                                         |
| `ai_calls`                             | Calls with the user ID                                                                                                                                                                                                                                                                                                                                                                                                    |
| `user_first_seen`                      | The user's first-seen times                                                                                                                                                                                                                                                                                                                                                                                               |
| `spans`, `logs`                        | Spans and log records whose attributes hold the ID under `user.id` or `enduser.id`, the names Ottertrail reads it from. No index finds an attribute's value, so finding them reads the project's whole tables: these two deletes are queued for ClickHouse to run in the background (`lightweight_deletes_sync = 0`), not waited for or counted, so a project with much telemetry cannot outlast the request's time limit |
| `replays`, `replay_chunks`, `replays/` | Replays linked to the user, and those whose error event has the user ID: their objects first, then their rows and chunks. A replay is one browser session and is deleted whole, so when another user signed in later in the same session, their part of it goes too                                                                                                                                                       |

Reports, funnels, retention, an error's affected users, and the Users pages are worked out from these when asked, so the user leaves them at once. ClickHouse's deletes are lightweight (filtered by `project_id` first): reads, `FINAL` included, stop seeing the rows at once, since every copy of a retried event holds the same user ID. The rows leave the disk with the worker's next `APPLY DELETED MASK`, within 6 hours ([ClickHouse](clickhouse.md#retention-and-deleting-a-project)).

What does not go:

- **Events sent after the deletion.** They are stored again, under the same ID. The app must stop sending events for the user (and stop naming them in spans and logs) before asking.
- **Anonymous events.** Events without the user ID, even those of the same visit before the user signed in, are kept. They carry only a daily visitor ID, which is not linked to a person and may be shared by others on the same network and browser, so they cannot be found by name. The same holds for any anonymous visitor: there is nothing to delete them by.
- **The ID anywhere else.** In event properties, error messages and stacks, log bodies, other attribute names, resource attributes, span events, metrics, and the other spans of a trace. Searching free text for an ID could also match other people's data, so it is not done.
- **Heatmaps.** They hold no user or visitor ID: there is nothing to tie a click to a person.
- **What names an error, not a person:** error resolutions and assignments, alert history, notifications and their deliveries. A notification may quote an error's message, which the app may have filled with the ID; it goes after 30 days (deliveries) or 90 (inbox).
- **Backups.** Scheduled backups and `backup.sh`'s files keep the data until they expire or are deleted ([deployment](deployment.md#scheduled-backups)). A restore from an older backup brings the user back; ask for the deletion again after one.
- **ClickHouse's own records of the statements.** Queries are logged with their values in `system.query_log` (7 days), and each table keeps the text of its last 100 finished changes, the deletion's `DELETE` among them (`system.mutations`). Both hold the user ID until they roll over.
- **A failed attempt's error,** in `last_error` until the deletion succeeds, and in the worker's log. Both have the user IDs replaced with `[user ID]`, as written and as ClickHouse quotes them, since some ClickHouse errors quote the query with its values.

## Known gaps

Rows that grow with use and are never pruned by age: expired `dashboard_sessions` that are never signed out, `uptime_incidents` while their check exists, and `alert_error_groups`, `error_resolutions`, and `error_assignments` after their errors leave the event retention. All are small. `replay_chunks` can pile up if the worker has no object store while the API has one, or while the store keeps refusing with an error that may pass.
