# Uptime checks and alerts

**Status: stage 4 of the [roadmap](roadmap.md), complete. Steps 1 to 4 are built: uptime checks ([what was built](#step-1-uptime-checks-as-built)), the channels alerts go to and their delivery ([what was built](#step-2-channels-and-delivery-as-built)), alert rules on checks, certificates, and errors ([what was built](#step-3-alert-rules-as-built)), and alerts on telemetry ([what was built](#step-4-alerts-on-telemetry-as-built)).**

Ottertrail checks that a customer's sites and APIs answer, from outside the servers they run on, and tells the team when something breaks: a check that fails, an error never seen before or come back after being resolved, a sudden rise in errors. Alerts go out by email and by a signed webhook. The choices below were made on 18 November 2026.

## Uptime checks

A check is an HTTP(S) request a dashboard user sets up for a project: a URL, `GET` or `HEAD`, how often (every 1, 2, 5, 10, 15, 30, or 60 minutes), a timeout (10 seconds by default, at most 30), the status codes that count as up (200 to 399 by default), and optionally a word the body must hold, or must not. Redirects are followed, at most 5.

- **Where checks run:** in the worker of the customer's own instance, from one location. That is outside the servers the customer's app runs on, unless they host it on the same machine. If the instance itself is down, its checks are too: the instance needs a monitor of its own outside it, a hosting task.
- **Down and up:** a check is down after it fails twice in a row (1 to 5, set per check), so one lost packet does not page anyone, and up again after one success. Each time down is an incident, with when it started and ended and the first failure's cause (timeout, refused connection, DNS, TLS, status code, missing word).
- **TLS:** each HTTPS check records when its certificate expires; an alert can warn a set number of days before (14 by default).
- **Scheduling:** checks live in PostgreSQL with the time each is next due. The worker takes due checks every few seconds (`FOR UPDATE SKIP LOCKED`, so two workers never run one check twice), spreads their start times so checks set up together do not all fire at once, and runs at most 20 at a time.
- **Results** go to ClickHouse (`check_results`: check, time, up or not, status code, response time, the cause of a failure), ordered by project, then check, then time, as metrics are ordered by name, since every query reads one check's results. They are kept 90 days. Incidents stay in PostgreSQL, with the check.
- **Uptime** over a period is the share of the period not inside an incident, so a check every 10 minutes and one every minute mean the same thing.

### Requests a check must not make

A check is a request the instance makes to an address a dashboard user types in, so it must not reach what is behind the instance: its own databases, the cloud's metadata service, or the private network. The URL must be `http` or `https`; its host is resolved first, and a check whose addresses include loopback, private, link-local, unique-local, shared (CGNAT), multicast, or unspecified ones is refused, at setup and on every run. The request then connects to the address that was checked, never resolving again (so DNS cannot answer differently in between), and every redirect is checked the same way. The body is read up to 1 MB for the word. A self-hosted install that must check its own private network can allow it with a setting; the hosted service does not. Webhook URLs follow the same rules.

## Alerts

A project's alert rules say what to watch and where to send it:

| Rule                 | Fires when                                                                                    | Resolves when                          |
| -------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------- |
| Check down           | A check (one, or any of the project's) goes down                                              | It is up again                         |
| Certificate expiring | A check's certificate expires within the set number of days                                   | It is renewed                          |
| New error            | An error group is seen for the first time, in the chosen environment                          | (once per group)                       |
| Regressed error      | An error group resolved in the dashboard occurs again                                         | (once each time)                       |
| Error spike          | Errors (all, or one group) in the last N minutes reach a threshold, in the chosen environment | They stay below it for the same window |

- **Evaluation:** check rules fire from the checker, as soon as a check changes state. Error rules are evaluated by the worker every minute, from the error list's own data in ClickHouse ([errors](errors.md)), for browser and server errors alike.
- **State:** each rule keeps, per check or error group, whether it is firing and since when, in PostgreSQL, so a restart sends nothing twice and misses nothing.
- **Noise:** a notification goes out when an alert fires and when it resolves. A rule sends at most 20 an hour; past that, one message says how many more were held back.

### Alerts on telemetry (step 4)

Added on 18 November 2026: the numbers a team watches on its servers, not only whether they answer.

| Rule           | Fires when                                                                                                                                                                                                           | Resolves when                                    |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| Route latency  | A service's route (or the whole service) has its p95 or p99 duration above a value over the last N minutes, with at least a set number of requests                                                                   | It stays below for the same window               |
| Route failures | A service's route (or the whole service) has its failed share above a value over the last N minutes, with at least a set number of requests                                                                          | It stays below for the same window               |
| Metric         | A metric, read as its chart reads it (a gauge's average, minimum, or maximum; a counter's rate; a histogram's percentile), for one host or attribute value or all, is above or below a value over the last N minutes | It is back on the right side for the same window |

- **Below too:** a value under a threshold can be what matters: response times that drop suddenly (an empty page answers fast), a queue that stops moving, requests that stop coming.
- **Evaluation:** by the worker every minute, from the same data and computations as the Services and Metrics pages, over windows of 5 to 60 minutes; each rule's query is bounded like the dashboard's, and the worker evaluates a few at a time, so rules cannot crowd out ingestion or the dashboard.
- **Not yet:** alerts on matching log lines.

### Alerts on data that stops arriving

Added on 26 November 2026: if a site's tracker breaks, or a server stops sending telemetry without an error, a rule tells the team.

| Rule                | Fires when                                                                                         | Resolves when                    |
| ------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------- |
| Data stops arriving | Fewer than N records of one source arrived in the last window (N is 1 by default: nothing arrived) | At least N arrived in the window |

- **Sources:** events (what the tracker and server events send, optionally of one name, such as `pageview` or `waitlist_signup`), traces (spans, optionally of one service), logs (optionally of one service), or metrics (one metric, optionally of one `host.name`), in one environment. A larger N also catches a sharp drop.
- **Windows:** 5, 10, 15, or 30 minutes, or 1, 2, 4, 6, 12, or 24 hours.
- **By arrival:** records count by when they arrived, not when they happened, so late or backfilled data does not hide a stop.
- **A new rule** judges only once it is a whole window old (since it was added, turned on, or changed), so its source has had a full window to send.
- **Quiet hours:** a small site may have no visitors for hours at night. There are no schedules: pick a window that the site's quietest hours fill.
- **Not in scope:** schedules or quiet hours, alerts on matching log lines, and heartbeat checks that a cron job reports to.

How it is built is [below](#data-stops-arriving-as-built).

## Where alerts go

Channels belong to the instance (its settings), so every project can use them; each rule picks one or more.

- **Email:** a list of addresses. Sent through the SMTP server the instance is set up with (`SMTP_URL`, `EMAIL_FROM`); without one, the dashboard says email is not set up on this instance. Plain, short messages: what happened, when, and a link to the check or error in the dashboard. Ottertrail sends no other email from alerts.
- **Webhook:** a JSON `POST` to a URL, for a team's own scripts or another service. Each request carries the time and a signature, an HMAC-SHA256 of the time and body with the channel's secret, so the receiver can check it came from Ottertrail and is not a replay. The body names the event (`check.down`, `check.up`, `certificate.expiring`, `error.new`, `error.regressed`, `error.spike`, `error.spike_resolved`, and for telemetry `route.latency`, `route.failures`, `metric.threshold`, `data.stopped` and their `_resolved` forms), the project, what it is about, and the dashboard link. The format is documented and versioned.
- **Delivery:** every notification is recorded in PostgreSQL before it is sent, and sent by the worker: a webhook gets 10 seconds to answer 2xx, then is retried with growing waits, for up to an hour; email is retried likewise. The dashboard lists each channel's deliveries of the last 30 days, with their outcome, and can send a test.
- **The dashboard's inbox:** each alert that fires or resolves, and each held-back summary, is also an item in the notifications of everyone who can see the rule (uptime and alerts at view, and one of the areas its kind watches), whether or not the rule has channels, written in the alert's transaction, so it is there once ([access](access.md#notifications), [dashboard](dashboard.md#notifications)). The instance's storage and backup warnings, raised and cleared, and the backup notices are items for the owner and admins. Items are not emailed.

## The dashboard

- **Uptime** (project nav): the project's checks, each with its state, uptime over the last 24 hours, 7 days, and 30 days, and its response time; add, edit, pause, and delete. A check's page: its response time over the period, its uptime, its incidents, and its latest failures with their causes.
- **Alerts** (project nav): the project's rules, with what each watches, its channels, whether it is firing now, and its recent alerts; add, edit, turn off.
- **Notification channels** (instance settings): email lists and webhooks, with a test send and their recent deliveries; a webhook's secret is shown to the instance's dashboard users.
- An error's page links to the rules that watch it.

## Limits

At most 50 checks per project. Requests: 30-second timeout at most, 5 redirects, 1 MB of body read. Rules: at most 50 per project, 20 notifications an hour each. A webhook's answer is read only for its status. Channels: at most 20 per instance, 60 deliveries an hour each, 5 test sends a minute each; deliveries are kept 30 days.

## Not in the first version

- Slack and Discord messages in their own formats (a webhook can reach a small relay meanwhile), SMS, and phone calls.
- Alerts on matching log lines.
- Checks from several locations, and checks other than HTTP (TCP, ping, DNS); heartbeat checks that a job reports to.
- Status pages, on-call schedules, escalation, and maintenance windows (a check can be paused).

## Step 1, uptime checks, as built

Built on 18 November 2026, from the design above. Code: `apps/api/src/uptime/`, the worker (`apps/api/src/worker.ts`), and `apps/web/src/features/uptime/`; the pages are described in [the dashboard](dashboard.md#812-uptime).

- **Storage.** PostgreSQL holds `uptime_checks` (what each check asks and expects, whether it is paused, its state, its failures in a row and when and why that run of failures started, when it is next due, its latest answer, its certificate's expiry, and when its URL last changed) and `uptime_incidents` (check, start, end, first cause and what it said; at most one open per check). Deleting a project or a check deletes both. ClickHouse holds `check_results`, ordered by project, check, and time, partitioned by day, kept 90 days; project deletion and the search for forgotten projects cover it ([ClickHouse](clickhouse.md#retention-and-deleting-a-project)).
- **The request** (`request.ts`, `addresses.ts`). The URL's host is resolved with a DNS resolver of the worker's own (Node.js's `dns.Resolver`, c-ares), which asks the name servers the system is set up with for A and AAAA records. It does not use the system's `getaddrinfo`, which runs on libuv's four threads: a few checks on a host whose name server never answers held them for seconds, past their own timeouts, and every other check, and the worker's own connections to PostgreSQL and ClickHouse, waited behind them. The resolver's queries end when the check's timeout does. It does not read `/etc/hosts`, so a name only `/etc/hosts` knows, `localhost` among them, does not resolve; an IP address in the URL is used as it is, without DNS. Every address the host resolves to is checked; one refused address refuses the check. Refused: IPv4 `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`, `192.88.99.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `224.0.0.0/4`, and `240.0.0.0/4`; IPv6 `::`, `::1`, `fc00::/7`, `fe80::/10`, `ff00::/8`, `2001::/23`, `2001:db8::/32`, `3fff::/20`, `64:ff9b:1::/48`, and anything else outside `2000::/3`. Cloud metadata services, which hand out an instance's credentials, are refused whatever the settings say: `169.254.169.254` (AWS, Google Cloud, Azure, Oracle Cloud, DigitalOcean, Hetzner), `100.100.100.200` (Alibaba Cloud), `168.63.129.16` (Azure's host endpoint), `fd00:ec2::254` (AWS over IPv6), `fd20:ce::254` (Google Cloud on IPv6-only instances), and `fd00:c1::a9fe:a9fe` (Oracle Cloud over IPv6, as cloud-init reads it; Oracle's own documentation names only the IPv4 address). So are the addresses and ranges an operator lists in `UPTIME_DENY_ADDRESSES`. An IPv4-mapped (`::ffff:a.b.c.d`), NAT64 (`64:ff9b::/96`), or 6to4 (`2002::/16`) address is judged by the IPv4 address inside it too. The request connects to the first checked address through a lookup that answers only with it, so the host is never resolved again, while the Host header, TLS's server name, and the certificate check keep the host's name. Each redirect (301, 302, 303, 307, 308) is resolved and checked the same way, at most 5. One timeout covers resolving, connecting, redirects, and the body. The body is read only when a word is looked for, up to 1 MB, and the word is matched as typed. The certificate's expiry is read from the first HTTPS answer's connection.
- **Causes.** Timeout, refused connection, DNS, TLS, status code, word, address not allowed, and two more than the design named: connection, for a connection reset or a network that cannot be reached, and redirects, for more than 5 or one to an address that is not http or https.
- **Saving a check** resolves its host, with the same resolver, and refuses an address the rules refuse with a 400. For a host name, the answer says only that the host resolves to an address checks may not reach, and a failed run's detail and its incident say the same: naming the address and its kind would let a dashboard user learn the instance's internal names and addresses (its containers' among them) one try at a time, without even saving a check. The address and its kind go to the API's or the worker's log. Only an IP address the user typed is named, with its kind. A host that does not resolve is saved, and its runs fail with a DNS cause until it does. The URL must be http or https, without a user name or password (they would be stored as plain text); a word needs `GET`.
- **`UPTIME_ALLOW_PRIVATE_ADDRESSES`** (off by default) lets loopback, private, unique-local, and shared addresses through, for a self-hosted install that checks its own network. Link-local addresses and the metadata services above stay refused even then. With it on, any dashboard user can point a check at any service on that network, and the word check reads its answers: one yes or no per run (is this word in the body?), enough to read data out of a service that answers without a password, a word at a time. Set it only where every dashboard user may read those services ([deployment](deployment.md#uptime-checks)).
- **`UPTIME_DENY_ADDRESSES`**: addresses and CIDR ranges checks may never reach, checked when the API and the worker start. Its reason is the server's own public address: a check to it on another port reaches services a cloud firewall closes only to the outside, such as a database published on the host.
- **Scheduling** (`scheduler.ts`, `checks.ts`). Every 2 seconds the worker takes the due checks there is room for, at most 20 requests at once and 10 of one project, with `FOR UPDATE SKIP LOCKED`, and moves each one's next due time on by whole intervals past now in the same statement, before any request: a crash during a run skips that run, and the check is due again one interval later. Now is PostgreSQL's clock, not the worker's, and a next due time more than one interval ahead, as a clock that jumped leaves, is brought back to one interval from now. A check keeps its place in its interval after the worker was away. Requests run without holding the tick back: a slow check holds only its own place. When slow checks fill every place, the rest wait and run late; the worker logs once when checks are taken 30 seconds or more after they were due, and once when they are on time again. One project's checks fill at most half the places, so they cannot hold back every other project's.
- **State.** Each outcome is recorded on the check in one transaction (`recordOutcome`, the one place a check's state changes): down after its failures in a row, with an incident from the first failure of that run; up again after one success, which ends the incident. It returns the change, which the worker logs and hands to the alert rules ([step 3](#step-3-alert-rules-as-built)). An outcome is not recorded when its run started before the latest recorded one, or before the check's URL changed, so two overlapping runs never record out of order. A changed URL is a new check: it ends an open incident, starts again as pending with no failures, and forgets the old URL's certificate. The result then goes to ClickHouse with an asynchronous insert that waits for the write, as events do; while ClickHouse fails, the worker logs it once and carries on, and the state in PostgreSQL stays right.
- **Uptime** is worked out in PostgreSQL from incidents: the share of the window not inside one, an open incident lasting until now, counted from the check's creation when that is later. The list shows the last 24 hours, 7 days, and 30 days; a check's page also shows its uptime over the chosen days. Incidents are kept with the check, so uptime reaches past the results' 90 days.
- **Routes**, each behind the one access check of every project route, with Fastify schemas and limits: list, add, read, change (any field, or `paused`), and delete checks, at most 50 per project; a check's results over whole days in the instance's timezone (its response times in buckets, runs and failures, the latest 20 failures, and its uptime) and its incidents (the latest 100). The ClickHouse reads filter by project and check, take parameters, and run with the telemetry pages' settings and their limit on queries at once, which both now share (`telemetry/dashboard-limit.ts`, `dashboardReader`).

Decided differently from the design, or settled where it said nothing:

- **First runs** come at a random moment within the check's interval, but at most 5 minutes off, so checks set up together are spread out and an hourly check still answers within minutes.
- **Pausing** ends an open incident and forgets the state: nothing is known of a check while it does not run, and it starts again as pending. Paused time counts as up in uptime.
- **Deleting a check** deletes it and its incidents; its results in ClickHouse are no longer reachable and leave with the 90 days, rather than costing a ClickHouse deletion each time.
- **Response time** is the time to the last answer's headers, redirects included; the chart averages the runs that got an answer.
- **Refusals** do not name the address a host name resolved to (above), where the design's setup check would have.
- **Metadata services and `UPTIME_DENY_ADDRESSES`** are refused whatever the private-address setting says; the design named only the ranges.

### Not done in step 1

- Alerts on a check going down or its certificate expiring: built in [step 3](#step-3-alert-rules-as-built).
- A check of a host that resolves to several addresses uses the first (IPv4 first); it does not try the others when that one fails.
- Names from `/etc/hosts` do not resolve (above).
- Request headers, a body, or authentication for a check; checks from several locations.

## Step 2, channels and delivery, as built

Built on 18 November 2026, from the design above. Code: `apps/api/src/notifications/`, the request machinery uptime checks and webhooks share (`apps/api/src/outbound/`), the worker (`apps/api/src/worker.ts`), and `apps/web/src/features/settings/`; the dashboard's part is in [the dashboard](dashboard.md#notification-channels), and the webhook format in [webhooks](webhooks.md).

- **Channels** (`channels.ts`, PostgreSQL's `notification_channels`) belong to the instance, at most 20, each with a name (1 to 100 characters; the first address or the URL's host when left empty) and a kind that never changes. An email channel holds 1 to 20 addresses, each one sign-in would accept (zod's `z.email()`, as `canSignInWith` checks it), trimmed, and each kept once whatever its case. A webhook holds its URL, which follows the uptime checks' rules exactly (`outbound/url.ts`: `http` or `https`, a host, no user name or password, at most 2048 characters), and a secret the server makes: 32 random bytes as base64url, which the owner and admins can read from its own route and replace on demand. The list's and a channel's answers say only whether a webhook has one (`hasSecret`), so the secret reaches the browser only when asked for; replacing it answers the new one once. Both answers are `Cache-Control: no-store`. A webhook's host is resolved when it is saved, with the checks' resolver, deny list, and private-address setting (`outbound/addresses.ts`, moved from `uptime/` so both use it), and a refused address answers 400 with the checks' wording, "webhooks" in place of "checks"; a host that does not resolve yet is saved. The owner and admins manage channels ([access](access.md)); changes need the dashboard's origin.
- **Notifications** (`deliveries.ts`, `notify`) are what step 3 calls: `notify(db, { channelIds, type, project, subject, message, url, time? })` writes one row per channel that exists in `notification_deliveries`, in one transaction, before anything is sent, and returns the notification's ID and each delivery's ID and status. The row holds the channel, the event type, the payload (the webhook body, version 1, as `json`, so its keys keep their order), the attempts, the next attempt, the status (pending, sent, or failed), the last error (one line, at most 300 characters, which never names an address the rules refused for a host name), and when it was sent. Unknown channels are skipped. Input no caller should send (an unknown type, an empty message, a relative URL, a subject that is not flat) throws.
- **The channel's cap.** The transaction locks the channels' rows, then counts each channel's deliveries of the last hour, test sends left out (they have their own limit of 5 a minute, and a capped channel still takes one): at 60, the notification is refused ("Not sent: this channel had 60 deliveries in the last hour, which is its limit."). A channel's first refusal in an hour is a failed row; later ones in that hour only count on it (`refused`, and its error ends "N notifications refused so far."), so a flood does not fill the table. Refusals do not count towards the cap, so a flood that goes on does not keep a channel closed. A rule's own cap of 20 an hour is step 3's.
- **The worker** (`sender.ts`) takes due deliveries every 2 seconds, as many as there is room for, at most 10 sending at once, with `FOR UPDATE SKIP LOCKED`, counting the attempt and moving its next attempt on to the retry's time in the same statement, before anything is sent, as uptime checks are taken. That statement, and the one before it that fails deliveries whose last attempt never finished, run in one transaction with one `now()`, and the take passes over any delivery already at its last attempt, so a lease that ends between the two can never push a delivery past it. Two workers never take one delivery at once, and a worker that stops mid-send leaves the delivery to be tried again after its wait. A late outcome never overwrites a newer one: only the attempt that took the delivery records it.
- **Retries** wait 30 seconds, then 1, 2, 5, 10, 20, and 20 minutes: eight attempts over about an hour, then the delivery fails for good with its last error. The last attempt holds its delivery for 60 seconds; if no outcome is recorded by then, the delivery is recorded as failed ("The last attempt did not finish"), so one that stops the worker each time is not tried for ever.
- **Email** (`email.ts`) goes through Nodemailer to the host, port, TLS mode, and login `SMTP_URL` names (handed over one by one, never as the URL), from `EMAIL_FROM` ([deployment](deployment.md#email)), as one plain-text message to the channel's addresses: the message, when it happened in the instance's timezone, the project, and the dashboard link; the subject is the instance's name, a colon, and the message, on one line, at most 200 characters. Over `smtp://` with a password, STARTTLS is required. A message has 20 seconds. SMTP errors are put in words that never hold the URL or the password, with the server's code and answer where it gave one. Without `SMTP_URL`, an email delivery fails at its first attempt: "Email is not configured on this instance. The instance's operator must set SMTP_URL and EMAIL_FROM."
- **Webhooks** (`webhook.ts`) are a JSON `POST` with the headers and signature [webhooks](webhooks.md) describes. The host is resolved and checked again on every delivery and the request pinned to the checked address (`outbound/request.ts`, shared with uptime checks), so a DNS change after saving cannot reach an address the rules refuse; the refused address and its kind go to the worker's log only. One 10-second timeout covers resolving, connecting, and the answer's headers; any 2xx is delivered, a redirect is not followed, and the answer's body is not read.
- **Pruning:** the worker deletes deliveries older than 30 days every hour; deleting a channel deletes its deliveries.
- **Routes** (`routes.ts`), for the owner and admins, changes with the dashboard's origin, with Fastify schemas and bodies of at most 32 KB: `GET` and `POST /api/channels` (the list says whether email is set up), `GET`, `PATCH`, and `DELETE /api/channels/:id`, `GET /api/channels/:id/secret` (a webhook's secret), `POST /api/channels/:id/secret` (a new one, answered once), `POST /api/channels/:id/test` (a `test` notification, at most 5 a minute per channel, else 429), and `GET /api/channels/:id/deliveries?before=<delivery ID>&limit=<1 to 100, 20 by default>`, the last 30 days newest first, with the ID to ask for the next page.

Decided differently from the design, or settled where it said nothing:

- **Who manages channels:** the owner and admins, who can also read a webhook's secret; it comes only from its own route. Members see channels' names only, when choosing a rule's ([access](access.md)).
- **Test sends** do not count towards a channel's hourly cap.
- **`SMTP_URL` takes no query string:** Nodemailer would read options from it over Ottertrail's own (TLS, timeouts, logging), so the mailer gets its host, port, TLS, and login one by one.
- **One message per email channel,** to all its addresses at once, so its recipients see each other's addresses: a channel is one team's list.
- **`SMTP_URL` without a password** is accepted, for a relay that needs none.
- **Two IDs:** the body's `id` is the notification, shared by its channels; `Ottertrail-Delivery` is the delivery, one per channel. Both stay the same on every retry.
- **4xx answers are retried** like 5xx: a receiver that is being deployed or misconfigured for a moment often answers 404 or 401.
- **Address refusals at send time are retried** like any failure, since DNS may change back; they fail for good after the last attempt.

### Not done in step 2

- Alert rules, which call `notify`: built in [step 3](#step-3-alert-rules-as-built).
- An overlap when a secret is replaced, during which both secrets sign; a receiver must take the new one at once.
- A cap on deliveries waiting across all channels, beyond each channel's 60 an hour.

## Step 3, alert rules, as built

Built on 18 November 2026, from the design above. Code: `apps/api/src/alerts/` (`kinds.ts`, `rules.ts`, `fire.ts`, `check-rules.ts`, `error-rules.ts`, `evaluator.ts`, `routes.ts`), the worker (`apps/api/src/worker.ts`), and `apps/web/src/features/alerts/`; the pages are described in [the dashboard](dashboard.md#813-alerts), and the notifications' bodies in [webhooks](webhooks.md#example-bodies).

- **Rules** (`rules.ts`, PostgreSQL's `alert_rules`) belong to a project, at most 50. Each has a name (1 to 100 characters; the kind's name when left empty), a kind, the kind's settings as JSON, one or more of the instance's channels (at most 20), and whether it is on. The kinds are one list (`RULE_KINDS` in `kinds.ts`, with each kind's label, where it is evaluated, and the event types it sends), which step 4 extends; the database takes any short kind name, so step 4 needs no change to the table. Saving a rule checks, in its transaction, that each channel exists and that a named check is the project's, and locks what it found, so a deletion at that moment waits for the save.
- **Kinds and their settings:**
  - **Check down:** one check, or all the project's (`checkId` null, which takes in checks added later). Fires when the check is down, resolves when it is no longer down.
  - **Certificate expiring:** one check or all; `days`, 1 to 90, 14 by default. Fires once per certificate, told apart by its expiry, when it expires within the days (or has expired); resolves when the expiry moves past the window, as when the certificate is renewed. A new certificate that also expires within the window fires again, for its own date.
  - **New error:** an `environment`, or all (null). Fires once per error group whose first occurrence arrived after the rule was created or last turned on. The rule chosen: a group is new to a rule when no occurrence of it, in the rule's environment (or in any, for all), arrived before the rule was on, so a group seen before the rule was added (or while it was off) is never new to it, even if no rule ever told anyone about it.
  - **Regressed error:** no settings. Fires once per regression, decided by the errors module's own rule (`statusOf` in `errors/errors.ts`): an occurrence, in any environment, after the group's resolution, that arrived after the rule was on. A group resolved again and back again fires again; while one resolution stands, its group fires once, however long that lasts.
  - **Error spike:** an `environment` or all, a `fingerprint` (one group) or all, a window of 5 to 60 minutes (10 by default), and a threshold of 1 to 1,000,000 errors (10 by default). Fires when the count over the last window reaches the threshold; resolves once the count has stayed below it for a whole window.
- **State** (`alert_states`): per rule and subject (a check's ID, a fingerprint, or nothing for a spike rule, whose subject is the rule itself), whether it fires, since when, the key it fired for (a certificate's expiry, a resolution's time), when it was last notified, since when a spike has been below its threshold, and its open alert. **History** (`alert_history`): each alert, with the rule, the kind the rule had when it fired (migration 0021), the subject and its name, when it fired and resolved, the message, and the notifications sent on firing and resolving (none when the rule's cap held one back). Kept 90 days; an alert still firing is kept. Deleting a rule deletes both.
- **Since when a rule is on** (`active_since`): set when the rule is created, turned on again, or changed to watch something else. An error rule reads nothing that arrived before it, so a rule added (or turned on) after an error happened does not tell of it, whatever the project's cursor says.
- **One transaction per alert** (`fire.ts`): the rule's row is locked, the state read, and the state, the history, and the notification (`notifyIn`, the transaction-held form of `notify`) written together. An alert fires only when its state differs from what is true, so a second worker, a repeated evaluation, or a restart sends nothing twice, and a worker that stops before the commit leaves the alert to the next evaluation. The transaction also checks that the locked rule still has the kind and settings the evaluation read (`RuleRead`): a rule changed meanwhile to watch something else, whose states the change forgot, gets no alert and no firing state for what it watched before, which no later evaluation would look at, and so never resolve. Every evaluator passes what it read (check, error, and telemetry rules).
- **Check rules** (`check-rules.ts`) read PostgreSQL only. The checker hands each state change from `recordOutcome` to the evaluator at once (`onStateChange`), and each run that records a certificate expiry other than the check's (`onCertificate`, a scheduler hook) evaluates that check's certificate rules. Every minute, the worker also compares every "check down" rule's state with its checks', which catches a change the worker stopped before acting on; every hour, every certificate rule, since its window moves with time. A paused check, or one whose URL changed, is no longer down and has no certificate: its alerts resolve. An alert's transaction reads the check again, `FOR SHARE`, after the rule's lock, and goes ahead only while the check exists and still has what the evaluation read (its state, whether it is paused, its certificate's expiry): a check deleted, back up, or renewed meanwhile is left to the next evaluation. Locks are always taken rule first, then check. Each minute also ends, without a notification, any alert still firing for a check that no longer exists.
- **Error rules** (`error-rules.ts`) are evaluated every minute, a project at a time, with the dashboard's ClickHouse settings (`DASHBOARD_SETTINGS`: 15 seconds and 300 MB a query) and parameters for every value. New and regressed errors are evaluated apart from spikes: a query of one past its limits is logged, and the other still runs.
  - **Arrivals:** one query reads the error groups (per environment) whose occurrences arrived since the project's last evaluation, by `received_at`, kept to the days such arrivals can be on by the occurrence time (from a day before, as an event is at most a day old when it arrives, to five minutes after, as a server's clock may be ahead), on the table's project and day order. It reads a page of 1,000 groups at a time, in the order of their first arrival, fingerprint, and environment, at most 5 pages a minute; when more are left, the project's cursor keeps its time and the last group read, and the next minute goes on from there. Ties are common (one batch shares one arrival time), hence the whole key.
  - **History**, for "new" only: when each group first arrived, per environment. PostgreSQL keeps each group's first arrival once it has been read (`alert_error_groups`), so ClickHouse is asked only about groups it does not know, 200 fingerprints a query, over all the project keeps. The bloom filter on the fingerprint skips the parts without the group, which helps for a new, rare group; a frequent group is in nearly every part, so its history costs a read of the project's whole retention, once. Measured on a project of 644,005 events over 28 days with an error 3,000 times a day: 644,005 rows read every minute before PostgreSQL kept the groups, none after.
  - **Regressions:** the groups' resolutions from PostgreSQL and the latest occurrence among the arrivals. A regressed rule's state for a group lasts as long as the resolution it fired for: resolving the group again or reopening it removes it (`setResolution`), and pruning keeps it while the resolution stands.
  - **Spikes:** one query counts every spike rule's window, each retry once by its event ID (so without `FINAL`), with each window's latest error type, message, and environment; `PREWHERE` reads the other columns only for the rows in the longest window. The table is ordered by project, then day, so the query still reads the project's rows of the window's day (or two): 14,199 rows in the measurement above, before and after.
  - **Where it starts:** the project's evaluation records how far it read (`alert_evaluations`), and the next starts there, or where the earliest of its rules came on when that is later (a cursor left from before its rules were on, or none). It reads up to 30 seconds before now, so an insert still landing is read the next minute. After a gap, such as a stopped worker, it reads at most the last hour: alerts from longer ago are not sent, rather than all at once. A project whose arrivals fail to read is not moved on, and is read again the next minute.
- **Notifications** go through `notify`'s transaction-held form to the rule's channels: one when an alert fires and one when it resolves, for the kinds that resolve. The message names the project, says what happened, and names the subject: the check's name and URL, the certificate's host and expiry date, the error's type and message (cut to 200 characters) and environment, or the count, threshold, and window. The link is the check's page, the error group's page (in the alert's environment), or the error list. The subject carries the same, with the rule's ID and name. Two event types were added: `certificate.renewed`, when a certificate alert resolves, and `alert.held_back`, the cap's summary.
- **The cap:** a rule sends at most 20 notifications an hour, counted from the first; past that, each alert is recorded in the history, marked as held back, and counted. When the hour is over, one `alert.held_back` message says how many were held back (sent within a minute of the hour's end by the worker's tick, or before the next notification), and the count starts again. The channel's own cap of 60 an hour stays as it was.
- **Deleting a check** (`forgetCheck`, in the transaction that deletes it, before the check): it locks the project's rules (in ID order), then the check, and only then turns off the rules that watch only it, with the reason ("the check it watched was deleted"), and ends every rule's alerts about it, without a notification. An alert or a rule being saved for the check meanwhile either finishes first and is seen here, or waits and then finds no check. **Deleting a channel** (`forgetChannel`, likewise): it locks the rules that name it, then the channel; every rule drops it, and a rule left without channels is turned off, with the reason, and its alerts end.
- **Turning a rule off, or changing what it watches,** forgets its states and ends its open alerts without a notification: turned on again, it starts from what is true then (a check still down fires again). Its history stays, each alert with the kind it fired under, and who may read an alert goes by that kind, not the rule's current one ([access](access.md#alert-rules-and-the-areas-they-watch)): an error rule changed into a check rule shows its old error alerts only to those who may read errors.
- **A rule the server turned off** (its check or its last channel deleted) is turned on again by a save that fixes it, one with a check that exists or a channel, and its reason goes, unless the save says itself to keep it off. The form drops channels the instance no longer has, so such a rule can be saved again.
- **Routes** (`routes.ts`), each behind the one access check of every project route, with Fastify schemas and bodies of at most 16 KB; changes need the dashboard's origin: `GET` and `POST /api/projects/:id/alert-rules`; `GET`, `PATCH` (any field, or `enabled`), and `DELETE /api/projects/:id/alert-rules/:ruleId`; `GET /api/projects/:id/alert-rules/:ruleId/history` and `GET /api/projects/:id/alerts` (the project's alerts), both `?before=<alert ID>&limit=<1 to 100, 20 by default>`, newest first; and `GET /api/projects/:id/alerts/firing`. An unknown channel or another project's check answers 400 (`channel_not_found`, `check_not_found`); a 51st rule, 409.

Decided differently from the design, or settled where it said nothing:

- **Certificates** are looked at every hour, not once a day, besides each run that sees a new expiry: a rule just added hears about a certificate within the hour.
- **A rule added while a check is down** fires for it at the worker's next minute: the check is down now. A new-error rule, by contrast, treats groups seen before it as not new.
- **Regressed errors** have no environment setting: whether a group regressed belongs to the project, as on the error list.
- **Two event types more** than the design named: `certificate.renewed` and `alert.held_back`.
- **The held-back summary** goes out when the hour is over, so it can say how many.
- **A one-group spike rule in every environment** links to the group's page in the environment of its window's latest occurrence.
- **Arrival time:** "new" and "regressed" read what arrived since the last evaluation, 30 seconds behind now, so an alert comes 30 to 90 seconds after the error arrives.
- **"Up again after"** counts from the incident's start, the first failure of the run that took the check down, to its end.

### Not done in step 3

- A server's exception that arrives more than a day after it happened is not read by the error rules (browser and server events older than a day are refused at collection; OTLP exceptions are not).
- A group whose occurrences keep arriving while a project works through a backlog of more than 5,000 groups a minute is read once per backlog: a regression among its later arrivals waits until the backlog is read.
- Muting a rule for a while, alerts on more than one condition, and repeat notifications while an alert keeps firing.

## Step 4, alerts on telemetry, as built

Built on 18 November 2026, from the design above, and revised the same day after a review (the scheduling, the batched read without `FINAL`, the 30-minute route window, the project budget, read-only queries, the recorded failures, up-down totals of fresh series, and the longer look back). Code: `apps/api/src/alerts/` (`kinds.ts`, `telemetry-rules.ts`, `evaluator.ts`, `routes.ts`), the shared computations in `apps/api/src/telemetry/services.ts` (`routeWindows`, `requestsSeen`, `recentRoutes`) and `metrics.ts` (`metricFilter`, `metricWindow`), the worker (`apps/api/src/worker.ts`), migration `0004_telemetry_rule_evaluation`, and `apps/web/src/features/alerts/` with the links on the Services page and a metric's page ([the dashboard](dashboard.md#813-alerts)); the notifications' bodies are in [webhooks](webhooks.md#example-bodies).

- **Kinds and their settings** (`kinds.ts`, three more in `RULE_KINDS`, evaluated from `telemetry`). Each has an `environment` (production when none is sent; one at a time, as the Services and Metrics pages show) and a window, `windowMinutes`, 5 to 60 for a metric rule and 5 to 30 for a route rule (10 by default).
  - **Route latency** (`route_latency`): a `service` (as `service.name` names it), a `route` (at most 1,000 characters) or the whole service (`null`), `percentile` `p95` (the default) or `p99`, `thresholdMs` (above 0, at most an hour), and `minRequests`, 1 to 1,000,000 (20 by default). Fires when the window's percentile is above the threshold.
  - **Route failures** (`route_failures`): the same scope, and `thresholdPercent`, 0 to just under 100. Fires when the share of requests whose span status is Error is above it.
  - **Metric** (`metric_threshold`): a `metric` and its `metricKind` (`gauge`, `counter`, `updown`, `histogram`: a name may be sent as two kinds), an `aggregate` the kind offers (`avg`, `min`, `max`; `rate`; `sum`; `p95`, `p50`, `p99`; the first is the default), a `direction`, `above` (the default) or `below`, a `value` (any number up to 10^15 either side of 0), and optionally a `host` (its resource's `host.name`) and an `attributeKey` with its `attributeValue` (each at most 1,000 characters). Fires when the window's value is above the value, or below it.
- **The same numbers as the pages.** A route rule counts as the Services page does: spans of kind SERVER, the route their `http.route` else their name; `routeWindows` adds each rule's requests, failed ones, and 95th and 99th percentile durations, interpolated as the page's are. A metric rule reads its metric as its chart does, through the same query (`metrics.ts`, `chartIn` behind `metricChart`), with one bucket covering the window (`metricWindow`): a gauge's average, minimum, or maximum of the points; an up-down counter's total; a counter's increases, each step spread over the time it covers, over the window's seconds; a histogram's percentile from the window's bucket counts (the last cumulative point in the window less the last before it). The host and attribute filters are the chart's own (`resource` and `attribute` in `metricFilter`), which the metric chart route also takes (`host`, `attr`, `attrValue`).
- **The window** ends a minute before the evaluation (`TELEMETRY_LAG_MS`): metrics are exported every minute by default, so the last minute's points may not have arrived. A metric's points are read up to the evaluation, so a counter step that ends after the window still counts the part inside it, and from the window's length before it (at least 5 minutes, `WINDOW_LOOKBACK_MS`), so a cumulative series' first point in the window has the one before, even for a counter exported less often than every 5 minutes.
- **Up-down totals** add the last value of each series whose last point is within 2 minutes of the window's end (`FRESH_SERIES_MS`, two export intervals). A series that stopped before, such as a pod replaced in a rolling deploy, is not counted beside the one that took over: 3 old and 3 new pods count 3. A delta series adds its changes in the window instead, fresh or not ([telemetry](telemetry.md#how-metrics-are-charted)).
- **Scheduling** (`takeDueRules`): each rule is due once a minute (`next_evaluation_at` in PostgreSQL; null when the rule is added, changed, or turned on, so due at once). Every 5 seconds, each worker takes the due rules (at most 200) with `FOR UPDATE SKIP LOCKED` and moves each one's next evaluation a minute on in the same statement, keeping its place in the minute, so one worker of several evaluates a rule each minute, and rules added at different times are spread over the minute. A worker that stops before evaluating what it took leaves those rules to the next minute; one shutting down (`stop()`) starts nothing more and hands back the rules it took but had not started (`releaseRules`), due again at once for any worker.
- **One read per project and environment.** A worker evaluates at most 4 projects at once (`TELEMETRY_CONCURRENCY`). A project's due route rules of one environment are read in one query over the longest of their windows (`routeWindows`), each rule counted over its own with `-If` combinators; `PREWHERE` keeps the read to the rules' services before the spans' attributes (for the route) are read. Each metric rule is its own query (two when its metric has series).
- **Without `FINAL`.** Route rules read spans without `FINAL`: a retried copy counts twice in its window until its day is merged, which the spans table forces within about an hour of the day's last insert ([storage](telemetry.md#storage)); a copy barely moves a share or a percentile. With `FINAL`, merging the window's overlapping parts went past the 300 MB limit even for one rule (below).
- **Bounds.** Every query filters by project first, takes every value as a parameter, reads only the window (a metric also the time before it), and runs with the dashboard's settings: 15 seconds and 300 MB a query, and read-only, so ClickHouse stops a query whose connection closes (`cancel_http_readonly_queries_on_client_close` acts only on read-only queries). Each project has 20 seconds a pass (`PROJECT_BUDGET_MS`): each of its queries' time limit is cut to what is left (the reader's `deadline`), its connection is closed when the budget ends, and a rule not reached by then is recorded as failed for this minute and evaluated again the next, so one project cannot hold up the others.
- **Measured** on a project with 6 million server spans in the last hour (100,000 a minute, 5 services, 200 routes, each span with 6 attributes as an HTTP server's), in 60 parts left unmerged, each spread over the whole hour as concurrent inserts leave them, in a test database:

  | Read                                                | Rows read | Bytes read | Memory  | Time   |
  | --------------------------------------------------- | --------- | ---------- | ------- | ------ |
  | Before: one route rule, 15 minutes, `FINAL`         | 507,904   | 161 MiB    | 285 MiB | failed |
  | Before: one route rule, 30 minutes, `FINAL`         | 540,672   | 171 MiB    | 284 MiB | failed |
  | Before: one whole-service rule, 15 minutes, `FINAL` | 2,047,488 | 132 MiB    | 173 MiB | 608 ms |
  | Ten rules in one read, 15 minutes, `FINAL`          | 786,432   | 249 MiB    | 286 MiB | failed |
  | After: ten rules in one read, 15 minutes            | 2,047,488 | 565 MiB    | 26 MiB  | 821 ms |
  | After: ten rules in one read, 30 minutes            | 3,522,048 | 986 MiB    | 61 MiB  | 516 ms |
  | Ten rules in one read, 60 minutes (not allowed)     | 5,979,648 | 1.65 GiB   | 116 MiB | 886 ms |
  | After: one route rule, 15 minutes                   | 2,047,488 | 565 MiB    | 8 MiB   | 588 ms |

  "Failed" is the 300 MB memory limit; before, each rule was its own query, so ten rules read ten times. With parts each holding its own minute (as after merges), one route rule with `FINAL` read 1.5 million rows, 429 MiB, in 7 MiB. A route rule reads every span of its project in the window, since spans are ordered by project and time, not by service, and the spans' attributes hold the route: hence the 30-minute cap on route windows (`MAX_ROUTE_WINDOW_MINUTES`) until a per-minute rollup of requests by route exists. Metric rules read their metric's rows only (the tables are ordered by project, then name): measured earlier on 5.76 million points a day, 8,192 to 24,576 rows a query.

- **Firing and resolving** (`judge`): state and history are step 3's (`alert_states`, one subject per rule, and `fire.ts`), with the hourly cap. A rule fires when the window's value is on the wrong side; while it fires, it remembers since when the value has been back on the right side (`clear_since`), forgets it as soon as the value crosses again, and resolves once it has been back for a whole window, at every evaluation. An alert's transaction goes ahead only while the rule is the one read (its `updated_at`), so a rule changed during an evaluation fires nothing for its old settings.
- **No data** (the rule chosen): a window without a point of the metric, or with fewer requests than the rule's minimum (none included), has no value. No value never fires, and never counts toward resolving: a firing alert stays firing through it, its time back on the right side starts again, and it resolves only after a whole window of values back on the right side, once data is back. A rule changed, or turned off, ends its alert without a notification, as in step 3. So a route rule whose service stops answering keeps firing until requests come back below the threshold for a window, and "requests stop coming" is a metric rule on a counter's rate below a value (a rate of 0 is a value, as long as the counter is still exported).
- **Failures** are recorded on the rule (`evaluation_error` and `evaluation_failing_since`, `recordEvaluation`): the reason (the query's error, or that the project's budget ran out before the rule) and since when its evaluations have failed, cleared by the next that works, or by changing the rule or turning it off or on. The rule API answers them as `evaluationError`, and the Alerts page shows "Not evaluated since …: <reason>" in the rule's row, so a rule that cannot be evaluated does not look quiet. The worker logs a rule once when it starts failing and once when it works again, whichever worker sees it.
- **Saving a rule** checks its settings with Fastify's schema and `settingsOf` (`invalid_service`, `invalid_route`, `invalid_min_requests`, `invalid_percentile`, `invalid_threshold`, `invalid_metric`, `invalid_metric_kind`, `invalid_aggregate`, `invalid_direction`, `invalid_attribute`, `invalid_window`), then looks for what it watches in the project's last 24 hours (`notSeenWarning`, through the dashboard's query limit): for a route rule, first whether the service sent a request at all, from the narrow columns, then, for a route, one of the service's spans with it; for a metric rule, one point of its kind with its filters. It is saved either way: a rule may be set up before the app is deployed. The answer's `warning` says why it may not fire, `{ "reason": "not_seen" | "not_checked", "message": … }`, or is `null`; a change of a rule's kind or settings looks again, a change of its name, channels, or `enabled` does not.
- **The form's route suggestions** come from `GET /api/projects/:id/services/routes`: up to 200 distinct services and routes of the last 24 hours (`recentRoutes`, a `DISTINCT` with a `LIMIT`, which stops reading once it has them), not the Services page's counts.
- **Notifications** (six event types): `route.latency`, `route.latency_resolved`, `route.failures`, `route.failures_resolved`, `metric.threshold`, `metric.threshold_resolved`. The message gives the value, the threshold, the window, and, for a route, the requests (and failed ones), quoting a route, host, or attribute value up to 300 characters; the subject the same as fields; the link the Services page on the service, its route marked (`?service=…&route=…&env=…`), or the metric's page with its kind and filters. A filter that would take the link past a notification's 2,048 characters is left out of it, the longest first (the message still names it).
- **Tests:** `apps/api/tests/telemetry-alerts.test.ts`, against real PostgreSQL and ClickHouse with spans and metrics sent through the OTLP routes: each kind fires over (or under) its threshold, not below the request minimum, resolves only after a whole window back, and does nothing without data (a firing alert stays, its wait starts again); a host filter and an attribute filter; a counter's rate from cumulative points, a histogram's 95th percentile from bucket counts, an up-down total after a rolling deploy, and a counter exported every 15 minutes, all worked out by hand in the test; a 1,000-character route that fires with its link cut; each rule taken by one of two workers, once a minute; at most 4 projects at once; a project past its budget without holding up another; a failing rule recorded, shown by the API, logged once per outage, and cleared; a stopping worker starting nothing more and handing back what it took; the routes' checks, warnings, the 30-minute route window, the route suggestions, and access (401 signed out, 404 for an unknown project); and the metric chart's host and attribute filters. `apps/api/tests/telemetry-dashboard-limit.test.ts`: an aborted dashboard query leaves `system.processes` within a second (without `readonly` it ran on to its limit), and a reader's deadline cuts a query's time.

Decided differently from the design, or settled where it said nothing:

- **The window ends a minute before the evaluation**, so an alert comes a minute or two after a change; reading to the evaluation's own time would show a counter's rate low, and fire "below" rules, whenever the last export has not arrived.
- **No value is not "back on the right side"**, so a route whose traffic stops does not resolve. Data that stops arriving has its own rule since 26 November 2026 ([below](#data-stops-arriving-as-built)).
- **Route windows are at most 30 minutes**, not 60, and route rules read without `FINAL`, for the cost above.
- **Rules are spread by when they were added**, each keeping its place in the minute, rather than spread over each minute's pass.
- **Environment** is one per rule, production by default, as the telemetry pages read one at a time; the error rules' "all environments" has no telemetry counterpart.
- **A histogram's rule** reads p50, p95, or p99, not its observations per second; a counter's rate covers a rate.
- **The Services page and a metric's page** gained the addresses alerts link to: a service shown alone with its route marked (saying so when the list does not hold the service, or the route is past the 100 busiest), and a metric's chart narrowed to a host or an attribute value. Neither page offers a control for those filters yet; the address sets them.
- **The form's pickers** are text fields with suggestions, so a service, route, metric, host, or attribute value that has not reported can be typed, and saved with the warning.

### Data stops arriving, as built

Built on 26 November 2026, from the design [above](#alerts-on-data-that-stops-arriving). Code: `apps/api/src/alerts/stopped-rules.ts`, with `kinds.ts`, `telemetry-rules.ts`, `fire.ts`, and `routes.ts`; migration `0031_notification_any_areas`; and `apps/web/src/features/alerts/` ([the dashboard](dashboard.md#813-alerts)). The notifications' bodies are in [webhooks](webhooks.md#datastopped-and-datastopped_resolved).

- **Two kinds, one name.** Events and telemetry need different areas ([access](access.md#alert-rules-and-the-areas-they-watch)), and an alert's readers go by the kind it fired under (`alert_history.kind`), so the design's one kind is two in the API: `events_stopped` (source `events`) and `telemetry_stopped` (source `traces`, `logs`, or `metrics`). Both are named "Data stops arriving", and the form shows them as one: its **Data** select picks the kind. A rule changed from events to traces changes kind, as any rule may.
- **Settings:** `source`, `environment` (production when none is sent), `eventName` (events), `service` (traces and logs), `metric` (required) and `host` (metrics), each null when unused or for all; `windowMinutes`, one of 5, 10, 15, 30, 60, 120, 240, 360, 720, or 1440 (60 by default); and `minCount`, 1 to 1,000,000 (1 by default). Other sources' fields are stored as null. Errors: `invalid_source`, `invalid_window`, `invalid_min_count`, `invalid_metric`, and `invalid_attribute` (a host past 1,000 characters).
- **Evaluation:** with the telemetry rules, by the worker every minute (`takeDueRules`, the project budget, the dashboard's reader, settings, and limits, and the recorded failures above). One query per rule.
- **Counting by arrival.** Every table has `received_at`: events and, since ClickHouse migration 0011, spans and metric rows carry the time the API received them; logs carry ClickHouse's clock as it wrote them (migration 0005). The window ends 30 seconds before the evaluation (`ARRIVAL_LAG_MS`, as error rules), so an insert still landing is counted the next minute. The tables are ordered by project, then their event time, not by arrival, so each query also bounds the event time: events from a day before the window (collection refuses older ones) to 5 minutes after it; telemetry from an hour before to an hour after (`TELEMETRY_LATE_MS`; OTLP takes times up to an hour ahead). Telemetry that arrives more than an hour after it happened, such as a backlog sent after an outage, is not counted: the rule stays firing until current data arrives.
- **What counts:** events that web analytics counts (no errors, no Web Vitals), of one name or all; spans and log records of one service or all; points of one metric in `metric_points` and `metric_histograms`, of one host or all. Each query filters by project first and has `LIMIT N`, so it stops once it has enough; it reads without `FINAL`, so a retried copy counts twice until merged, which can delay an alert but never cause one.
- **Measured** in a test database: a project with 86,400 spans over two days (one every 2 seconds), a 30-minute rule: 7,649 rows read, with or without matching data. With 172,800 spans (one a second) and a 24-hour rule: 93,505 rows read for a service with no spans (the window and the hour before it, in whole granules), 61,824 for one with spans. Never the project's whole retention. `apps/api/tests/stopped-alerts.test.ts` checks that a 30-minute rule reads at most 3 granules (24,576 rows).
- **Firing and resolving** (`judge`): fires when the count is below N; resolves at the next evaluation with at least N, without the other telemetry rules' wait of a whole window. A rule whose window starts before its `active_since` has no value yet: it neither fires nor resolves.
- **Notifications:** `data.stopped` and `data.stopped_resolved`. The message names the source and filter, the project, the environment, and the window: "No events from Main site in production in the last 30 minutes.", "Only 2 events named waitlist_signup from Main site in production in the last 1 hour, fewer than the rule's 3.", and, resolved, "Events arrive again from Main site in production." (with "At least N arrived in the last …" when N is above 1; the count stops at N). The link is the rule's page on the Alerts page. The inbox titles: "Data stopped arriving: <rule>", "Data arriving again: <rule>".
- **The save warning** looks for one record of the rule's source in the last 24 hours, by arrival, and says when none arrived: the rule fires once it is a window old unless they arrive.
- **Access:** `events_stopped` needs web analytics or product analytics at view, `telemetry_stopped` monitoring. Its inbox items need uptime and alerts and one of the two analytics areas: `notifications.any_areas` (migration 0031) holds areas a reader needs one of, besides `areas`, all of which they need.
- **Tests:** `apps/api/tests/stopped-alerts.test.ts` (each source, by arrival, below N, a new rule's first window, the filters, the environment, another project's data, the messages, the worker's pass, the rows read, the routes' checks, and who sees the rules, their alerts, and their inbox items), and `apps/web/tests/browser/stopped-alerts.test.tsx` (the form, its sources by access, the bodies sent, the rule's row and edit form).

### Not done in step 4

- Alerts on matching log lines.
- A per-minute rollup of requests by route, which would let route rules read a few rows a minute instead of the window's spans, and allow windows past 30 minutes.
- A route rule cannot narrow to an HTTP method or status code beyond what its route names.
- A metric rule on a histogram's observations per second, on an attribute of the resource other than `host.name`, or on more than one attribute value.
