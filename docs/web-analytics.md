## 1. The event

### Facts, not totals

Ottertrail stores one row per thing that happened (an event) and computes every number from those rows when a report asks. Nothing stores a running total such as "pageviews today".

This makes definitions changeable. If the session timeout changes from 30 to 20 minutes, reports recompute from the same rows. It also makes cleanup possible: fake or bad events can be deleted, and every report stays correct.

### The events table

Created by `apps/api/src/db/migrations/0001_create_projects_and_events.ts`.

| Column              | Meaning                                                                     | Set by   |
| ------------------- | --------------------------------------------------------------------------- | -------- |
| `project_id`        | The project (website or app) the event belongs to                           | Server   |
| `event_id`          | Random ID generated by the sender                                           | Sender   |
| `name`              | `pageview`, or a custom name such as `signup`                               | Sender   |
| `occurred_at`       | When it happened, by the sender's clock. Reports use this.                  | Sender   |
| `received_at`       | When the server stored it, by the database clock                            | Database |
| `path`              | Page path without the query string, such as `/lessons/closures`             | Sender   |
| `referrer`          | The page that linked here, if the browser reports one                       | Sender   |
| `utm_*` (5 columns) | Campaign tags from the page URL: source, medium, campaign, term, content    | Sender   |
| `properties`        | Custom details as a JSON object, such as `{ "plan": "free" }`, at most 8 KB | Sender   |

Later steps add columns in new migrations: browser, OS, device, and country (step 4), visitor (step 5), and session (step 6).

### Two timestamps

The sender's clock can be wrong, and events can arrive late: a phone goes offline, or a browser retries. `occurred_at` is what reports use; `received_at` is the server's trusted clock, used to spot bad clocks and late data. Step 2 decides how far apart the two may be.

### Event IDs make retries harmless

Networks lose replies. A sender can deliver an event, never hear back, and send it again. The primary key is `(project_id, event_id)`, and inserts skip IDs that already exist (`on conflict do nothing`), so:

- a retried event is stored once;
- the same event twice in one batch is stored once;
- the same ID in two different projects is two different events.

Delivery is "at least once"; storing is idempotent (doing it twice changes nothing), so each event counts exactly once. `storeEvents` in `apps/api/src/collection/event-store.ts` returns how many events were new and how many were duplicates.

A batch is one SQL statement, so it is saved completely or not at all. A batch with one invalid event saves nothing.

### Columns plus a flexible part

Fields every event has get their own typed columns, because reports filter and group by them constantly. Custom details go in one `jsonb` column, limited to a JSON object of at most 8 KB.

### Limits in the database

Check constraints cap text lengths (event name 200 characters, path and referrer 2,048, each UTM value 200) and the properties size. Step 2 validates requests before they reach the database; these constraints are the last line of defense.

### Indexes follow the questions

Almost every report asks "this project, between these two times", so the table has an index on `(project_id, occurred_at)`. Add other indexes only when a real query needs one.

### Not done yet

- Removing query strings from URLs happens in the collection endpoint (step 2) and the tracker (step 3). The table only stores what it is given.
- There is no retention or deletion policy for events yet.
